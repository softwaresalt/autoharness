# Lifting shipment-reconcile no-auto-repair for queued-with-active-work: bounded operator-invoked repair vs keep-out

## Problem Frame

<!-- BEGIN:problem-frame -->
The queued-with-active-work inconsistency (shipment record `queued` while manifest tasks are `active`/`done`) is ALREADY fully DETECTED at three layers, all detect-and-report only: `SHIPMENT_STATE_INCONSISTENT` (Ship intake, 106-S/102-F), `CLAIM_VERIFY_FAILED` (Ship post-claim, 106-S/102-F), and shipment-reconcile pre-mode `record-queued-with-active-work` classification (109-S/105-F). 936C68F3 part (2) — true self-repair / auto re-claim — has been DECISION-GATED on the operator deliberately lifting shipment-reconcile's "no auto-repair" stance. The operator's dark-factory "with all approvals" instruction authorizes DELIBERATING this lift, NOT blanket authority to bypass safety. The EXTERNAL backlogit-internal active->queued transition guard is RESOLVED-UPSTREAM (backlogit 1.8.0 isValidShipmentTransition forbids active->queued; ClaimShipment is all-or-nothing with rollback, 061-F). Question: can the report-and-halt / no-auto-repair stance be SAFELY lifted, and if so exactly how, WITHOUT inventing locks/CAS/leases or unsafe mutation authority (operator explicit constraint)? Route claude-opus-4.8/anthropic/high, DARK_MODE. No source/template/config mutated by this deliberation.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
A) FULL AUTOMATIC self-repair — reconcile silently auto re-claims (queued->active) whenever it detects queued-with-active-work. REJECTED for three independent safety reasons: (1) shipment-reconcile's core invariant is "NEVER mutates the shipment record or any task" — every closure/audit path depends on that no-mutation property; injecting automatic mutation into the safety-critical skill breaks the guarantee. (2) The correct repair DIRECTION is genuinely AMBIGUOUS: queued-with-active-work can mean "claim silently dropped but work is legitimately proceeding" (forward-repair = re-claim to active) OR "session crashed mid-flight, tasks are half-done/torn" (backward = return tasks to queued / operator investigation); automation cannot reliably distinguish, and a wrong forward-repair MASKS incomplete or corrupt work. (3) Auto-mutation to `active` can VIOLATE the at-most-one-active-shipment invariant under the documented TOCTOU windows — the 109-F pipeline-topology gate is DETECTION-ONLY (no lock/lease at any scope) — silently producing two active shipments. B) KEEP report-and-halt permanently, no lift. Safe, but does not answer the operator's explicit ask to decide whether a safe lift exists, and leaves the high recovery cost (manual archived-status surgery) unaddressed. C) (CHOSEN) CONSTRAINED lift — NOT automatic. Add an explicit, operator-invoked, single-purpose guarded repair MODE (e.g. shipment-reconcile `mode: repair-record-status`, gated behind an explicit `--confirm` flag) that performs ONLY the constrained FORWARD transition (re-claim queued->active; best-effort DETECTION + fail-closed, NOT provably safe — see Addendum B) and ONLY when ALL strict preconditions hold, else falls closed to the existing report-and-halt.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Option C — CONSTRAIN, do NOT fully lift. Decision: the report-and-halt / no-auto-repair DEFAULT is PRESERVED for all existing pre/post/safe-close paths (they remain strictly no-auto-mutation). The stance is lifted ONLY into a distinct, opt-in, operator-invoked `repair-record-status` mode that is ISOLATED from the detect-and-report paths. That mode executes the forward re-claim ONLY when ALL of these preconditions hold, else it refuses and falls back to report-and-halt: (i) TOPOLOGY precondition via a TARGET-AWARE READ-ONLY REPAIR-INSPECTION (RE-DELIBERATED 2026-08-06 — see Addendum A; supersedes the original "invoke `autoharness gate pipeline-topology` and require zero other active" wording, which is UNREACHABLE for this repair). The plain `gate pipeline-topology` invocation cannot serve as this precondition because its detect-before-consistency scan returns SHIPMENT_STATE_INCONSISTENT (blocked) on the very queued-with-active-work TARGET being repaired BEFORE the active-shipment invariant is ever evaluated (src/autoharness/gates/topology.py `_evaluate_core`: `_detect_before_consistency` runs and early-returns ahead of `_active_invariant_check`), so the mode could never observe the "zero other active" signal it needs. Instead the repair mode performs its OWN target-aware READ-ONLY inspection composed of EXISTING backlogit read commands (no new gate code required): (a) enumerate all shipments (`backlogit shipment list`) and require ZERO active shipments (the target is still `queued`, so it will become the SOLE active); (b) confirm the TARGET is the SOLE queued-with-active-work inconsistency — every OTHER `queued` shipment must have NO `active`/`done` manifest task (a shipment carrying a non-lifecycle/malformed status, e.g. a legacy `blocked` value, HALTS for manual remediation — see Addendum C); (c) any OTHER active shipment, OR any NON-target inconsistency, OR any ambiguity => REFUSE + report-and-halt. This DISCRIMINATES the narrow reparable state while FAILING CLOSED on all non-target ambiguity. The inspection is strictly READ-ONLY; the forward re-claim still executes ONLY through backlogit's existing atomic all-or-nothing ClaimShipment (061-F) — queued->active only, no locks/CAS/leases invented. (ii) The record re-reads as `queued` — the ONLY re-claimable shipment status (CORRECTED, see Addendum C). Backlogit 1.8.0 has NO `blocked` shipment status (ShipmentStatus is only queued|active|shipped|abandoned) and isValidShipmentTransition has no blocked state and no blocked->queued transition. A shipment record whose persisted status is anything other than a valid 1.8.0 lifecycle state — e.g., a legacy `blocked` value — is treated as MALFORMED LEGACY DATA: REFUSE + HALT for manual remediation; the mode NEVER fabricates a blocked->queued (or any) transition. (iii) Manifest tasks are `active`/`done` in a shape consistent with a silently-dropped claim, not a torn/partial mid-flight state. (iv) backlogit is reachable (CLI-preferred re-read per 106-S); the repair reuses backlogit's EXISTING atomic all-or-nothing ClaimShipment (061-F), so it is atomic and STRICTLY SINGLE-SHOT (NOT idempotent — CORRECTED, see Addendum C): a repeated claim on an already-`active` shipment is REJECTED by backlogit's double-claim guard — ClaimShipment issues MoveShipmentStatus(active), and isValidShipmentTransition permits ONLY queued->active and active->shipped|abandoned, so an active->active re-claim returns ErrShipmentConflict. This fail-closed rejection IS the double-claim/TOCTOU guard (a racing or repeated second claim on an already-active target fails closed, never silently re-activates); NO new lock/lease/CAS is invented (satisfies the operator's do-not-invent-locks constraint). (v) Every repair writes a structured audit entry AND a telemetry event, mirroring the pipeline-topology force-audit pattern. BACKWARD-repair (returning tasks to queued) stays permanently MANUAL/operator — too ambiguous to automate. FULL automatic/silent self-repair is permanently REJECTED. Net: mutation authority enters shipment-reconcile ONLY through a narrow, explicit, target-aware-inspection-gated, TOCTOU-explicit, forward-only, atomic, audited, operator-invoked seam; the ambiguous/unsafe directions stay out. This is buildable and bounded (single template family: shipment-reconcile skill + audit/telemetry wiring).
<!-- END:chosen-direction -->

### Addendum A (RE-DELIBERATION 2026-08-06, route claude-opus-4.8/anthropic/high, DARK_MODE — independent BLOCKED-review repair)

FINDING (P1, independent re-review): the original precondition (i) — "invoke `autoharness gate pipeline-topology` and require zero other active shipments" — is UNREACHABLE for the exact state this repair targets. Root cause (read-only source inspection, NOT mutated): in `src/autoharness/gates/topology.py::_evaluate_core`, the check order is `_detect_before_consistency` (line ~722) THEN `_active_invariant_check` (line ~727), and `_detect_before_consistency` early-returns a `blocked` CheckResult with token `SHIPMENT_STATE_INCONSISTENT` as soon as it finds ANY `queued`/`blocked` shipment whose manifest has an `active`/`done` task. The repair target IS such a shipment, so a `gate pipeline-topology` invocation always halts on the target's own (expected, reparable) inconsistency before the zero-active signal is computed — the precondition can never be satisfied.

RESOLUTION (chosen): replace precondition (i) with a TARGET-AWARE READ-ONLY REPAIR-INSPECTION composed from EXISTING backlogit read commands (`backlogit shipment list` / per-shipment `shipment get` / per-task `get`), NOT the early-halting topology gate. The inspection: (a) requires ZERO active shipments; (b) requires the TARGET to be the SOLE queued-with-active-work inconsistency (all OTHER queued/blocked shipments have no active/done tasks); (c) fails closed (REFUSE + report-and-halt) on any OTHER active shipment, any NON-target inconsistency, any per-item anomaly, or any ambiguity. It remains operator-invoked (`--confirm`), forward-only (queued->active) through the existing atomic all-or-nothing ClaimShipment (061-F), atomic per existing behavior, with NO locks/CAS/leases and NO silent/broad/backward repair.

WIDTH-ISOLATION EVALUATION: the inspection is expressed as PROSE in the shipment-reconcile SKILL (task B1 / 112.001-T, template family = shipment-reconcile SKILL) composing existing read-only backlogit reads; it requires NO new gate/CLI code surface. Therefore width isolation does NOT require a separate task, and 118-S membership stays exactly {112.001-T, 112.002-T, 112.003-T, 112.004-T}. A separate bounded CLI/gates task would only be warranted if the plan chose to add a new target-aware read-only gate mode — explicitly NOT chosen here, to keep the fix within a single template family and bounded. HARDENING: adds H7 (target-aware inspection fails closed on all non-target ambiguity) to 112-F. No source/template/config mutated by this re-deliberation.

### Addendum B (SECOND RE-DELIBERATION 2026-08-05, route claude-opus-4.8/anthropic/high, DARK_MODE — second independent BLOCKED-review repair)

FINDING (P1, second independent re-review): the plan and its provenance described the forward re-claim as "provably-safe" and "topology-gated", which OVERSTATES the guarantee. The target-aware read-only repair-inspection (Addendum A) and the forward ClaimShipment are SEPARATE, UNLOCKED operations: (a) another claim can race in the window BETWEEN the inspection and the re-claim; (b) the post-condition may only DETECT a second active shipment AFTER the target has already been activated; (c) the target's active->queued rollback is FORBIDDEN by backlogit 1.8.0 (isValidShipmentTransition), so the mode cannot undo its own re-claim if a race is detected post-hoc. The existing zero-active inspection + ClaimShipment therefore do NOT prevent two active shipments, do NOT serialize concurrent claims, and are NOT "provably safe."

RESOLUTION (chosen): RETAIN the documented TOCTOU limitation explicitly (identical to the 109-F claim-path TOCTOU: best-effort DETECTION, not prevention). The mode NEVER claims prevention/serialization/atomic exclusion/"provably safe." The post-condition re-verifies the GLOBAL exactly-one-active==target invariant AFTER the re-claim and, on detecting a two-active state, FAILS CLOSED: emit audit+telemetry, HALT, and surface the inconsistency for OPERATOR remediation. The mode performs NO remediation mutation and MUST NOT attempt an active->queued rollback of the target. Fail-closed manual remediation = the operator resolves the two-active state via backlogit's OWN sanctioned lifecycle transitions (e.g., completing/shipping or otherwise terminalizing one shipment), never via an autoharness-issued active->queued rollback. A test is required that a concurrent claim racing between inspection and re-claim is detected by the post-condition and fails closed to operator remediation (folded into 112.002-T).

ACCEPTABILITY DECISION (honest): the constrained operator-invoked FORWARD repair REMAINS ACCEPTABLE with this residual TOCTOU risk, so 112-F is NOT re-scoped to report-only and mutation is NOT deferred. Rationale: (1) operator-invoked, single-shot, in a deliberate single-active manual context — not automatic; (2) the residual two-active window is IDENTICAL in nature/scope to the already-accepted 109-F claim TOCTOU — NO new risk class is introduced beyond what every ClaimShipment already carries; (3) the post-condition DETECTS the race and FAILS CLOSED to audited operator remediation, bounding blast radius; (4) the forbidden active->queued rollback is never performed. Report-only was CONSIDERED and REJECTED: it would remove the operator's ability to perform the safe forward re-claim with NO safety gain (the underlying ClaimShipment TOCTOU is identical whether reached here or via a normal claim). PRESERVED: no locks/CAS invention, target-aware non-target-ambiguity refusal, explicit `--confirm` operator invocation, narrow forward-only semantics. HARDENING: adds H8 (TOCTOU residual risk explicit; detection + fail-closed; no forbidden rollback; concurrent-claim test) to 112-F. ### Addendum C (THIRD RE-DELIBERATION 2026-08-05, route claude-opus-4.8/anthropic/high, DARK_MODE — third independent BLOCKED-review repair; two P2 factual corrections)

Two factual defects in this deliberation and its dependent artifacts were corrected against the verified backlogit 1.8.0 source (read-only inspection of C:\Source\GitHub\backlogit @ fd8d2c9d; NOT mutated). This addendum is authoritative and SUPERSEDES the superseded wording wherever it appears, including in Addenda A/B, 112-F, and the 112.00x-T tasks.

P2-1 (ClaimShipment is NOT idempotent — single-shot). The chosen-direction previously called the forward re-claim "atomic and idempotent." That is FACTUALLY WRONG: `internal/core/shipment.go::isValidShipmentTransition` permits ONLY `queued->active` and `active->{shipped,abandoned}`; a `ClaimShipment` on an already-`active` shipment issues `MoveShipmentStatus(active)` which evaluates `active->active` as INVALID and returns `ErrShipmentConflict`. So a repeated claim is REJECTED, not a silent no-op. CORRECTION: the re-claim is atomic and STRICTLY SINGLE-SHOT (NOT idempotent). This rejection is exactly the desired DOUBLE-CLAIM GUARD and preserves the TOCTOU fail-closed behavior: a repeated or racing second claim on an already-active target FAILS CLOSED (ErrShipmentConflict) rather than re-activating; the mode surfaces the conflict for operator handling and NEVER retries into a second activation. (The 109-F/Addendum-B TOCTOU window between the read-only inspection and the ClaimShipment is unchanged; the single-shot guard is what makes the post-claim two-active state DETECTABLE-and-fail-closed rather than silently doubly-applied.) No new lock/lease/CAS invented.

P2-2 (no `blocked` shipment status / no blocked->queued transition in 1.8.0). The plan previously spoke of a `blocked` shipment record that "must first go blocked->queued via gate resolution" and enumerated "every OTHER queued/blocked shipment." That references a NONEXISTENT lifecycle: `ShipmentStatus` in 1.8.0 is ONLY `queued|active|shipped|abandoned` (`internal/core/shipment.go`), and `isValidShipmentTransition` has NO blocked state and NO blocked->queued edge. CORRECTION: `blocked` is REMOVED from all supported repair paths. The re-claimable status is `queued` only. If a shipment record is encountered whose persisted status is not a valid 1.8.0 lifecycle state (e.g., a legacy `blocked` value carried over from stale/legacy data), it is classified as MALFORMED LEGACY DATA and the mode REFUSES + HALTS for OPERATOR manual remediation — it NEVER fabricates a blocked->queued (or any) transition. HARDENING: 112-F H3 is re-cast from "BLOCKED HARD-EXCLUSION (blocked->queued via gate resolution first)" to "MALFORMED-STATUS HARD-EXCLUSION (non-lifecycle status => malformed legacy data => refuse + halt for manual remediation; no fabricated transition)."
