# Ship execution contract must exclude pre-archived manifest members from the executable task set

## Problem Frame

<!-- BEGIN:problem-frame -->
A shipment manifest now serves TWO purposes that have silently diverged.

(1) CLOSURE MEMBERSHIP (P-015 / `classify_shipment_close_path`): after the correction at HEAD e88a8d62, a manifest MUST list every child of its covering feature — including children that were superseded and archived before the shipment runs — or the classifier returns `safe_close` with "feature member X has children outside the manifest", and safe-close then halts on the pre-archived protected member. 144-S = [136-F, 136.002-T, 136.003-T, 136.001-T(archived, SUPERSEDED by 138.001-T)] and 145-S = [137-F, 137.002-T, 137.001-T, 137.003-T, 137.004-T, 137.005-T(archived), 137.006-T(archived)] are correct under this rule.

(2) EXECUTABLE TASK SET (Ship Step 2 task loop): the installed `.github/agents/_ship.agent.md` says, verbatim, "For each task in the shipment/feature: 1. **Claim**: Move the task to active via `backlogit_move_item`." It iterates the manifest with no status filter, no `pre-archived` classification, and no `shipment-reconcile mode: pre` intake step. The template `templates/agents/_ship.agent.md.tmpl` DOES carry that intake step (Step 0.5 item 6) and builds its ready queue from label+QUEUED status (Step 3), but derives it from the FEATURE rather than the manifest and never states a pre-archived exclusion rule, so the template contract is under-specified rather than correct.

The two purposes are now in direct conflict: the very membership that makes closure valid makes execution invalid. Ship, running 144-S under the INSTALLED dogfood contract, would reach 136.001-T and attempt to move an archived, explicitly `*** SUPERSEDED — NOT EXECUTABLE — DO NOT SCHEDULE ***` task to `active` — either reactivating superseded work that 138.001-T already replaces, or hard-failing mid-loop with a claimed shipment and a partially-executed manifest.

Existing guards do not catch this. Step 0.5 item 1a's queued-with-active-work early-warning halts only when a manifest task is `active` or `done`; an archived task carries `status: archived`, so the scan passes and execution proceeds straight into the unfiltered loop. `templates/skills/shipment-reconcile/SKILL.md.tmpl` already classifies `pre-archived` as VALID across `mode: pre`, safe-close, and cascade — the knowledge exists in the skill, but the Ship agent contract never consults it before the loop.

Blast surface: 146-S ([138-F, 138.001-T]) has no pre-archived members and executes safely today. 144-S and 145-S both do and are blocked until the contract is fixed.

P-021 C1: FAILS. The e88a8d62 work was a shipment-MEMBERSHIP correction (backlog records + closure classifier behaviour). This is an EXECUTION-CONTRACT surface (agent-instruction task loop + its regression tests). Different contract, different test surface, so capture-first normal intake applies — captured as stash B19E9662, deliberated here.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
OPTION A — Contract-level executable-set derivation with explicit pre-archived exclusion (BOTH the installed dogfood agent and the template), plus regression coverage.
Ship stops treating the manifest as the executable set. It derives the executable set by reading each manifest TASK artifact's record and keeping only `queued`/`active` statuses, explicitly excluding `archived` (`pre-archived`) members and recording them in a skipped set. The full manifest is left completely untouched, so P-015 cascade classification is unaffected. The installed copy additionally gains the `shipment-reconcile mode: pre` intake reference the template already has, which is the existing authority for classifying a member `pre-archived` as VALID. `.autoharness/harness-manifest.yaml` checksum for `.github/agents/_ship.agent.md` is refreshed in the same change.
+ Fixes the actual executing contract (144-S runs under the installed copy).
+ Zero backlog-record mutation; no manifest weakening; no unarchiving.
+ Reuses the `pre-archived` vocabulary already defined and tested in shipment-reconcile — no new concept.
+ Instruction-level, so no source/schema/CLI blast radius.
- Prose contract, enforced by text-assertion regression tests rather than executable logic.

OPTION B — Revert the manifests: strip pre-archived members back out of 144-S/145-S.
- REJECTED. Directly undoes e88a8d62 and reintroduces the `safe_close` misclassification and the P-015 protected-member halt this branch exists to fix. Explicitly out of bounds ("do not weaken closure membership").

OPTION C — Unarchive/requeue 136.001-T, 137.005-T, 137.006-T so the loop's assumption holds.
- REJECTED. Reactivates work explicitly stamped `[SUPERSEDED by 138.001-T]` / superseded, duplicating 138.001-T and the 137 successors. Explicitly out of bounds ("do not reactivate superseded tasks"). Also merely hides the contract defect until the next superseded child appears.

OPTION D — Enforce in code: a new `autoharness gate` subcommand (or a `shipment_execution.py` module) that emits the executable set and fails closed.
- DEFERRED, not rejected on merit. Strongest enforcement, but adds a CLI surface, a JSON contract, schema/exit-code semantics, and gate wiring in three agent files — well past the 2-hour rule and past a prerequisite's acceptable blast radius, while 144-S waits. Ship is instruction-driven at this seam today (the whole Step 2 loop is prose), so a prose contract is the in-kind fix. Recorded in open questions as a follow-up candidate.

OPTION E — Template-only fix.
- REJECTED. 144-S executes under the INSTALLED `.github/agents/_ship.agent.md`. A template-only edit changes nothing for the shipment that is actually blocked, and would leave the installed mirror drifted with a stale manifest checksum.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
OPTION A — smallest executable contract fix, applied to BOTH Ship contracts, with regression coverage, shipped as its own separate prerequisite shipment ordered between 146-S and 144-S.

Precise contract to be stated in both `.github/agents/_ship.agent.md` (Step 2 task loop) and `templates/agents/_ship.agent.md.tmpl` (Step 3 ready-queue construction / Step 4 loop):

1. The shipment manifest (`custom_fields.items`) is the CLOSURE membership record. It is NEVER the executable task set and is NEVER mutated to make execution work.
2. Before the loop, derive the EXECUTABLE TASK SET: filter the manifest to task artifacts (IDs ending `-T`; the covering feature is resolved via `parent_id` and is not executed), read each task record, and keep only those whose status is `queued` or `active`.
3. Explicitly EXCLUDE members whose record is archived — the `pre-archived` classification already defined by `shipment-reconcile`. Record them in a reported `pre_archived_skipped` set with their IDs; never claim them, never move them to `active`, never unarchive them, never remove them from the manifest.
4. A `pre-archived` manifest member is EXPECTED AND TOLERATED, not an error — it is exactly what a closure-valid manifest looks like when a child was superseded before the shipment ran. It must not trigger a halt, and it must not be conflated with the Step 0.5 item 1a `SHIPMENT_STATE_INCONSISTENT` early-warning, which fires only on `active`/`done`.
5. If the derived executable set is EMPTY while the manifest is non-empty, halt and report rather than proceeding to build/PR — a fully pre-archived manifest is a closure case, not an execution case.
6. Installed copy only: add the `shipment-reconcile mode: pre` intake reconciliation reference that the template already carries at Step 0.5 item 6, adapted to this repository's self-hosting note (the skill is read from `templates/skills/shipment-reconcile/SKILL.md.tmpl`, since `.github/skills/shipment-reconcile/SKILL.md` is not installed here).
7. `.autoharness/harness-manifest.yaml`'s `.github/agents/_ship.agent.md` checksum is refreshed in the SAME change as the instruction edit, computed from the LF-normalized committed git blob per the established procedure, with an appended provenance note.

Regression coverage, in the established `tests/test_ship_safe_close_pointer.py` contract-test pattern: a new module asserting BOTH the template and the installed mirror declare the executable-set derivation and the pre-archived exclusion; a negative control asserting the old unconditional "For each task in the shipment/feature ... Move the task to active" formulation no longer stands alone; and a data-level regression over a synthetic closure-valid manifest with superseded archived children asserting that `classify_shipment_close_path` still returns the cascade verdict with the archived members PRESENT in the manifest — pinning the invariant that the execution fix must never be "fixed" by removing them.

Sequencing: this ships as its own shipment, containing only newly created queued items (NO pre-archived members), so it is executable under the CURRENT unfixed contract. Chain becomes 146-S -> <this shipment> -> 144-S -> 145-S. A MANDATORY post-merge instruction reload is required before 144-S begins, because the fix only takes effect for a Ship session that reloads `.github/agents/_ship.agent.md` after the merge.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
1. Executable enforcement (Option D) remains an open follow-up: a machine-checkable executable-set derivation (`autoharness gate` subcommand or a `shipment_execution` module) would replace the prose contract with fail-closed logic. Deliberately deferred here for 2-hour-rule and blast-radius reasons while 144-S is blocked; not captured as a separate stash entry in this session because it is a design alternative recorded in this deliberation rather than a distinct defect.

2. Whether the Step 0.5 item 1a early-warning should ALSO learn about `archived` status (currently it only fires on `active`/`done`). Decision: NO change in this fix. Item 1a's purpose is detecting a stale `queued` shipment record whose work already started; an archived member is not that condition and folding it in would risk a false fail-closed halt on every closure-valid manifest. The task loop's derivation step is the correct and sufficient seam.

3. Ordering of contract edit vs. regression test across the two harvested tasks. Ship enforces a green gate at every task boundary, so a test-first (red) ordering would break the gate on the first task. Contract task therefore precedes the test task, and the test task carries an explicit negative-control assertion so the guard is proven to discriminate against the pre-fix text rather than merely passing vacuously.

4. Template/dogfood divergence is intentional and pre-existing: the template already has the `mode: pre` intake step and a label+status ready queue; the installed mirror does not, and has other unrelated drift (798 lines vs. 1073). This fix mirrors the NEW contract text into each file's own structure rather than performing a full re-render, per the width-isolation precedent recorded repeatedly in `.autoharness/harness-manifest.yaml` notes.

5. Residual risk if the post-merge instruction reload is skipped before 144-S: a Ship session still holding the pre-merge contract in context would re-expose the original failure. Mitigated by recording the reload as a mandatory Orchestrator step in the shipment-order record and the staging handoff memory, not by any backlog-record mechanism.
<!-- END:open-questions -->
