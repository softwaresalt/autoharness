=== CYCLE 1 FINDINGS (4 raised: 2 P1, 2 P2 — all RESOLVED) ===

P1-1 AMBIGUOUS-PROVENANCE BRANCH UNDERSPECIFIED — RESOLVED.
The original resolution order had only 6 branches and disposed of ambiguous live/archive provenance in a trailing prose sentence: such a record 'is never a cursor in any branch; if such a record occupies the active role, resolution falls to branch 3's fail-closed treatment.' But branch 3 was `more than one active`, so a SINGLE active shipment with ambiguous provenance matched NO branch and would have fallen through to `resume_active` — recommending resumption of a record whose own state is corrupt. This is precisely the failure shape named in docs/compound/2026-08-07-copilot-review-fix-introduces-new-filter-bug.md: an anomaly silently re-expressed as a normal result. FIX: promoted ambiguous provenance to its own branch 3, evaluated on the FULL UNFILTERED enumeration BEFORE any active/ready partitioning, with a distinct reason code `ambiguous_provenance` plus offending ids; the resolution order is now 7 branches. Added hardening item H3b making it a P0 defect to fold `ambiguous_provenance` into `multi_active_anomaly` or `no_candidates`, or to skip the ambiguous record and continue, and requiring a dedicated regression test for the single-active-but-ambiguous case. Mirrored into 115-F DoD#5 and 115.001-T AC6.

P1-2 MISSING INTEROP CONTRACT — `next_eligible` VS `ready_set` MEMBERSHIP — RESOLVED.
Under branch `resume_active` the cursor is an `active` shipment, but Phase 1's `ready_set` contains ONLY live `queued` shipments. The plan never stated this, so a consumer could reasonably assert `next_eligible in ready_set` and break on the single most important branch (crash resumption) — the exact case the feature exists to serve. FIX: added an explicit 'next_eligible is NOT a ready_set member' contract section naming `next_eligible_reason` as the authoritative discriminator and forbidding consumers from treating non-membership as an error; propagated to 115.003-T AC6 and required in the --json field table.

P2-1 `next_eligible_detail` REFERENCED BUT NEVER SPECIFIED — RESOLVED.
The backward-compatibility section named a third field with no shape. FIX: specified as {"candidate_ids": [...], "offending_ids": [...]} with BOTH keys ALWAYS present (empty lists when not applicable) so consumers need no key-existence checks; added a full field table. Propagated to 115.001-T AC4 and 115.002-T AC1.

P2-2 OPT-IN FLAG VS UNCONDITIONAL EMISSION LEFT OPEN — RESOLVED.
014-DL deferred this to the plan and the plan then also left it open, which would have pushed an interface decision down into implementation. FIX: decided explicitly — emit unconditionally, no new flag, no new subcommand; additive fields are already backward compatible and an opt-in flag would create two payload shapes to test and document for no benefit. Recorded in 115.002-T AC8.
