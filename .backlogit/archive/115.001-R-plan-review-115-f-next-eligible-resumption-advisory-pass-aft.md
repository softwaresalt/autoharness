=== CYCLE 1 FINDINGS (4 raised: 2 P1, 2 P2 — all RESOLVED) ===

P1-1 AMBIGUOUS-PROVENANCE BRANCH UNDERSPECIFIED — RESOLVED.
The original resolution order had only 6 branches and disposed of ambiguous live/archive provenance in a trailing prose sentence: such a record 'is never a cursor in any branch; if such a record occupies the active role, resolution falls to branch 3's fail-closed treatment.' But branch 3 was `more than one active`, so a SINGLE active shipment with ambiguous provenance matched NO branch and would have fallen through to `resume_active` — recommending resumption of a record whose own state is corrupt. This is precisely the failure shape named in docs/compound/2026-08-07-copilot-review-fix-introduces-new-filter-bug.md: an anomaly silently re-expressed as a normal result. FIX: promoted ambiguous provenance to its own branch 3, evaluated on the FULL UNFILTERED enumeration BEFORE any active/ready partitioning, with a distinct reason code `ambiguous_provenance` plus offending ids. Added hardening item H3b making it a P0 defect to fold `ambiguous_provenance` into `multi_active_anomaly` or `no_candidates`, or to skip the ambiguous record and continue, and requiring a dedicated regression test for the single-active-but-ambiguous case. Mirrored into 115-F DoD#5 and 115.001-T AC6. (NOTE: cycle 1 described the outcome set as '7 branches' of the analyzer; cycle-2 finding C2-P1-1 below corrects that attribution — the count of OUTCOMES is 7, but only 6 are analyzer branches.)

P1-2 MISSING INTEROP CONTRACT — `next_eligible` VS `ready_set` MEMBERSHIP — RESOLVED.
Under branch `resume_active` the cursor is an `active` shipment, but Phase 1's `ready_set` contains ONLY live `queued` shipments. The plan never stated this, so a consumer could reasonably assert `next_eligible in ready_set` and break on the single most important branch (crash resumption) — the exact case the feature exists to serve. FIX: added an explicit 'next_eligible is NOT a ready_set member' contract section naming `next_eligible_reason` as the authoritative discriminator and forbidding consumers from treating non-membership as an error; propagated to 115.003-T AC6 and required in the --json field table.

P2-1 `next_eligible_detail` REFERENCED BUT NEVER SPECIFIED — RESOLVED.
The backward-compatibility section named a third field with no shape. FIX: specified as {"candidate_ids": [...], "offending_ids": [...]} with BOTH keys ALWAYS present (empty lists when not applicable) so consumers need no key-existence checks; added a full field table. Propagated to 115.001-T AC4 and 115.002-T AC1. (Cycle-2 finding C2-P2-1 below tightens this further for the degraded path.)

P2-2 OPT-IN FLAG VS UNCONDITIONAL EMISSION LEFT OPEN — RESOLVED.
014-DL deferred this to the plan and the plan then also left it open, which would have pushed an interface decision down into implementation. FIX: decided explicitly — emit unconditionally, no new flag, no new subcommand; additive fields are already backward compatible and an opt-in flag would create two payload shapes to test and document for no benefit. Recorded in 115.002-T AC8.

=== CYCLE 2 FINDINGS — COPILOT PR #322 EXTERNAL REVIEW (5 raised: 2 P1, 3 P2 — all RESOLVED) ===

C2-P1-1 IMPOSSIBLE ANALYZER SIGNATURE — `degraded` WAS AN UNREACHABLE ANALYZER BRANCH — RESOLVED.
plan line ~53 and 115.001-T AC2/AC3/AC9 asserted the analyzer implements 7 branches, the first being DEGRADED. That branch is UNREACHABLE BY CONSTRUCTION. Verified read-only against src/autoharness/cli.py:936-955: `BacklogUnavailableError` is raised by `readers.list_shipments()`, i.e. BEFORE the `shipments` tuple exists; `compute_dag_readiness` is therefore never called and no `DagReadinessResult`/`ready_set` is ever produced on that path. Both of the analyzer's inputs (`shipments`, `readiness`) are absent exactly when degradation would be signalled, so `degraded` cannot be evaluated against a shipment enumeration or a readiness value. Shipping the plan as written would have produced dead, untestable analyzer code and an AC (AC9, 'cover every one of the 7 branches') that could not be satisfied honestly.
FIX — RESPONSIBILITY MADE EXPLICIT, SEPARATION PREFERRED OVER AN EXTRA INPUT: the analyzer now handles ONLY successfully-read data and implements EXACTLY SIX branches (gate outcomes 2-7: cycle_detected, ambiguous_provenance, multi_active_anomaly, resume_active, ready_set_head, no_candidates) and MUST NEVER emit `degraded`. Outcome 1 `degraded` is synthesized deterministically and EXCLUSIVELY by the CLI (115.002-T) inside the existing `BacklogUnavailableError` handler, BEFORE the analyzer is invoked. The alternative of adding an explicit `is_degraded` input to reach the branch was CONSIDERED AND REJECTED as less simple and self-contradictory (it would let a caller assert degradation while simultaneously passing successfully-read data). Every unreachable-analyzer-branch claim was removed. New hardening item H4b makes it a P0 defect to implement or emit `degraded` from the analyzer. Propagated to: plan Resolution-order section (with an explicit reachability proof), plan H4b, 115-F description + DoD#1/#5, 115.001-T title/AC2/AC3/AC9/new AC10/description, 115.002-T description + AC5/new AC9/AC10, 115.003-T AC3 + description.

FIX: the annotation now states the canonical FOUR-value enum, and an appended ENUM CORRECTION note records that a `blocked` value in a shipment status field is MALFORMED LEGACY DATA that MUST FAIL CLOSED to report/operator handoff and must never be normalized, coerced, or treated as a valid lifecycle state.
