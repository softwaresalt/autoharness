# Plan 2 un-defer decision packet: Gradio + Microsoft devtunnel remote control plane — 7 open questions

## Problem Frame

<!-- BEGIN:problem-frame -->
Operator un-deferred stash 04AFF97B and supplied final rulings for all seven design questions at 2026-08-13T20:51:55-07:00. The required outcome is one bounded Plan 2 V1 remote-control implementation plan for Observe + Steer over the local Copilot supervisor, grounded in the existing design doc and completed Plan 1 event/journal seams. The plan must preserve local authority and explicitly accept, rather than silently upgrade, the Q3 decision that devtunnel authentication alone is sufficient for V1.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
Per-question alternatives evaluated (from design doc §12, cross-referenced against §3-11 threat model/architecture):

Q1 (Gradio vs. minimal purpose-built page): (A) Keep Gradio — fast to stand up, Python-native, matches "Python-first, no new language" precedent from Plan 1; con: large surface (auto-generated components, websocket/queue internals, broad JS dependency tree) for a supposedly "fixed structured command vocabulary" (T6). (B) Minimal purpose-built control page (e.g. a small FastAPI/Starlette + hand-rolled static JS or server-rendered HTML) exposing only the closed command vocabulary — con: more code to write and secure ourselves; pro: attack surface scales with what we actually built, not a general-purpose ML-demo framework never designed for adversarial remote exposure. (C) Defer the UI-framework choice entirely to impl-plan/spike, deciding only the non-negotiable properties (loopback-only bind, closed vocabulary, no arbitrary Gradio components) now — avoids a premature framework lock-in before the auth/authorization/streaming decisions (Q2-Q6) are settled, since those decisions may constrain the practical framework choice anyway.

Q2 (minimum viable capability set): (A) Observe-only first release (status/phase/progress/redacted stream/journal tail per the Observe tier in §5) — smallest attack surface, delivers most of the "not tied to my desk" value (watching a long-horizon run) with zero remote mutation capability. (B) Observe + Steer (pause/resume/cancel/checkpoint) — adds real remote value (can intervene without being at the desk) but requires the full control-channel/idempotency/state-machine-authority machinery in §7 from day one. (C) Observe + Steer + class-restricted Approve — matches the design doc's full 4-tier model but is the largest first-release scope and touches the highest-risk approval-channel threat (T3).

Q3 (does devtunnel authenticated access control alone suffice, or is a second app-layer factor mandatory): (A) Tunnel-layer authentication only — simpler, but makes devtunnel's access-control configuration a single point of failure and violates the design doc's own T1/T2 principle that "the tunnel must never be the security boundary." (B) Tunnel authentication (Entra ID via devtunnel) PLUS independent application-layer identity verification (the design doc's stated default in §4) — defense in depth, but doubles the auth surface to build and test, and requires the app to validate identity assertions itself rather than trusting tunnel-arrival.

Q4 (approval-class taxonomy; which classes are permanently local-only): (A) Adopt §5's 4-tier table verbatim as the taxonomy (Observe/Steer/Approve/Privileged) with the Privileged tier — git push, PR create/merge, shipment claim, credential use, writes outside workspace — permanently local-only, never remotely approvable in v1. (B) Start narrower: only Observe + Steer exist in v1, deferring any remote Approve capability (and therefore the entire approval-class taxonomy question) to a later release — sidesteps T3 risk entirely for v1 at the cost of less operator value.

Q5 (retention/access policy for streamed session content): (A) No retention — stream is transient/in-memory only, nothing is persisted beyond the existing local session journal (119.005-T) which is not exposed remotely for storage purposes, only for live tailing. (B) Time-bounded remote-side retention (e.g. reconnect buffer only, purged on session end) to support the reconnect-from-journal-cursor behavior in §7. (C) No new retention decision needed — the local journal is already the single source of truth and remote clients are explicitly "stateless with respect to session truth" per §7, so this question may collapse to "confirm no separate remote-side store is created."

Q6 (browser terminal streaming — ever acceptable, and under what containment): (A) Permanently out of scope — the design doc already treats this as its "own later decision, gated on T6" and flags it as the path to "arbitrary remote shell"; keeping it excluded removes an entire threat class from v1. (B) Conditionally acceptable in a future release ONLY under a hard containment contract (no raw stdin passthrough without an explicit, separately-reviewed opt-in; audited; capability-scoped) — defers rather than permanently forecloses.

Q7 (corporate-network/tunnel-policy constraints in target environments): (A) Treat as an explicit non-goal/known-limitation for v1 — devtunnel may be blocked by corporate egress/proxy policy in some environments; document this as a deployment prerequisite rather than solving for it. (B) Require a documented fallback/detection story (e.g. preflight check that devtunnel connectivity works before enabling the feature, per §10's existing preflight requirement) so a blocked environment fails closed with a clear message rather than a confusing partial failure.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
AUTHORITATIVE OPERATOR RULINGS (2026-08-13T20:51:55-07:00)

Plan 2 proceeds as ONE combined V1 Observe + Steer implementation plan. It is not split into observe-only work. The following rulings are final and trace to stash 04AFF97B:

Q1 = C. Defer UI framework choice to an implementation spike. Set non-negotiables now: loopback-only bind, a closed structured command vocabulary, and no raw/general-purpose component exposure.
Q2 = B. V1 scope is Observe + Steer: status, phase, progress, redacted output stream, journal tail, plus pause/resume/cancel/request-checkpoint. Remote approvals are excluded from V1.
Q3 = A. Devtunnel authenticated access control alone is the V1 authentication mechanism. Additional application-layer verification is a future separate decision/follow-up, not a hidden V1 requirement. This is an accepted V1 risk and must be surfaced in hardening and review.
Q4 = A. Adopt the four-tier taxonomy Observe/Steer/Approve/Privileged. V1 exposes Observe and Steer only. Approve and Privileged are not remotely exposed; privileged actions remain local-only in V1. Future expansion is an explicit boundary, not V1 scope.
Q5 = C. No separate remote-side retention store. The local journal is the sole source of truth and remote clients are stateless.
Q6 = A. Browser terminal streaming is permanently out of scope for V1.
Q7 = A. Devtunnel-only for now. No separate corporate-network fallback or preflight requirement is added to V1. Availability/configuration is a prerequisite and known limitation; failure when unavailable must be clear.

SCOPE DECISION: implement one Plan 2 V1 Observe + Steer plan. Defer only Approve/Privileged implementation and future application-layer authentication enhancement. Do not silently expand scope.

Rationale: preserve local authority while delivering remote monitoring and bounded intervention. Loopback binding, closed structured commands, redaction, stateless clients, local-journal authority, local-only privileged authority, and explicit tunnel-unavailable failure are non-negotiable.

<!-- END:chosen-direction -->
