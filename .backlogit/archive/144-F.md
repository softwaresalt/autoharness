## Defect

The canonical gate `$env:PYTHONPATH='src'; python -m unittest discover -s tests` fails on Windows with exactly five failures and this verbatim stderr:

```
error: missing config value GIT_CONFIG_VALUE_2
fatal: unable to parse command-line config
```

Hosted Linux CI is green throughout.

## Root cause (mechanism A)

`unittest.mock.patch.dict('os.environ', ...)` restores by **clear-then-update** (`_unpatch_dict` -> `_clear_dict(in_dict)` then `in_dict.update(original)`), regardless of the `clear=` argument. For `os.environ` that is `unsetenv` for every key followed by `putenv` for every key. On Windows `putenv` of an empty value reaches `SetEnvironmentVariableW(name, L"")`, which **DELETES** the variable from the true Win32 process environment block instead of storing an empty value. CPython's `os.environ` keeps its own dict entry showing `''`, so the destruction is invisible from Python.

The ambient environment carries `GIT_CONFIG_COUNT=3` with `KEY_2=core.fsmonitor` / `VALUE_2=(empty)`. After any `patch.dict(os.environ, ...)` block exits, `VALUE_2` is gone from the real block while `COUNT=3` and `KEY_2` remain. Child git processes (`env=None` -> `lpEnvironment=NULL` -> inherit the real block) then fail at config-parse time.

This explains every prior puzzle: zero code references to `GIT_CONFIG_*` (nothing names them; a blanket clear/restore destroys them incidentally); failure only "partway through" a long process (needs one `patch.dict` block to exit first); fresh shell fine; Linux green (POSIX `setenv(name,"")` stores an empty value).

## Approach (deliberation option R9, accepted)

- **Layer 1 (root fix)** `tests/_env_patch.py::patched_environ` restores by targeted **diff** — never `os.environ.clear()`. Touches no `GIT_CONFIG_*` variable at all, so every legitimate injection (`safe.bareRepository=explicit`, `credential.interactive=never`) is preserved perfectly rather than approximately.
- **Layer 2** migrate all 13 bulk `os.environ` mutation sites under `tests/`.
- **Layer 3** AST structural regression guard (not a line regex, per `docs/compound/2026-08-21-ast-based-structural-regression-guards-beat-line-regex.md`).
- **Layer 4** `tests/_git_env.py::consistent_git_env` defense-in-depth normalizer, provable no-op when the triple is self-consistent (hence a no-op on Linux/CI).
- **Layer 5** assertion integrity: stop laundering git infrastructure failures into false domain diagnoses.

Rejected: accept-permanent-red (R1), clear all `GIT_CONFIG_*` (R2), `GIT_CONFIG_COUNT=0` (R3), mutate global/system git config (R4), skip/xfail the victims (R5), scrub in `ci.yml` (R6), fix only `src/` seams (R7), `tests/__init__.py` bootstrap (R8).
