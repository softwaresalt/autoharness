### Causal statement (corrected)

The intra-file order dependence `141.004-T` measured standalone
(`BranchOwnershipTests`, sorted before `FilesystemTopologyReadersTests` by
`unittest`'s `dir(module)`-based discovery order) is a direct, downstream
symptom of **mechanism A**, exactly as established in
`.backlogit/archive/144-F.md:45-61` and predicted in
`.backlogit/queue/145-F.md:50-54` — **not** a leak of the
`GITHUB_HEAD_REF`/`GITHUB_REF_NAME`/`GITHUB_REF_TYPE` overrides
themselves. All five polluters used the destructive
`unittest.mock.patch.dict('os.environ', {...}[, clear=False])` (+ manual
`_os.environ.pop(...)`) idiom, whose restore path is
clear-then-update (`_unpatch_dict` -> `_clear_dict` -> `in_dict.update`)
regardless of `clear=`. On Windows, restoring an **empty-valued** key via
`putenv`/`SetEnvironmentVariableW(name, "")` **deletes** it from the true
Win32 process environment block rather than storing `""`, even though
CPython's `os.environ` dict still shows the empty value. The ambient
ephemeral shell in this measurement environment carries
`GIT_CONFIG_COUNT=3` with `KEY_2=core.fsmonitor` / `VALUE_2=` (empty).
Because each of the five polluters' `patch.dict`/manual-`pop` block exits
*before* the victim runs (in-file class-then-method discovery order:
`BranchOwnershipTests` before `FilesystemTopologyReadersTests`), the
first such block's exit silently deletes the real
`GIT_CONFIG_VALUE_2` from the Win32 environment block while
`GIT_CONFIG_COUNT`/`KEY_2` remain. The victim's own git subprocess
invocation (`_run_git`, `src/autoharness/gates/topology.py:198-`)
inherits that now-inconsistent ambient environment (`env=None` ->
`lpEnvironment=NULL`), and `git`'s `GIT_CONFIG_COUNT`-driven parser fails
with `missing config value GIT_CONFIG_VALUE_2` / `fatal: unable to parse
command-line config`. `_run_git`'s designed `check=False` swallow (any
nonzero git exit collapses to `""`, per its own docstring) launders that
config-parse failure into an unresolved branch name, which the gate
reports as `detached_head` -> `BRANCH_MISMATCH` -> `result.exit_code == 1`
— exactly the assertion that fails above, and exactly why this order
dependence looked like an unrelated "mechanism B" until measured against
mechanism A's fix. `144.003-T`'s migration of these same five sites to
`patched_environ`'s restore-by-diff semantics (152-S/144-F) restores only
the keys that changed, in the byte-exact diff needed, so it never touches
`GIT_CONFIG_VALUE_2` and eliminates the destructive Win32-empty-value
deletion by construction. The reverted-checkout negative control (above)
directly confirms this causal link: reverting *only* the migration for
these five methods reproduces the exact original `GIT_CONFIG_VALUE_2`
-> config-parse-failure -> `BRANCH_MISMATCH` chain, and restoring it
removes the failure again.
