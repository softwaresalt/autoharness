SIZE: M. COMPLEXITY: medium. (Two independent axes; also emitted as structured backlog fields.) Shipment 3 (P1). Create src/autoharness/supervise/approvals.py: a structured LOCAL command and approval channel IMPLEMENTING the approval request/response contract defined upstream in the shared supervisor core (118.003-T contracts.py). F32/F33 RULING - RUNTIME WIRING (CORRECTS THE EARLIER F21 DISPOSITION): the previous text claimed that placing the contract in the core meant the approval path 'cannot be silently omitted'. THAT CLAIM WAS FALSE and is withdrawn. Contract placement fixed F19 (definition ordering) only; F21 was a RUNTIME WIRING defect, and at the time of that claim this task still had ZERO reverse dependencies while 120.004-T - the single orchestrator - did not reference approvals at all, so the H2 fail-closed guarantee remained fully omissible from the shipped runtime. THE FIX IS THE DEPENDENCY DIRECTION: the 120.005-T -> 120.004-T edge is REMOVED and REPLACED by 120.004-T -> 120.005-T. This task is now UPSTREAM of the orchestrator and on the critical path: the runtime chain T15 -> T17 -> T18 -> T19 can no longer be satisfied with this task unstarted, which was the precise structural property F21 identified as missing. This module MUST therefore expose the approval service as a constructible, injectable object (no import-time singleton, no global mutable default) so 120.004-T can require it as a parameter with no default and so the recording/spy and raising fixtures its acceptance criteria mandate can be substituted in tests. The supervisor emits ApprovalRequested carrying a typed request (kind, summary, options, default, timeout), renders it on the LOCAL CONSOLE, blocks for the operator's answer, and journals both request and response. Structured local commands (status, pause, resume, cancel) are handled over the same console channel. HARD CONSTRAINTS: console/TTY only - NO socket, NO port, NO HTTP, NO tunnel, NO remote identity, NO delegated approver, NO Gradio, NO devtunnel. Any remote approval path is DEFERRED to Plan 2 and is an explicit non-goal here. FAIL CLOSED (H2): in a non-interactive session an approval request resolves ACCORDING TO THE CATALOG ENTRY'S TAGGED FALLBACK POLICY, which 118.003-T defines as a two-variant union (ruling C, 2026-08-12): USE_SAFE_DEFAULT(reference/value) resolves to that named option, and REFUSE resolves to REFUSED. EVERY ENTRY DECLARES EXACTLY ONE VARIANT, and where no safe default exists REFUSE is the required fail-closed outcome - NO PLACEHOLDER OR BOGUS DEFAULT IS EVER INVENTED TO SATISFY A METADATA REQUIREMENT. Either way the resolution is journaled as auto-resolved, and it NEVER silently auto-approves. Tests cover BOTH FALLBACK VARIANTS EXPLICITLY - a USE_SAFE_DEFAULT entry resolving non-interactively to its declared option, and a REFUSE entry resolving to REFUSED - plus interactive approve/deny, timeout, and the no-safe-default -> REFUSED, and an assertion that the module opens no socket.
