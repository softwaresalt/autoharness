THREE CONSUMPTION SITES, EACH BOUND TO EXACTLY ONE INVOCATION LABEL:
1. Orchestrator step 2a — route-to-Ship eligibility check -> `orchestrator_pre_route`.
2. Ship step 3, first `pre_claim` run — before branch/worktree creation -> `ship_pre_branch`.

CONTRACT TEXT AT EACH SITE (uniform):
- Before invoking the gate, check for `.autoharness/bootstrap-grants/{shipment_id}.yaml`. NO GRANT FILE -> invoke exactly as today, with no added flag, and the existing exit-1 halt stands UNCHANGED. This is the default path and must remain the overwhelmingly common one.
- A GRANT FILE EXISTS -> invoke with `--bootstrap-grant-invocation {label}` for THIS site's label only. The CLI performs all matching (165.011-T Deliverable 2); the agent MUST NOT pre-judge applicability, MUST NOT retry with a different label, and MUST NOT substitute `--force`.
- Exit 0 with `forced: false` -> ordinary native pass; proceed.
- Exit 0 with `forced: true` -> the grant matched and was consumed. Log `BOOTSTRAP_GRANT_CONSUMED: {shipment_id} {label} token={token} predecessor={predecessor} head={sha}`, surface the audit-log path to the operator, and proceed.
- Exit 1 or 2 -> HALT exactly as today. A present-but-non-matching grant changes NOTHING about the halt. Grant absence and grant mismatch are indistinguishable in their effect on the agent.

EXPLICIT PROHIBITIONS, STATED IN THE AGENT TEXT:
- NO agent may author, edit, extend, re-date, or create a bootstrap grant. Grants are operator-authored and review-gated; an agent that writes its own grant has self-authorized a force (P-005/P-001 violation). State this as a NON-NEGOTIABLE rule alongside the existing "Ship must not self-declare `dag-root`" rule that 165.008-T introduces.
- The Orchestrator's CURSOR-ADVANCE `pre_claim` check evaluates a DIFFERENT shipment (`{next_shipment_id}`) and is NOT a grant consumption site. It never passes `--bootstrap-grant-invocation`.
- The post-claim `CLAIM_NOT_OBSERVED` reclaim path's `pre_claim` re-run is NOT a consumption site. It runs unforced and ungranted; if it blocks, Ship halts to the operator. A grant exists to REACH a claim and is exhausted by it.
- `post_claim`, `lifecycle`, and `ambient` phases are never grant sites.

BRANCH-VANTAGE NOTE (empirically verified during PR review-fix cycle 1): `pre_claim` runs the `branch_ownership` check ahead of `shipment_readiness`, and it short-circuits — a run from a non-shipment, non-default branch returns a SOLE blocking check of `BRANCH_MISMATCH`, never `PREDECESSOR_NOT_SHIPPED`. Because a grant is bound to an exact expected token, a grant written for `PREDECESSOR_NOT_SHIPPED` CANNOT match from a wrong-branch vantage. State in the agent text that grant consumption sites are only reached from a contract-valid vantage (default branch for `orchestrator_pre_route`/`ship_pre_branch`; the shipment branch for `ship_pre_claim`), and that a `BRANCH_MISMATCH` block is never grant-eligible.
