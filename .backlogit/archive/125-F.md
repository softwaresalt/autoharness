Implementation plan (scoped to target workspaces only): extend Auto-Tune's deterministic drift model so start.ps1 and start.sh are evaluated against the current startup-script contract, not only the installed workspace's historical checksum. The implementation should define a named contract/version tied to the canonical templates, retain compatibility handling for manifests that predate that metadata, and classify each script as missing, current, known-legacy pre-shim, user-modified/customized, or ambiguous/unknown. Structural markers must distinguish the current autoharness run delegation from duplicated bootstrap, sidecar-preflight, CLI-resolution, and lifecycle-supervision logic. A legacy file that is unchanged relative to its old manifest must still produce a migration proposal.

The migration path must follow Tune's non-destructive rules: generate a missing script from the current template; for a known stale script, back up the original under the target workspace's dated autoharness backup area before refreshing; update manifest contract/checksum metadata only after the accepted refresh; preserve supported operator-added Claude Code/Codex/custom sections through deterministic extraction and reattachment; and fail closed to an operator review proposal when content cannot be safely classified or preserved. The plan must wire the drift result into tuning reports and verification, and must define exact PowerShell/POSIX markers, backward-compatible version defaults, backup paths, and proposal evidence.

Likely implementation surfaces are .github/skills/tune-harness/SKILL.md plus the verifier/contract-support path in src/autoharness and targeted tests. Include .github/skills/install-harness/SKILL.md or templates/scripts/start.ps1.tmpl/start.sh.tmpl only if implementation evidence shows shared contract metadata or generation behavior is missing; current templates and repository-root start scripts are already the reference and are explicitly out of scope. Do not resurrect Plan 3 remote UI work.

Plan Hardening conclusion: Requires plan hardening: yes. Reason: this is a contract-versioned migration that can rewrite installed target files and must preserve operator customizations; incorrect classification has cross-workspace impact even though the primary changes are skill/template and verifier guidance.
