## Findings

**F1. SURFACE INVENTORY — the CLI is the ONLY real surface.** pyproject.toml declares exactly one entry point (`[project.scripts] autoharness = "autoharness.cli:main"`). Dependencies are only jsonschema and PyYAML: there is NO MCP SDK and NO web/API framework. COUNTING CONVENTION (used consistently throughout this artifact): a TOP-LEVEL COMMAND is a token dispatched directly by `main()`; an EXECUTABLE LEAF COMMAND PATH is a fully-specified invocation that runs work, obtained by expanding the grouped dispatchers. `main()` (cli.py:2253) exposes 10 TOP-LEVEL COMMANDS: home, version, verify-workspace, gate, telemetry, eval, setup-vscode, setup-copilot-cli, setup-claude, setup-codex. Expanding the three grouped dispatchers — gate {check,size,copilot-review,pipeline-topology,dag-readiness} (5), telemetry {begin,record,event} (3), and eval {review,run} (2) — yields 17 EXECUTABLE LEAF COMMAND PATHS (7 ungrouped leaves + 5 + 3 + 2). Argument parsing is hand-rolled per subcommand (no argparse), so the argument contract exists only as prose inside the USAGE/GATE_USAGE/TELEMETRY_USAGE strings.

**F2. MCP SURFACE IS ABSENT (not partial).** A repo-wide scan of src/ for FastMCP, mcp.server, stdio_server, `@mcp.`, or `Server(` returns ZERO hits. The SUPPORTED CONCLUSION is precisely this: NO NATIVE MCP SERVER IMPLEMENTATION OR FRAMEWORK IDENTIFIERS EXIST IN src/ — there is no MCP SDK dependency and no server entry point. That is a claim about SERVER-FRAMEWORK ABSENCE, and it must NOT be overstated into a claim that no `mcp` token appears in src/ at all. The `mcp` tokens that DO exist in src/ fall into two NON-SERVER vocabularies: (i) BACKLOG-REGISTRY VALIDATION vocabulary — 31 occurrences in verify_workspace.py, including the operation constants at verify_workspace.py:140-159 (OP_CREATE_MCP, OP_LIST_MCP, ... OP_RESOLVE_CHECKPOINT_MCP), by which autoharness VALIDATES that a workspace's backlog-registry.yaml declares MCP tool mappings for an EXTERNAL tool; and (ii) TELEMETRY VOCABULARY — 1 occurrence at tool_event.py:35, where `TOOL_SURFACES = frozenset({"mcp","cli","shell","builtin","api","unknown"})` enumerates the ALLOWED VALUES of the `tool_surface` field. Neither vocabulary implements, hosts, or exposes an MCP server. autoharness CONSUMES external MCP servers (backlogit/Engram/graphtor) through the agent runtime and VALIDATES their registry wiring, but EXPOSES nothing of its own over MCP. Notably, the telemetry vocabulary in (ii) already models the multi-surface world autoharness does not yet have, since its own single emission site hardcodes `tool_surface='cli'` (cli.py:789).

**F3. THE PYTHON LIBRARY SURFACE IS NOMINAL, NOT CONTRACTUAL.** Real importable core functions exist (verify_workspace.verify_workspace; gates.gate.check; gates.feedback.enforce; gates.sizing.size_task; gates.topology.evaluate / compute_dag_readiness / compute_next_eligible; telemetry.*). But scanning scripts/ and templates/ for `from autoharness` or `import autoharness` returns ZERO hits — the ONLY consumers are src/autoharness/cli.py and tests/. autoharness/__init__.py is 7 lines with no `__all__` and no declared public API. There is no second consumer proving the core is surface-sufficient.

**F4. THE DE-FACTO SECOND SURFACE IS STRINGLY-TYPED SHELL PROSE.** Agent templates, skills, and instructions invoke autoharness by shelling out with `--json` — for example `autoharness gate pipeline-topology --mode agent --shipment {shipment_id} --phase pre_claim --json`, `autoharness gate copilot-review <pr> --repo <owner/name> --enforcement <mode>`, `autoharness telemetry begin|record|event ...`, and `autoharness verify-workspace --workspace {workspace_path}`. The agent contract is therefore argv strings plus exit codes plus ad-hoc JSON, with no schema binding the prose to the code.

**F5. CALL-PATH MAP (surface to core).** Items marked (*) are POLICY LEAKED INTO THE ADAPTER.

**F6. INSTALL/TUNE ORCHESTRATION IS PROSE-ONLY, AND IS THE LARGEST GENUINE DUPLICATION.** There is NO Python implementation of install or tune: .github/skills/install-harness and .github/skills/tune-harness are LLM-followed SKILL.md workflows, and install-harness carries an explicit variable-resolution TABLE ({{PROJECT_NAME}}, {{SUFFIX_*}}, {{DOCS_*}}, {{PRIMARY_LANGUAGE}}, {{BUILD_COMMAND}}, {{CAPABILITY_PACKS_YAML}}, and more). Yet verify_workspace.py independently RE-IMPLEMENTS the same rules in Python in order to check the result: `_render_template` (:1142), `_derive_template_variables` (:2193, including PROJECT_NAME/DATE/CAPABILITY_PACKS/PREFIX_* defaults), `_language_defaults` (:2148), `_resolve_source_template` (:1974), `_scan_uninstalled_templates` (:2001). Two independent authorities for one rule set, with NO mechanism forcing them to agree — drift is silent by construction. This is a REAL duplication of business logic, and it is prose-versus-code rather than surface-versus-surface.

**F7. RESULT AND ERROR SHAPES DIVERGE.** verify-workspace returns an untyped `dict[str, Any]` whose failure semantics are adapter-derived. Gates return frozen dataclasses with `.to_dict()` (GateResult, CheckResult, TopologyResult, DagReadinessResult, NextEligibleResult, and the sizing result) — good, but each has a bespoke shape with NO shared envelope (no common status / exit_code / messages / artifacts contract), and the dag-readiness payload emitted to callers is core `to_dict()` PLUS adapter-injected keys. Error handling mixes ValueError-to-`sys.exit(2)` in each hand-rolled parser, typed GatesConfigError and BacklogUnavailableError, and a blanket `except Exception` fail-open in telemetry emission. Exit codes 0/1/2/3 carry DIFFERENT meanings per subcommand and are specified ONLY in the CLI USAGE prose — there is no machine-readable exit-code contract a second adapter could honor.

**F8. GOOD NEWS — THE CORE IS ALREADY DEPENDENCY-INJECTED AND TESTABLE.** topology.py defines a `TopologyReaders` Protocol with FilesystemTopologyReaders and _NullReaders; `runner.run_gate` accepts `run_fn`; `sizing.size_task` accepts `fetch_fn`. The gate and telemetry cores are genuinely surface-independent and heavily covered (test_gates_topology.py 1814 lines, test_gates_dag_readiness.py 566, test_verify_workspace.py 6306). The missing piece is NOT testability — it is that policy, observability, and degraded-mode synthesis sit ABOVE the core, in the adapter.

**F9. PRODUCT VERSUS EXTERNAL BOUNDARY.** autoharness product = src/autoharness/**, templates/**, schemas/**, .github/{agents,skills,instructions}/**, docs/**, and plugin.json (marketplace packaging of agents/skills only — no code surface). EXTERNAL, OUT OF SCOPE, READ-ONLY: backlogit (Go binary with its own MCP and CLI, C:\Source\GitHub\backlogit), Engram (memory sidecar, .mcp.json), and graphtor (Rust, build.rs, docs MCP). autoharness consumes these through registry-declared MCP tools with CLI fallbacks and must neither vendor nor reimplement them. Per operator decision, Engram is a READ-ONLY workspace-memory sidecar with NO execution or mutation authority; autoharness may consult it to improve performance and outcomes only.

**F10. CLASSIFICATION = PARTIAL GAP.** A single-source-of-truth architecture EXISTS for the computational core of gates and telemetry (typed, injected, tested) but is INCOMPLETE at the seam: policy, verdict mutation, audit-log authorship, telemetry classification, degraded synthesis, and config loading live in the CLI adapter (F5); one whole capability family (setup-*) has no core at all (F5); the install-versus-verify variable-derivation rules are genuinely duplicated across prose and Python (F6); there is no shared result envelope or error/exit-code taxonomy (F7); and there is no declared public API or second consumer to prove sufficiency (F3). It is neither ALREADY SATISFIED nor ABSENT.

**F11. SPEC SECTION 3 AS LITERALLY WRITTEN IS MOSTLY NOT AUTOHARNESS'S JOB.** docs/product-specs/autoHarness-framework-specifications.md section 3 asks for a unified tool-execution abstraction treating CLI commands and MCP requests as equivalent ACTIONS in an Action/Observation loop, sequential pipelining, and stderr routed back to the active model. That describes an AGENT RUNTIME (Copilot CLI / Claude Code), which already owns the action/observation loop, tool dispatch, and stderr surfacing. autoharness is a harness-COMPOSITION tool that emits prose and config artifacts plus deterministic gates; building a runtime executor inside it would be a large speculative framework with no consumer. The DEFENSIBLE, evidence-backed residue of section 3 is the INTERNAL one: make autoharness's OWN functionality a single source of truth behind thin adapters. Per operator decision, product-spec model names are illustrative and non-authoritative, and .autoharness/config.yaml remains the model-routing authority — no work should hardcode spec model names.

**F12. DOES (c) DEPEND ON (a)? NO — (c) BENEFITS FROM (a) but is not blocked by it.** Candidate (c) (background Verification and Compaction: log parsing, history summarization, state pruning) already has BOTH substrates: Python-side log/telemetry parsing (telemetry/reader.py, aggregation.py, tool_event_compose.py, _jsonl_segments.py, gaps.py) and prose-side compaction (P-020 post-merge compaction, context-efficiency instructions, and prune-on-restore already shipped via 002-SP / 111-F). (c) could therefore be scoped independently today. The dividend of doing (a) first is structural: if (a) establishes the shared application-service seam and result envelope, (c)'s new log-parsing and summarization entry points land in the core layer by default instead of accreting in cli.py — which is precisely how cli.py reached 2,289 lines. RECOMMENDATION: keep the operator's (a)-then-(c) sequence, but do NOT declare a blocking dependency, so (c) can be re-scoped independently if (a) is deferred or descoped.

## Recommendation

**CLASSIFICATION: PARTIAL GAP. VERDICT: CONDITIONAL PROCEED (confidence medium-high).** Confidence is medium-high because F1-F10 are direct file-and-line observations, but the CONDITION is material: PROCEED only if (a) is scoped as a CONSOLIDATION of logic that already exists, and NOT as building an MCP server or an action/observation execution engine. If the operator wants section 3 literally (runtime executor, pipelining, stderr-to-model routing), the answer is NO-GO — that is agent-runtime territory (F11), unbounded, and has no consumer in this repo.

**MINIMAL TARGET ARCHITECTURE (only what evidence warrants).** (1) One thin application/service function per capability, owning ALL policy currently stranded in cli.py — config loading, pass/fail definition, exit-code semantics, force-override and audit-log writing, telemetry emission, and degraded-mode synthesis. (2) ONE shared typed result envelope (status, exit_code, data, messages, warnings, artifacts) with `.to_dict()`, WRAPPING rather than rewriting existing results, including the 4,453-line verify_workspace dict. (3) ONE error taxonomy (a single AutoharnessError base carrying a machine-readable `kind`) replacing the per-parser ValueError-to-`sys.exit(2)` pattern, plus a machine-readable exit-code contract. (4) cli.py reduced to: parse argv, call the app function, render human or JSON, `sys.exit(result.exit_code)` — with NO policy. (5) A declared public API (`__all__` plus docs) once the seam exists. DO NOT build an MCP server or HTTP API now; the deliverable of (a) is that one COULD be added without touching policy. If proof-of-sufficiency is wanted, add an in-process JSON dispatch used only by tests — not a real server.

**AUTHORITY / ERROR / OBSERVABILITY CONTRACTS.** Adapters MAY translate transport (argv, JSON, stdio) and MAY render output, but MUST NOT own policy or business decisions — no verdict mutation (today's `dataclasses.replace` force path), no audit-log authorship, no telemetry classification, and no synthesis of outcomes the core cannot produce. Every observable outcome must be reachable from the core, closing the CLI-exclusive `degraded` outcome. Telemetry must be emitted by the core with `tool_surface` supplied BY the adapter, so the already-existing TOOL_SURFACES enum stops being aspirational. Engram remains READ-ONLY with NO execution or mutation authority. .autoharness/config.yaml remains the authority for dynamic model routing, and no spec model names are to be hardcoded.

**EXPLICIT NON-GOALS.** (i) No autoharness-owned MCP server in (a). (ii) No action/observation execution loop, sequential-pipelining engine, or stderr-to-model routing — agent-runtime responsibility. (iii) No generic plugin/registry framework or abstract Tool base class built for symmetry. (iv) No change to backlogit, Engram, or graphtor. (v) No hardcoded model names. (vi) No rewrite of the install/tune prose skills into Python — only DECLARE one authority for the duplicated variable-derivation rules. (vii) No parallel execution, scheduler, or extra worktree (P-001/P-016 preserved).

**RISKS.** R1 behavior drift — cli.py's exit codes are load-bearing for agent prose and are characterized by CLI-level tests (test_gate_pipeline_topology_cli.py, test_telemetry_record_cli.py, test_telemetry_event_cli.py); mitigate by keeping those tests UNCHANGED as the characterization suite and moving logic beneath them. R2 scope creep into a runtime or MCP build, actively invited by spec section 3; mitigate with the non-goals above plus plan-harden (elevated blast radius: CLI distribution plus multiple template families). R3 verify_workspace.py is 4,453 lines returning an untyped dict; mitigate by WRAPPING in the envelope, never rewriting. R4 the install-versus-verify dedup spans a prose skill AND Python simultaneously, a width-isolation hazard; mitigate by making it a DECLARE-THE-AUTHORITY documentation task first, not a code move. R5 zero external library consumers means no forcing function and the refactor could be pure churn; mitigate by keeping the operator's (a)-then-(c) sequence so (c) becomes the seam's first real consumer.
