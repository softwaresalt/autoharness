## Description

<!-- BEGIN:description -->
Surface metric-quality provenance (estimated vs observed) in eval-summary derived ratios instead of treating all denominators as equally trustworthy (source: stash D194A24B, 3EFC51DE).

Files (4): src/autoharness/telemetry/aggregation.py, src/autoharness/eval/summary.py, tests/test_eval_summary.py, tests/test_telemetry_aggregation.py

Current state (two coupled defects): eval/summary.py has no general mechanism surfacing whether an economics metric was estimated vs observed in its output -- only one special-case exists for context_area_tokens (summary.py:161). gap_rate (summary.py:143: float | str = UNAVAILABLE if expected == 0 else missing / expected) ignores metric_quality entirely, and _derived_ratio (aggregation.py:118-121) is likewise not quality-aware -- it only guards against None values / zero denominators, not against a denominator whose provenance is "estimated".

TDD (red->green): add two tests to test_eval_summary.py (both fail first). (1) test_gap_rate_flags_estimated_denominator_provenance: a metric history where the denominator's quality is "estimated" (not "observed") asserts the summary output surfaces a provenance marker (quality field alongside gap_rate) distinguishing it from a genuinely observed ratio. (2) test_gap_rate_unavailable_when_numerator_unavailable: 3EFC51DE's concrete case -- a usable denominator (expected_tool_count=1) with an "unavailable" numerator (missing_expected_tool_count=0 marked unavailable) must surface "unavailable" provenance, NOT a bare 0.0. Then: extend _derived_ratio in aggregation.py to accept/propagate a quality indicator for BOTH its numerator and denominator operands (a denominator-only design still returns 0.0 for the unavailable-numerator case and does not fix 3EFC51DE), and update summary.py's gap_rate computation (and any other _derived_ratio consumers sharing the same gap) to surface that provenance in the returned summary structure, generalizing the existing context_area_tokens special-case rather than duplicating it. Because _derived_ratio is shared by every derived metric, also add operand-quality regression cases to tests/test_telemetry_aggregation.py (which owns the derived_efficiency_metrics contract at lines 182-224) for the OTHER _derived_ratio consumers -- consumption_generation_ratio and cost_per_successful_epoch (aggregation.py:140,142) -- asserting an unavailable/estimated numerator or denominator degrades those ratios' provenance too and does not silently change their shape -- so the broadened API is covered where it is actually consumed, not only via gap_rate in test_eval_summary.py. (net_offload_tokens at aggregation.py:136-139 is a direct subtraction, not a _derived_ratio consumer, and already returns UNAVAILABLE when either operand is None; it is out of scope for this _derived_ratio broadening.)
<!-- END:description -->

## Acceptance Criteria

<!-- BEGIN:acceptance-criteria -->
- eval-summary output for gap_rate (and other _derived_ratio-based metrics) includes a provenance/quality indicator derived from BOTH numerator and denominator operands.
- An unavailable (or estimated) numerator degrades the ratio provenance (e.g. expected=1 with an unavailable missing-count numerator surfaces "unavailable", not a bare 0.0).
- Existing context_area_tokens special-case behavior is preserved or generalized into the same mechanism (no regression).
- Ratios with fully-observed numerator and denominator are unaffected (no provenance noise added for the common case where nothing is estimated).
- The broadened _derived_ratio is covered in tests/test_telemetry_aggregation.py (derived_efficiency_metrics contract) with unavailable/estimated operand cases for its consumers consumption_generation_ratio and cost_per_successful_epoch (net_offload_tokens is a direct subtraction, not a ratio -- out of scope); no unrelated derived metric silently changes shape or provenance.
<!-- END:acceptance-criteria -->
