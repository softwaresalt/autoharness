Document the new gate contract and the migration procedure for workspaces that relied on unstated numeric sequencing.

DELIVERABLES:
1. Gate documentation in `docs/` describing: explicit-DAG predecessor derivation; the four derivation states and their `predecessor_source` values (`explicit`, `declared_root`, `genesis`, `unsequenced`); the UNSEQUENCED_SHIPMENT token; and the root-declaration surface (the `dag-root` label on a shipment record) including WHO may apply it — operator/Stage only, never Ship self-declaring to unblock its own claim. NARROWED CLAIM (review-fix cycle 3, finding 6): document this at its true strength. `dag-root` is a VERSION-CONTROLLED, REVIEW-GATED DECLARATION in backlog data inside the repository trust boundary; it is AUDITABLE — visible in a diff, attributable to a commit — but it is NOT mechanically permission-enforced and NOT a security boundary. Do NOT write that self-declaration is impossible, technically prevented, or that there is "no escape hatch". The documentation must not promise an enforcement guarantee the implementation does not provide.
2. GENESIS IS THE SOLE-RECORD RULE — DOCUMENT IT PRECISELY (PR review-fix cycle 2, thread PRRT_kwDORzpWpM6h3frF; REPLACES the cycle-2 three-probe wording). State the full rule: genesis requires no edges, no `dag-root`, and the candidate being the ONLY shipment record in the workspace — live and archived counted TOGETHER, REGARDLESS OF STATUS AND PROVENANCE. State that ANY other shipment record disqualifies genesis, explicitly naming `queued`, `active`, `shipped`, and `abandoned` — the CURRENT four-value shipment status vocabulary — and that a record whose status is missing, empty, non-string, or unrecognized (including an unrecognized `archived_status`) ALSO disqualifies, FAIL-CLOSED, rather than being skipped. DOCUMENT `blocked` HONESTLY (PR review-fix cycle 3, thread PRRT_kwDORzpWpM6h3ttS): `blocked` is NOT a shipment status — it is MALFORMED LEGACY DATA, writable historically because `backlogit move` accepted unvalidated status writes and still advertised only because the `header-def` metadata catalog's shipment `status` enum is stale at five values. Document the two dispositions separately: a LIVE shipment record carrying `status: blocked` makes the gate FAIL CLOSED at read time (BacklogUnavailableError, "missing or unsupported status") and derives no state at all; an ARCHIVED record carrying `archived_status: blocked` counts as a disqualifying unclassifiable record, so the candidate resolves to `unsequenced`. Cross-reference docs/compound/2026-05-07-backlogit-shipment-status-constraints.md. Do NOT write `blocked` into the documented status list. State plainly WHY absence of shipped history alone is insufficient: in a workspace with several queued shipments and nothing yet shipped, a "no shipped history" rule would return genesis for EVERY one of them at once, including later-numbered candidates downstream of other pending work — an unearned pass in exactly the fail-open direction this change exists to close. State ALSO why the rule counts records instead of enumerating statuses: the retired three-probe form admitted every value outside its three enumerations, and any future status added to the vocabulary would have re-opened the same hole. State the practical consequence for operators: a fresh install's FIRST shipment passes as `genesis` and cannot deadlock, but the SECOND shipment onward must either declare a real `blocks` edge or carry `dag-root`.
3. MIGRATION GUIDE built around the `audit_sequencing` phase (165.003-T): run the audit — a READ-ONLY REPORT that performs no backlog mutation and no migration-state/ledger write (NOT "persists nothing": the ordinary, observational, fail-open `pipeline-topology` telemetry emission happens on every phase, per PR review-fix cycle 1, thread PRRT_kwDORzpWpM6h3Tgi) — review every edge-less shipment it lists, then for each one either record the real `blocks` edge or declare it a root, and COMMIT that change. State plainly that in a workspace disqualified from genesis an un-audited edge-less shipment BLOCKS as `unsequenced` — the intended fail-closed posture — and that the block names both remedies.
4. Document the REMOVED behaviour (numeric adjacency) and why it was retired, citing the three prior defect cycles in docs/compound/ and the directional-numeric root cause they share.
5. Explain that NO configuration key exists for this contract (decision D2): the posture is per-shipment declared intent in backlog data, so there is nothing to configure, no schema version to track, and nothing for install/tune to preserve.
6. ROLLBACK POSTURE — CORRECTED AND ORDERED (review-fix cycle 2, P2 finding 11, as REVISED by review-fix cycle 3, finding 13; this supersedes both the cycle-1 "a code revert suffices" claim and the cycle-2 ledger-based claim). A code-only rollback DOES NOT restore the pre-migration workspace. Migration mutates BACKLOG DATA: `blocks` edges added and `dag-root` labels applied during the audit persist after the engine is reverted, and the reverted numeric engine will then interpret those edges as real explicit predecessors — potentially blocking claims that the pre-migration engine allowed. Document:
   a. WHAT IS AND IS NOT REVERSIBLE BY CODE ALONE: the derivation logic, the `predecessor_source` output field (additive, safe for older consumers to ignore), the `audit_sequencing` phase, and the UNSEQUENCED_SHIPMENT token are all code-reversible with no orphaned configuration, because no configuration was introduced. Migrated edges and root labels are NOT.
   b. THE MIGRATION RECORD IS THE VERSION-CONTROLLED OPERATOR COMMIT. The gate writes NO MIGRATION STATE and owns no ledger, no durable audit artifact, and no persistence subsystem — 165.003-T's audit is a read-only report that mutates no backlog record. Do NOT write that "the gate persists nothing" or that "it owns no write path at all" (PR review-fix cycle 1, thread PRRT_kwDORzpWpM6h3Tgi): `pipeline-topology` emits an ordinary, observational, fail-open telemetry event on EVERY run of EVERY phase, and a `--force` run additionally appends to its force audit log; neither is a migration record and neither may be read back as state. The recoverable pre-migration state lives where every other reviewable change in this repository lives: in the COMMITS AND DIFFS that added the edges and `dag-root` labels. A `git` diff of the migration commit shows each shipment's before and after edge set and label set exactly, which is what makes data rollback precise rather than guessed. This is strictly stronger evidence than a gate-written ledger would have been — reviewable, attributable, and already protected by the repository's own history.
   c. ORDERING IS MANDATORY: revert BACKLOG DATA FIRST by reverting the migration commit(s) (removing the edges and `dag-root` labels the migration added, restoring the committed pre-migration state), THEN revert the ENGINE. Reverting code first leaves migrated data being interpreted by the restored numeric engine — a state that existed in neither the before nor the after configuration, and the most likely source of a confusing mid-rollback block.
   d. If a workspace's migration was NEVER COMMITTED — edges and labels applied by hand in a dirty working tree, or applied outside version control — say so plainly: there is no diff to revert, data rollback for that workspace is manual and must be reconstructed from backlog record history, and the rollback claim is correspondingly NARROWED. It is not automatic. State the preventive rule directly: COMMIT THE MIGRATION as its own reviewable change, and rollback stays mechanical.

State explicitly that the grant mechanism is FUTURE-FACING product behaviour for later self-hosted migrations and did NOT and COULD NOT authorize 173-S's own claim, which was entered by the one-time operator-run BOOTSTRAP-A path recorded on the 173-S shipment record. Document the full-provenance force audit fields added by 165.011-T, and state that the `--force` flag remains operator-only with unchanged semantics.

8b. DOCUMENT THE AT-MOST-ONCE CONSUMPTION MECHANISM AND ITS HONEST SCOPE BOUND (ADDED in PR review-fix cycle 2, thread PRRT_kwDORzpWpM6h3fqf; 165.011-T Deliverable 6). Explain that at-most-once is enforced by a DURABLE EXCLUSIVE-CREATE CONSUMPTION RECORD under the gitignored `.autoharness/gates/bootstrap-grant-consumption/`, claimed atomically BEFORE the force conversion, with the audit emitted from that claimed record. Document, in operator-facing terms: that a second attempt on the same label fails closed with the ordinary exit 1 and is never retried, waited on, or stolen; that there is NO TTL and NO auto-expiry; that editing the grant does NOT reset consumption, because the record binds the grant's digest; that a malformed or stale record is treated as CONSUMED (fail-closed), which is the deliberate opposite of a malformed GRANT being treated as NO GRANT, both resolving toward NO FORCE; and that recovery from a crashed claim is an OPERATOR-ONLY out-of-band act — the CLI deliberately offers no reset flag, because such a flag would let an agent re-open an exhausted grant. STATE THE SCOPE BOUND HONESTLY RATHER THAN IMPLYING A STRONGER GUARANTEE: at-most-once holds PER WORKSPACE CLONE, because the record tree is gitignored; a fresh clone starts with no consumption state. Document the compensating bounds that make this acceptable (`expires_on_claim`, the exact-token binding that stops matching once the shipment leaves `queued`, and the manifest-digest binding that drifts as the shipment progresses), and state plainly that a cross-machine guarantee is NOT provided and was deliberately not invented.
