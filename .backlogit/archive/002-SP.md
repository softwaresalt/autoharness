## Findings

There is today NO defined on-restart / crash-resumption protocol: detect an ACTIVE (unresolved) checkpoint at session start -> classify as an interrupted session -> restore the recorded state_dump -> prune stale/superseded context on restore (bounded window; drop superseded action-observation history) -> resume from the recorded single-active cursor, or hand to the operator when ambiguous. This is expressible ENTIRELY as product-template prose (orchestrator agent template + a supporting checkpoint-recovery instruction) driving the EXISTING backlogit checkpoint API + engram, with degraded fallback when backlogit/engram are unreachable (mirror the existing Tool-Availability-Gate + ENGRAM_DEGRADED patterns).

4. OUT-OF-BOUNDARY / stays DEFERRED: any change requiring NEW backlogit checkpoint schema fields, engram-internal changes, or a runtime execution engine (candidate (a)/(c) territory). If the prose protocol needs a field the checkpoint schema lacks, that portion is externalized/deferred, NOT patched here. Do NOT mutate C:\Source\GitHub\backlogit or engram binaries.
5. P-001/P-016 PRESERVED. Crash-resumption is SINGLE-ACTIVE session-state restoration; it introduces NO parallel execution and NO new worktrees. Resumption picks up the SAME single-active pipeline cursor (the 109-F at-most-one-active-shipment linearization); it does not schedule parallel work.

CORRECTION to Finding 2 / Recommendation (append-only; original findings + prior addendum preserved above). The prior sketch spoke of driving the recovery over "the recorded single-active cursor" but did NOT establish WHO may perform the restore/resume or HOW the target checkpoint is chosen when several are unresolved. A third independent review (P1-6) established a ROLE-OWNERSHIP gap: (a) at session start MORE THAN ONE checkpoint can be ACTIVE/unresolved concurrently across agents — a `stage`-owned and a `ship`-owned checkpoint can both be active — so a "detect the active checkpoint" step is AMBIGUOUS and could silently restore the wrong session; (b) the checkpoint MUST NOT be auto-picked; (c) the backlogit CheckpointV1 schema carries an authoritative `agent` field (`required,oneof=ship stage`) identifying the OWNING agent, which the protocol must honor. RESOLUTION (chosen): the recovery contract now (1) REQUIRES the operator to EXPLICITLY SELECT a SINGLE checkpoint by filename (never auto-pick); (2) VALIDATES the selected checkpoint's CheckpointV1 `agent` ownership (`stage`/`ship`); (3) the ORCHESTRATOR ROUTES restore/resume/prune EXCLUSIVELY to that owning agent (stage-owned => Stage subagent only; ship-owned => Ship subagent only) and NEVER executes Stage/Ship-owned restore work itself directly (preserves P-001 role separation / persona isolation); (4) FAILS CLOSED (operator handoff; no restore/resume/prune/resolve) on missing/invalid/ambiguous `agent` ownership OR a checkpoint that cannot be uniquely selected. This uses only the EXISTING CheckpointV1 `agent` field (no new schema/plumbing — in-boundary for the prose layer) and stacks on top of the operator-confirmation gate. ## Correction Addendum (2026-08-05, FOURTH independent PUBLICATION-review repair; route claude-opus-4.8/anthropic/high)

CORRECTION to the recovery-contract selection semantics (append-only; original findings + all prior addenda preserved above). The third addendum's fail-closed clause ("FAILS CLOSED ... on ... a checkpoint that cannot be uniquely selected") was over-broad: it swept the ZERO-CANDIDATE case into fail-closed/operator-handoff. That is wrong. At session start the common, expected steady state is that NO active recovery candidate exists — an ordinary clean start with nothing to recover. Treating zero candidates as a failure would wrongly force an operator handoff on every normal session. RESOLUTION: the recovery contract is now explicitly TWO-BRANCH — (i) ZERO active recovery candidates => NO recovery is needed and the Orchestrator CONTINUES NORMAL ORCHESTRATION (NOT a failure, NOT an operator handoff); (ii) ONE OR MORE valid recovery candidates exist => the explicit-operator-selection-by-filename + CheckpointV1 `agent`-ownership validation + owner-exclusive restore routing gate engages, with FAIL CLOSED (operator handoff; no restore/resume/prune/resolve) applying ONLY AMONG THOSE EXISTING CANDIDATES on a non-unique selection, selection ambiguity, or missing/invalid/ambiguous `agent` ownership. The Orchestrator NEVER auto-picks when candidates exist, and NEVER treats zero candidates as ambiguity. Uses only the EXISTING CheckpointV1 fields (no new schema/plumbing; in-boundary for the prose layer).
