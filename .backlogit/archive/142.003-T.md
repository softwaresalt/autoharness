## THE CRITICAL CONSTRAINT (C3 — the single highest-consequence error available in this feature)
`{{ESCALATION_*}}` is the ACTING-ROLE-COLLAPSED, RESOLVED value and renders `escalation-protocol.instructions.md` / agent-narrative PROSE ONLY. `{{LEGACY_ESCALATION_*}}`, `{{STAGE_ESCALATION_*}}` and `{{SHIP_ESCALATION_*}}` are RAW pass-through written verbatim into `harness-config.yaml.tmpl`'s flat and nested blocks.

Substituting the collapsed value into a raw slot copies a NESTED-ONLY override into the FLAT block on re-render, reproducing the H2 flat+nested ambiguity that PR #316 round 3 already fixed once — and would corrupt the escalation route agents resolve at session start.

**Amendment B6, role-route clause — CORRECTED IN REVIEW-FIX CYCLE 1.** The original B6 text claimed `{{STAGE_*}}`/`{{SHIP_*}}` occur ONLY in `harness-config.yaml.tmpl` raw storage and must therefore derive to empty. **That claim is factually false and is WITHDRAWN.** `templates/agents/_orchestrator.agent.md.tmpl` lines 527–533 consume `{{STAGE_FAMILY}}`, `{{STAGE_PROVIDER}}`, `{{STAGE_REASONING_EFFORT}}`, `{{SHIP_FAMILY}}`, `{{SHIP_PROVIDER}}` and `{{SHIP_REASONING_EFFORT}}` directly, and the prose immediately below requires them to resolve concretely ("An installed workspace resolves each placeholder to concrete values ... resolves `stage` to `claude-opus-5`/`anthropic` and `ship` to `claude-sonnet-5`/`anthropic`"). It is TRUE that `_stage.agent.md.tmpl`'s OWN frontmatter uses `{{TIER_3_*}}` — but that never implied `{{STAGE_*}}` is unused elsewhere in the tree.

**Correct classification.** `{{STAGE_*}}`/`{{SHIP_*}}` are `RESOLVED-FROM-SOURCE` with the P-013.5 PER-SUB-FIELD tier fallback APPLIED: `stage.<field>` → `{{TIER_3_<field>}}`, `ship.<field>` → `{{TIER_2_<field>}}` (SKILL.md rows 429–434; line 453: resolved "**per sub-field**, not as an all-or-nothing block ... never from a hardcoded default and never silently from the current session model", and the installer "MUST resolve `{{STAGE_*}}`/`{{SHIP_*}}` variables before rendering ... so the installed frontmatter never carries an unresolved `{{...}}` placeholder").

**Why the escalation analogy does NOT transfer.** For escalation, SKILL.md deliberately defines TWO variable families — resolved `{{ESCALATION_*}}` (prose-only) and raw `{{LEGACY_ESCALATION_*}}`/`{{STAGE_ESCALATION_*}}`/`{{SHIP_ESCALATION_*}}` (storage-only) — precisely so the resolved value is never round-tripped into raw storage. **No such second, raw-only family exists for the role routes**: there is exactly ONE variable per role sub-field, and the contract defines it WITH its fallback. Deriving `{{STAGE_*}}` to empty would not preserve a contract distinction; it would fabricate one, and would render `_orchestrator.agent.md` with empty role-route values contradicting its own prose.

**Residual risk (RECORD, do not silently resolve).** Writing the resolved value into `harness-config.yaml.tmpl`'s `stage:`/`ship:` block does materialise a concrete value where the operator declared none, so a LATER `tier3`/`tier2` change no longer propagates through that stored file. This is a real consequence of the contract as written, NOT licence to deviate from it. The harness-config comment "falls back to tier3 (stage) / tier2 (ship) when empty" describes CONSUMER behaviour on an empty field, not a derivation instruction — so contract and comment are consistent. Implement per contract, surface this round-trip consequence in the task record; if it is judged wrong, that is a change to `.github/skills/install-harness/SKILL.md` and re-enters P-021 capture. It is not a derivation-layer decision.
