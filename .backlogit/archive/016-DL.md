# Plan 3 protocol-neutral remote management over PTY and ACP

## Problem Frame

<!-- BEGIN:problem-frame -->
Plan 2 V1 is shipped as 130-S: a Gradio presentation surface over a loopback-bound Microsoft Dev Tunnel, with request-envelope workspace/session binding, Observe + Steer commands, manual tail refresh, local journal authority, bounded line input, and metadata-only audit. The current workspace changes also show the local supervisor's PTY path and one shared active-child write target. The next product ask is materially broader: remote operators need practical management of a native interactive Copilot CLI session and an ACP session without pretending the two protocols are interchangeable. The system must support model and permission/yolo controls, MCP status, PTY slash-command equivalents, ACP-aware request/response routing, agent-request responses, fair local/remote input, automatic updates, restart handoff, stable external API discovery, and an explicit authenticated account/workspace/session boundary. It must remain a supervisor/control plane over Copilot/ACP, not a new reasoning runtime or arbitrary remote shell.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
A. Extend the current Gradio callbacks directly with more commands and polling. Rejected as the primary architecture: it would make Gradio the protocol, preserve manual refresh coupling, duplicate transport logic, and cannot represent ACP semantics safely.

B. Build a protocol-neutral session broker with typed versioned envelopes, cursor/event delivery, capability registry, authorization policy, and adapter interfaces; implement PTY and ACP adapters behind it; keep Gradio and any stable HTTP/API surface as presentation/transport adapters. Chosen: it preserves the Plan 2 layering decision, allows native PTY slash commands without forwarding slash text to ACP, supports graceful capability absence, and makes local/remote arbitration testable.

C. Implement a new agent runtime that normalizes PTY and ACP into a shared reasoning loop or pipes model output back into a new orchestrator. Rejected: Copilot CLI/ACP remains the external reasoning and tool-execution runtime; autoharness owns supervision, control, policy, and presentation adapters only.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Proceed with one Plan 3 product scope, delivered as three queued dependency-ordered shipments because the complete system exceeds a reliable single shipment. S1 establishes the broker contracts, capability/authorization model, PTY-vs-ACP adapter boundary, and local+remote arbitration. S2 wires runtime controls, ACP request routing, PTY slash-command mapping, restart handoff, and cursor-based push/long-poll updates. S3 exposes the stable versioned API and named Gradio presentation, with responsive UX and end-to-end prerequisite/auth/control tests.

TDD is non-negotiable for S1-S3. Each implementation unit starts with a failing deterministic test. S3 must begin with red Playwright tests that launch the actual Gradio Web UI and exercise browser-visible behavior through real locators and network requests; unit-only tests or mocked callback invocation cannot satisfy the browser gate. The hermetic browser suite uses a local loopback Gradio app backed by deterministic fake broker, PTY, ACP, identity, and prerequisite adapters. A separate live-validation matrix covers actual Copilot CLI, Dev Tunnel authentication/account, MCP servers, and ACP runtime only when those prerequisites are installed and authenticated. Missing live prerequisites produce an explicit BLOCKED/NOT_RUN result and must never be reported as passing.

The protocol rule is explicit: native PTY mode may carry interactive slash commands through the PTY adapter, with a closed allowlisted command mapping and metadata-only audit; ACP mode never receives blind slash text and instead uses an ACP-aware adapter mapping model selection, permission/yolo requests, MCP status, prompts, approvals, and agent requests to ACP messages/capabilities. If a backend or prerequisite cannot provide a capability, the broker returns a typed unavailable/degraded result and does not emulate it unsafely.

Authentication/account boundary remains layered without inventing a second identity provider: Microsoft Dev Tunnel authenticated access is the reachability gate; the application validates the versioned request envelope, a session binding token, and a locally enrolled account/principal binding when the tunnel exposes one. Tunnel URL secrecy is never trusted. Workspace/session mismatch, absent or unverifiable principal, stale token, and invalid capability are fail-closed and locally journaled without retaining remote content. Privileged controls such as enabling yolo/permission broadening, credential-affecting actions, arbitrary filesystem effects, or shutdown/restart remain local-approval-gated; remote requests may be queued for local approval rather than self-authorizing.

The broker remains single-workspace/single-active-session, local-journal authoritative, no remote retention store, bounded/rate-limited, loopback-only, optional-extra compatible, and browser-terminal/arbitrary-shell/chain-of-thought exposure remains out of scope.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
Implementation-level questions to resolve inside the plan without changing product scope: exact ACP SDK/protocol version and message mapping; whether the installed Copilot runtime exposes a stable model/permission/MCP control surface in native PTY mode; the trusted Dev Tunnel principal metadata available in target environments; event cursor durability across process restart; Gradio version-specific named API registration; the local approval UI used when a remote request asks for a privileged capability; and the supported Playwright/browser/Node version in CI. These are spike/adapter questions, not reasons to duplicate V1 or silently fall back to raw slash text.

Explicitly deferred beyond this series: multi-operator/multi-workspace hosting, browser terminal emulation/raw keystreams, arbitrary shell or filesystem APIs, remote approval of privileged operations without local consent, remote-side transcript retention, automatic credential rotation, a native autoharness MCP server, and a new model reasoning/action-observation loop.
<!-- END:open-questions -->
