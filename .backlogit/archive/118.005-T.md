SIZE: M. COMPLEXITY: medium. (Two independent axes; also emitted as structured backlog fields.) Shipment 1 (P0). Create src/autoharness/supervise/locking.py enforcing exactly ONE active supervised session per workspace.

F34 RULING (2026-08-11, operator-accepted; SUPERSEDES the dual-backend wording of the earlier F27 formulation and is the SOLE locking contract for this module) - GUARD/RECORD SEPARATION WITH A SINGLE, UNAMBIGUOUS OS-LOCK BACKEND. The module MUST use TWO DISTINCT FILES with two DISTINCT roles, and it MUST NOT conflate them:

(1) THE GUARD FILE is the SOLE EXCLUSION PRIMITIVE. It is a STABLE, NEVER-DELETED file inside the workspace root (e.g. `<workspace>/.autoharness/supervise/session.guard`). It is created if absent and is thereafter PERMANENT. NO CODE PATH MAY EVER delete, unlink, rename, replace, truncate-and-recreate, or otherwise change the identity of the guard file - not acquisition, not release, not force-unlock, not stale cleanup, not error handling, not tests' own teardown of a live workspace. Exclusion is established by taking an OS-BACKED ADVISORY LOCK on an open handle to that guard file, held for the session lifetime.

(2) THE RECORD FILE is SEPARATE and REMOVABLE (e.g. `<workspace>/.autoharness/supervise/session.record`). It carries holder/diagnostic metadata ONLY - PID, process start-time, session id. It is EXPLICITLY NOT the exclusion mechanism; it may be read, written, replaced or removed, but ONLY while the guard lock is held (118.006-T). F34 IGNORE COVERAGE (closes a gap this ruling itself created, and an ORDERING defect in the first draft of that fix): the guard and record files are PERMANENT, workspace-local runtime state, and the F24 ignore contract covers ONLY `.autoharness/sessions/` - so without this criterion a never-deleted guard file becomes a committed artifact in every target workspace. ORDERING CONSTRAINT: this task is a `127-S` member and 119.005-T (the F24 journal task) is a `128-S` member that ships LATER, so this task MUST NOT depend on a seam owned by 119.005-T. Therefore THIS task defines the reusable ensure-ignore helper in the supervise package (shipping in `127-S`): a small, idempotent, ADDITIVE function that takes relative path(s) and guarantees a single self-contained ignore file inside `<workspace>/.autoharness/` covers them, creating it when absent and NEVER rewriting unrelated operator content. It is invoked on guard creation for BOTH `supervise/session.guard` and `supervise/session.record`. 119.005-T then REUSES this helper for `sessions/` rather than creating a second, competing ignore file - which preserves the F24 behavioural ruling (the CORE ensures ignore behaviour at runtime, enforced by test, not by a template) while fixing the direction of the dependency. ACCEPTANCE: a test asserts `git check-ignore` (or equivalent) reports BOTH files as ignored in a freshly initialised workspace - ENFORCED, not asserted in prose.

O_CREAT|O_EXCL IS REMOVED AS A PERMITTED BACKEND. Exclusive-create is NO LONGER an alternative locking mechanism anywhere in this module, and NO BACKEND AMBIGUITY REMAINS: there is exactly ONE exclusion primitive (the guard lock) and every path - acquisition and cleanup alike - uses it. The guard file itself is opened with create-if-absent semantics, which is idempotent and safe precisely BECAUSE the guard is never deleted; that create is file provisioning, NOT exclusion, and MUST NOT be relied on for mutual exclusion. WHY THIS RULING EXISTS (record it in the module docstring so the constraint is not re-litigated): the previous dual-backend contract was jointly unsatisfiable with the cleanup protocol. Under O_CREAT|O_EXCL, a stale lock means the path ALREADY EXISTS, so exclusive-create can NEVER succeed; a force-unlock required to first acquire that primitive would therefore ALWAYS refuse, making --force-unlock - the only reachable remedy for a stranded lock (T17/120.006-T) - permanently unreachable and the workspace unrecoverably strandable. Under an advisory lock on a file that is then UNLINKED, a path/inode race appears instead: holder A locks inode-1 and unlinks it while contender B creates and locks inode-2, so BOTH believe they hold exclusion, and the holder-record compare-and-delete cannot detect it because it is not a record race. A stable never-deleted guard eliminates BOTH failures: the lock target's identity is invariant, so cleanup can always take the same lock, and no second inode can ever exist.

CROSS-PLATFORM, EXECUTABLE ON WINDOWS AND POSIX (this is a planning contract, not an implementation). The guard lock MUST be a non-blocking, exclusive, OS-BACKED file lock obtained from the Python STANDARD LIBRARY: `msvcrt.locking(fd, msvcrt.LK_NBLCK, n)` over a FIXED byte range on Windows, and `fcntl.flock(fd, LOCK_EX | LOCK_NB)` on POSIX. TERMINOLOGY PRECISION (do not let this cause a false equivalence): `fcntl.flock` is an ADVISORY whole-file lock while `msvcrt.locking` is a MANDATORY byte-range lock, so the two backends are NOT semantically identical in general. That difference is IMMATERIAL to this contract, and it is immaterial for a stated reason rather than by assumption: the guard file is accessed ONLY through this module's own documented seam, so there is no second, non-cooperating accessor for advisory semantics to fail against, and the byte range is FIXED so Windows range-locking never partially overlaps. What both backends MUST deliver is the observable behaviour below - that, not the kernel mechanism, is the contract. If a platform adapter layer is introduced instead, it MUST be an EXPLICITLY SCOPED CONTRACT with identical observable semantics on both platforms, and those semantics are themselves acceptance criteria: (a) NON-BLOCKING - contention returns promptly and never hangs; (b) EXCLUSIVE - at most one holder workspace-wide; (c) OS-RELEASED ON PROCESS DEATH - the kernel drops the lock when the holding process dies (on both platforms this follows from handle/descriptor closure at process teardown), so a crashed holder never permanently strands exclusion, and this MUST be asserted by test rather than assumed; (d) "ALREADY HELD" IS DISTINGUISHABLE FROM "ERROR" as separate, testable outcomes. Acceptance criteria MUST be written so they execute on BOTH Windows and POSIX; a criterion that can only run on one platform does not satisfy this task.

F27 REQUIREMENTS PRESERVED IN FULL - ACQUISITION IS ATOMIC AND OS-BACKED. Exclusion is established by the SINGLE ATOMIC guard-lock operation and NEVER by a check-then-write sequence. A read-then-write acquisition remains explicitly PROHIBITED: it opens a TOCTOU window in which two supervisors starting simultaneously both observe no live holder and both take the lock, which is precisely the concurrent-session failure this module exists to prevent. The PID + process-start-time record is retained for STALE-LOCK DIAGNOSIS ONLY (118.006-T) and is explicitly NOT the exclusion mechanism.

F31 REQUIREMENT PRESERVED AND NOW ACTUALLY SATISFIABLE - THE PRIMITIVE MUST BE REUSABLE BY CLEANUP. Expose guard acquisition as a documented, testable seam (an explicit context manager, NOT a private import-time side effect) so that 118.006-T's force-unlock can ACQUIRE THE SAME GUARD LOCK and hold it across inspection AND record removal as one critical section. Exclusion must NOT be an acquisition-path-only internal detail: a cleanup path that cannot take the same lock is forced into the check-then-act deletion that F31 identified as able to remove a LIVE holder's state. A failed acquisition MUST be distinguishable from an error so cleanup can treat 'cannot acquire' as 'a live holder exists' and REFUSE. Under the guard/record split this requirement is now IMPLEMENTABLE, because the guard always exists and is never the thing being removed.

FAIL CLOSED (H2): a live lock is NEVER auto-broken - contention yields the distinct terminal outcome REFUSED, not FAILED. RELEASE IS IDEMPOTENT AND CRASH-SAFE, exposed both as an explicit release() and as a context manager, because the 119.003-T DRAINING state calls it unconditionally on every terminal path (F22) and must never fail when the lock was already released. Release drops the guard LOCK and MAY remove the RECORD, but MUST NOT remove the GUARD FILE. Every lock path is resolved and asserted INSIDE the workspace root before any write (path-traversal containment); an escaping path aborts rather than being clamped.

MANDATORY CONCURRENCY TEST (F27, non-negotiable, preserved): a REAL parallel-contender suite - at least 8 contenders launched simultaneously as separate processes, repeated over at least 50 iterations - asserting that EXACTLY ONE acquires and every other observes REFUSED, with zero double-acquisitions across all iterations. A SEQUENTIAL contention test (start A, then start B) is explicitly INSUFFICIENT and must not be presented as evidence of mutual exclusion: it proves exclusion against a non-contending peer, which is a different proposition from the one the invariant needs. ADDITIONAL F34 TESTS: (i) GUARD PERMANENCE - after acquire, release, crash-without-release, and a full force-unlock cycle, the guard file still exists with an UNCHANGED identity (inode/file-id compared before and after, not merely 'a file exists at that path'), asserted on both platforms; (ii) NO-INODE-RACE - the parallel-contender suite additionally asserts that all contenders locked the SAME guard identity, which is the assertion that would have caught the unlink/recreate race; (iii) OS-RELEASE-ON-DEATH - a holder killed without release leaves the guard lock acquirable by a fresh contender. Tests also cover atomic acquire, idempotent release, double-release, release-after-crash, and path containment. Errors use the taxonomy from 118.003-T (supervise/errors.py). Stale-record detection, --force-unlock and recycled-PID rejection are split into 118.006-T to keep this task inside the 2-hour box.
