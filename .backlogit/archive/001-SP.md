## Question
Where could directed-acyclic-graph (DAG) dependency modeling improve harness delivery speed/reliability across Stage, Ship, backlog sequencing, telemetry, and policy gates, versus today's linear shipment/dependency workflow — WITHOUT violating P-001 (serial Stage->Ship) or P-016 (single implementation branch/worktree)?

## Findings
1. **backlogit already IS a DAG substrate.** item_deps + shipment-to-shipment blocks (AddShipmentBlock: "item_id completed after depends_on", with cycle detection) already form a dependency DAG. The current "linear" workflow is a *topological linearization* of that DAG, not a separate model. So DAG modeling is an interpretation/visibility layer over existing edges, not new plumbing.
2. **Readiness scheduling / critical-path visibility = SAFE, in-boundary.** Computing ready-set (no unmet blocks) and critical path over the existing blocks graph gives sequencing clarity and deterministic resumption (pick the next eligible shipment deterministically) WITHOUT concurrent execution. This is additive and preserves P-001/P-016.
3. **Parallel-safe execution / concurrent worktrees = OUT OF BOUNDS.** The classic DAG payoff (run independent branches in parallel) DIRECTLY violates P-016 (exactly one implementation worktree) and P-001 (serial Stage->Ship). Must NOT be adopted. DAG interest must not become parallel implementation.
4. **Failure isolation / retry** maps onto existing return-blocked + blocked-status semantics; a DAG view makes blast radius (downstream dependents) legible but changes no execution concurrency.
5. **Telemetry/policy gates**: a DAG readiness view could annotate telemetry with critical-path position; low value now, defer.

## How this informs E3C25E6D (topology enforcement)
The topology gate's "at most one active shipment" invariant is precisely the *mechanical enforcement of the DAG linearization*: it forbids the parallel-execution interpretation of the shipment DAG while permitting the dependency-ordered serial walk. The gate should treat backlogit shipment blocks as the readiness DAG and enforce that at most one node is "active" at a time (single-token walk). No parallel scheduler is introduced.

## Recommended bounded adoption path (DEFERRED — separate future follow-up, not this turn)
Phase 0 (this turn, via E3C25E6D): enforce single-active linearization of the existing shipment-blocks DAG in the topology gate.
Phase 1 (future follow-up): read-only DAG readiness/critical-path *reporting* command over backlogit blocks (visibility only, no scheduler).
Phase 2 (future, operator-gated): deterministic next-eligible resumption helper (still single-active).
NON-GOAL (permanently, under current policy): parallel-safe multi-worktree execution — blocked by P-001/P-016.

## Constraints preserved
P-001 serial Stage->Ship: preserved (single-active walk). P-016 single worktree: preserved (no parallel execution recommended). No source/template/schema/config mutated by this spike.
