# docs/compound docline conformance: backfill source/doc_type via the official idempotent migration and align the authoring contract

## Problem Frame

<!-- BEGIN:problem-frame -->
`backlogit docs lint` validates against the docline BASE FRONTMATTER CONTRACT, which requires `source` and `doc_type` on every in-scope document. Essentially the entire `docs/compound/` corpus fails with two required-field errors each.

STAGE MEASUREMENT (read-only, this session): 73 markdown files under `docs/compound/`; **72 missing `source`**, **73 missing `doc_type`**, **0 with both**, and **4 with no YAML frontmatter block at all**.

THE CORE QUESTION IS OWNERSHIP: are `source`/`doc_type` an autoharness-authored convention (ours to backfill) or a backlogit/docline-imposed base-schema requirement (external, per the 90F2A9F8 precedent)?

DECISIVE EVIDENCE GATHERED BY STAGE (read-only introspection only — `docs scope`, `docs migrate` dry-run, `--help`; no lint run, no writes):
1. `backlogit docs scope` reports the ACTIVE scope as `include_dirs: ["docs/"]`, `exclude_dirs: [".github/", "docs/archive/", "docs/memory/"]`, and a `path_map` that explicitly maps **`docs/compound/` -> `learning`**. So `doc_type` is DERIVABLE FROM PATH, and `docs/compound/` is in scope by deliberate configuration (two sibling doc directories are already excluded).
2. `backlogit docs migrate` exists as a first-party, **idempotent**, dry-run-by-default frontmatter migration (`--apply` gated behind `--yes` AND an explicit `--path`).
3. Stage's DRY-RUN over `docs/compound` plans `action: update` for every file with **`body_bytes_changed: false`** — the backfill is frontmatter-only and body-invariant.
4. `backlogit docs lint --profile` offers ONLY the tool's built-in `authoring` and `ingestion` profiles. There is NO docline configuration file anywhere in this repository, so there is no repo-local lever to mark a base-schema field optional.
5. autoharness's OWN compound frontmatter contract (`templates/skills/compound/SKILL.md.tmpl`, Phase 3) specifies `title, description, problem_type, category, component, root_cause, resolution_type, severity, message, file_path, citations, tags` — and has NEVER specified `source` or `doc_type`.

So both halves of the entry's framing are partly right: the two fields ARE externally defined (point 5), AND the gap is fully self-closable with a first-party tool against a scope autoharness opted into (points 1-3). The ownership question resolves on point 4: the "make it optional locally" lever does not exist.

SOURCE REFS (P-021 traceability): feature 139-F; shipment 147-S; PR #380 (closure PR); task N/A (closure-time authoring, no task record — reconciled, see notes); review-thread N/A (found by independent linter verification, not a review comment). Sibling file cited in the entry: `docs/compound/2026-08-21-ast-based-structural-regression-guards-beat-line-regex.md`.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
(a) BACKFILL — add `source` and `doc_type` across `docs/compound/` (73 files).

(b) LOCAL PROFILE OPT-OUT — declare the two fields optional/non-required in this repository's own docline profile.

(c) EXTERNAL — classify as a backlogit/docline-owned concern per the 90F2A9F8 / 84D8E6AB / 3C7AAC71 precedent; record for visibility, do not schedule.

(d) DESCOPE — remove `docs/compound/` from the docline scope entirely.

(e) BACKFILL + CONTRACT ALIGNMENT — (a) executed through the official idempotent `backlogit docs migrate`, PLUS amend `templates/skills/compound/SKILL.md.tmpl` so newly authored compound docs carry both fields at birth.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
CHOSEN: (e) = (a) BACKFILL VIA THE OFFICIAL IDEMPOTENT MIGRATION **PLUS** CONTRACT ALIGNMENT so new compound docs are born conformant. Reject (b), (c) and (d).

WHY (a) IS CHEAP AND SAFE HERE — the decisive evidence the entry did not have:
1. `backlogit docs scope` shows `docs/compound/` is already mapped in the ACTIVE docline `path_map` to doc_type `learning`. `doc_type` is therefore MECHANICALLY DERIVABLE FROM PATH, not an authoring judgement — there is even a `backlogit docs classify <path>` command that prints it. **(Clarified in review-fix cycle 4:** these commands are THIS workspace's tooling and are cited here as local evidence only. `templates/skills/compound/SKILL.md.tmpl` is a base Primitive 1 artifact that installs into workspaces with no backlogit, so the amended template states a CAPABILITY-NEUTRAL authority order — tooling operation, else configured path map, else directory convention — and must not name any specific tool or command. See amendment C3.)
2. `backlogit docs migrate` is an OFFICIAL, IDEMPOTENT, BODY-PRESERVING migration with a dry-run default and a write path gated behind BOTH `--apply --yes` AND an explicit `--path`.
3. Stage ran the dry-run over `docs/compound` (read-only, plan-only, zero writes): every file plans `action: update` with **`body_bytes_changed: false`**. The corpus-wide backfill is a frontmatter-only, body-invariant, git-revertible operation — not the "touch dozens of unrelated docs" hazard the entry feared.

WHY NOT (c) EXTERNAL, DESPITE THE 90F2A9F8 PRECEDENT. The precedent does not transfer. 90F2A9F8 is a defect in backlogit's own ERROR-HANDLING BEHAVIOUR (hard-abort on first decode error) — a thing only backlogit can change, in backlogit's repository, on backlogit's release schedule. THIS finding is a CONFORMANCE GAP IN AUTOHARNESS'S OWN CORPUS against a contract autoharness has already opted into (docline scope explicitly INCLUDES `docs/` and explicitly EXCLUDES `docs/archive/` and `docs/memory/` — so `docs/compound/` is in scope BY CHOICE, not by accident). autoharness can close it today, unilaterally, with a first-party tool. Classifying a self-closable gap as external is how a lint gate becomes permanently decorative.

WHY NOT (b) MAKE THE FIELDS OPTIONAL IN THIS REPO'S PROFILE. The lever does not exist. `backlogit docs lint --profile` accepts only the tool's two BUILT-IN profiles (`authoring`, `ingestion`); there is no docline configuration file anywhere in this repository, and `backlogit docs scope` reports the scope/taxonomy/profile set as tool-owned. "Make it optional here" would require an upstream backlogit change — i.e. it collapses into (c), with all of (c)'s objections plus a worse outcome (we would be asking upstream to weaken a base schema to accommodate our own un-migrated corpus).

WHY NOT (d) EXCLUDE `docs/compound/` FROM SCOPE. Same unavailability as (b) (scope is tool-owned), and it is the wrong direction on the merits: `docs/compound/` is the LEARNINGS corpus that the Step 1.8 learnings-retrieval path reads. Frontmatter on that corpus is a retrieval ASSET, not a tax. Excluding it would trade a one-off mechanical migration for permanently worse retrieval metadata.

WHY (a) ALONE IS INSUFFICIENT — the contract-alignment half is mandatory. autoharness's OWN compound frontmatter contract lives in `templates/skills/compound/SKILL.md.tmpl` Phase 3 and specifies `title, description, problem_type, category, component, root_cause, resolution_type, severity, message, file_path, citations, tags`. It has NEVER specified `source` or `doc_type`. Backfilling the corpus without amending that template guarantees the very next compound doc is born non-conformant and the gap silently reopens — precisely the recurrence pattern the 137-F/6D62077C paired-edit work exists to prevent. PR #380's Copilot review already caught one instance of this drift by hand; the fix must remove the need for a human to catch the next one.

FAVOURABLE RISK FINDING: `.github/skills/` contains only `install-harness`, `tune-harness`, `verify-harness`, `workspace-discovery` — there is NO installed dogfood counterpart to `templates/skills/compound/SKILL.md.tmpl`. The template edit therefore triggers NO paired-edit obligation and NO `.autoharness/harness-manifest.yaml` checksum churn for a dogfood copy. This materially lowers the blast radius of the contract half.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
R1 (MUST BE RESOLVED IN THE FIRST TASK, BEFORE ANY WRITE): what VALUE does the migration write into `source`? `doc_type` is path-derived and unambiguous (`learning`), but `source` is tool-defined. The implementing task MUST inspect the dry-run JSON output first and confirm the value is truthful provenance; if the migration would FABRICATE provenance it does not know, the task STOPS and returns to Stage. Do not `--apply` an unexamined value.

R2: 4 of the 73 files have NO frontmatter block at all. Whether `docs migrate` synthesises a block or skips them is unverified. These 4 must be enumerated explicitly and verified individually after the migration; if migrate skips them they need a separate, explicit, hand-authored frontmatter step consistent with the amended template contract.

R3 (WRITE DISCIPLINE): `--apply` requires `--yes` AND an explicit `--path`. The apply MUST be scoped to `--path docs/compound` and to nothing else. The rest of the `docs/` corpus (`decisions/`, `plans/`, `reviews/`, `closure/`, `spikes/`, `research/`, `design-docs/`, `product-specs/`) is IN docline scope and may well have the same gap — that is a SEPARATE surface and is explicitly OUT OF SCOPE here. Widening the `--path` is a P-021 scope breach.

R4 (VERIFICATION OBLIGATION): the acceptance evidence must PROVE body invariance, not assert it. Required: a `git diff` demonstrating that every changed file's diff is confined to the frontmatter block, plus a re-run of the migration showing IDEMPOTENCE (second run plans zero changes).

R5: `docs/compound/` is read by the Step 1.8 learnings-retrieval path (and by the `learnings-researcher` subagent where installed). Adding frontmatter keys must not disturb any existing key or reorder in a way that breaks a consumer. Body bytes unchanged is necessary but not sufficient — existing frontmatter keys must also survive verbatim.

R6 (SCOPE GUARD): amending `templates/skills/compound/SKILL.md.tmpl` is a TEMPLATE-FAMILY edit and must be a SEPARATE task from the corpus migration (width isolation, P-003). Do not combine a 73-file data migration with a template contract change in one task.

REQUIRES PLAN HARDENING: NO. Rationale recorded explicitly rather than defaulted: the corpus half is a first-party, idempotent, dry-runnable, body-preserving, single-path-scoped, fully git-revertible migration with a mechanical verification predicate; the contract half is a single template file with NO installed dogfood counterpart, therefore no paired-edit obligation and no manifest checksum churn. Neither half touches schemas, CLI distribution, or multiple template families. This is a considered `no`, not an absent field.
