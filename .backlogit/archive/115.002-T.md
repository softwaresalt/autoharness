<!-- BEGIN:description -->
WIDTH: CLI/presentation ONLY. Files: src/autoharness/cli.py + tests/test_gate_dag_readiness_cli.py. Does NOT touch gates/topology.py (115.001-T owns it) and does NOT touch docs (115.003-T owns them).

Wire the analyzer from 115.001-T into the existing `autoharness gate dag-readiness` command. NO new flag and NO new subcommand: the three cursor fields are emitted UNCONDITIONALLY as ADDITIVE fields (014-DL open question 1 resolved — an opt-in flag would create two payload shapes to test and document for no benefit, and additive fields are already backward compatible).

OWNERSHIP SPLIT (normative). The gate exposes SEVEN observable outcomes. The analyzer (115.001-T) implements SIX of them — outcomes 2-7: `cycle_detected`, `ambiguous_provenance`, `multi_active_anomaly`, `resume_active`, `ready_set_head`, `no_candidates`. THIS TASK EXCLUSIVELY OWNS outcome 1, `degraded`, and synthesizes it deterministically. The split follows reachability: `BacklogUnavailableError` is raised by `readers.list_shipments()`, so on that path the `shipments` tuple never exists, `compute_dag_readiness` is never called, and there is no readiness result to hand the analyzer. A `degraded` analyzer branch is therefore unreachable by construction and must not be expected, called, or tested as such.

JSON FIELDS ADDED (all always present):
- `next_eligible`: shipment id or null.
- `next_eligible_reason`: exactly one of `resume_active`, `ready_set_head`, `no_candidates`, `multi_active_anomaly`, `ambiguous_provenance`, `cycle_detected`, `degraded`. Always populated, even when `next_eligible` is null. The first six come verbatim from the analyzer; `degraded` is emitted ONLY by the synthesized degraded payload below.
- `next_eligible_detail`: object that is ALWAYS exactly `{"candidate_ids": [...], "offending_ids": [...]}` — BOTH keys ALWAYS present and ALWAYS arrays (empty arrays when not applicable). Never the empty object `{}`, never null, never a partial key set. This holds on EVERY output-shape statement and on EVERY path: ok, empty, cycle, and degraded.

HUMAN REPORT: `_format_dag_readiness_report` gains AT MOST ONE line, e.g. `next eligible: 117-S (resume_active)` or `next eligible: (none) — multi_active_anomaly: 118-S, 119-S`. The line must render on the cycle and DEGRADED early-return paths too, so the operator never sees a report that silently omits the cursor. On the degraded path it renders as `next eligible: (none) — degraded`.

DEGRADED PATH (this task's exclusive responsibility): the existing `BacklogUnavailableError` handler builds its payload literally in `_gate_dag_readiness_command`. Extend that literal payload — WITHOUT calling the analyzer — with exactly:
  "next_eligible": None,
  "next_eligible_reason": "degraded",
  "next_eligible_detail": {"candidate_ids": [], "offending_ids": []}
The detail value is TWO EMPTY ARRAYS. Emitting `{}` there is a defect: it would break the invariant that consumers may index `candidate_ids` and `offending_ids` unconditionally, and it would make the degraded payload's key set differ from the ok/empty payloads, contradicting AC1 and the plan's backward-compatibility table.

EXIT CODES ARE UNCHANGED: 0 for any report (ok/empty/degraded) and 2 for invalid args. dag-readiness still has NO BLOCK verdict — the multi-active anomaly is REPORTED, never escalated to a non-zero exit here; the pipeline-topology gate owns that BLOCK. Changing exit codes would break the Phase 1 contract.
