Add the PRE-CLAIM BOOTSTRAP GRANT surface and extend `--force` audit provenance so a self-hosted shipment that is blocked by the very defect it fixes can be entered by an AGENT under an explicit, bounded, operator-issued grant — instead of requiring an out-of-band operator act every time.

ADDED BY PR REVIEW-FIX CYCLE 1 (staging PR #448, thread PRRT_kwDORzpWpM6h3Tgb). The review finding is VALID and is ACCEPTED: the D6 grant recorded on 173-S named three forced `pre_claim` invocations (U0/U1/U2), but NO installed agent contract passes `--force` to `autoharness gate pipeline-topology`, and both Orchestrator and Ship HALT on exit 1. Verified against the installed text: `.github/agents/_orchestrator.agent.md` step 2a and `.github/agents/_ship.agent.md` step 3 each invoke the gate with `--mode agent --shipment {id} --phase pre_claim --json` and no force flag, and each states "Exit 1 ... halt ... never inferred, never fail-open". The grant was therefore NOT EXECUTABLE BY ANY AGENT. This task builds the surface that makes it executable FOR FUTURE SHIPMENTS. It does NOT and CANNOT authorize the initial claim of 173-S itself — see the shipment record's BOOTSTRAP section for the one-time operator-run entry path.

SCOPE FENCE: this task is the PRODUCT MECHANISM only. It changes no derivation semantics, no gate verdict logic, and no existing exit-code contract. A run with no grant present behaves EXACTLY as today, byte-for-byte.

DELIVERABLE 1 — GRANT RECORD (version-controlled, not gitignored).
Read grants from `.autoharness/bootstrap-grants/{shipment_id}.yaml`. This path is deliberately NOT under `.autoharness/gates/`, `.autoharness/staging/`, or `.autoharness/metrics/`, all three of which are gitignored in this repository; a grant that cannot be committed cannot be reviewed, and an unreviewable grant is not an auditable authorization. Required fields, ALL of which must match at evaluation time or the grant does not apply:
- `schema_version: 1`
- `shipment_id` — EXACT string match against the resolved target; no prefix, glob, or range matching
- `authorized_invocations` — an explicit list of invocation labels drawn from the closed set {`orchestrator_pre_route`, `ship_pre_branch`, `ship_pre_claim`}; each label is consumable AT MOST ONCE, enforced by the durable consumption record specified in DELIVERABLE 6 (NOT by an unqualified "already consumed" notion)
- `expected_token` — the single blocking token the grant covers (for 173-S: `PREDECESSOR_NOT_SHIPPED`)
- `expected_predecessor_id` — the exact inferred predecessor the grant covers (for 173-S: `172-S`)
- `manifest_digest` — a stable digest over the shipment's ordered `custom_fields.items`
- `authorizing_decision` — the operator decision reference (for 173-S: `D6`)
- `operator` — the authorizing human actor
- `expires_on_claim: true`

DELIVERABLE 2 — GRANT MATCHING (fail-closed, exact-bound).
A grant AUTHORIZES a forced invocation only when ALL hold at that moment: the requested invocation label is in `authorized_invocations` AND its consumption claim under DELIVERABLE 6 SUCCEEDS; `shipment_id` matches exactly; the observed gate result has exit code 1; the observed payload contains EXACTLY ONE blocking check and its token equals `expected_token`; the derived predecessor equals `expected_predecessor_id`; and the shipment's current ordered manifest digest equals `manifest_digest`. ANY mismatch — including an ADDITIONAL blocking check, a different token, a different predecessor, or a changed manifest — means the grant DOES NOT APPLY and the ordinary exit-1 halt occurs. There is no partial match and no nearest-match. A malformed, unparseable, or schema-invalid grant file is treated as NO GRANT plus a warning; it never widens authority.

DELIVERABLE 3 — CLI SURFACE.
Add `--bootstrap-grant-invocation {label}` to `autoharness gate pipeline-topology`. When supplied, the CLI loads the grant for the resolved target, applies Deliverable 2 matching, and only on a full match performs the existing force conversion (exit 1 -> exit 0, `forced: true`). `--force` semantics are UNCHANGED and remain the operator-only, human-authorized flag; the new flag is the AGENT-CONSUMABLE path and MUST NOT be usable to force a verdict for which no matching grant exists. `--bootstrap-grant-invocation` combined with `--force` is rejected as an argument error (exit 2): the two authorization sources must not be stacked.

DELIVERABLE 4 — FULL-PROVENANCE AUDIT RECORD (closes the second half of the review finding).
`_audit_pipeline_topology_force` today records only `timestamp`, `actor`, `reason`, `mode`, `phase`, `target_shipment_id`, `token`, `message`. Extend the record — ADDITIVELY, no existing field renamed or removed — with:
- `invocation` — the invocation label (`orchestrator_pre_route` | `ship_pre_branch` | `ship_pre_claim`), or `operator_manual` for a bare `--force`
- `observed_payload` — the FULL pre-force gate result dict, every check with its `details`, exactly as evaluated
- `head_sha` — `git rev-parse HEAD` at the moment of the invocation
- `manifest` — the resolved shipment id plus its ordered `custom_fields.items` and the computed digest
- `blocking_token` and `inferred_predecessor_id` — lifted out as first-class fields rather than left buried in the payload
- `authorization` — `{source: grant|operator_force, decision: <ref>, grant_path: <repo-relative path or null>, operator: <actor>}`
SECRETS DISCIPLINE: `observed_payload` is the gate's own structured check output, which is already bounded and classified. Do NOT widen this to arbitrary free-text diagnostics.

DELIVERABLE 5 — TELEMETRY PARITY (bounded).
Extend the `_emit_pipeline_topology_telemetry` metadata with `invocation`, `authorization_source`, and `inferred_predecessor_id` only. Do NOT serialize `observed_payload`, `head_sha`, or the manifest into telemetry: the existing code comment at the metadata construction site explicitly excludes `result.message` because free-text can carry raw frontmatter and filesystem paths, and the same reasoning bars bulk payload export. Telemetry remains FAIL-OPEN and must never change gate behaviour or exit code.

DELIVERABLE 6 — DURABLE, ATOMIC, AT-MOST-ONCE CONSUMPTION (ADDED BY PR REVIEW-FIX CYCLE 2, staging PR #448, thread PRRT_kwDORzpWpM6h3fqf; the finding is VALID and ACCEPTED).
WHY: the cycle-1 text said a label "is not already consumed" and nothing more. That phrase named NO storage, NO durability, NO atomicity, and NO failure semantics, so it was not implementable as written — an implementer could satisfy it with an in-process set that resets on every CLI invocation, which is exactly a zero-guarantee at-most-once. "At most once" is the entire security value of the grant; leaving its mechanism undefined leaves the bound undefined. The undefined phrasing is REMOVED and replaced by the following concrete contract.

6a. CONSUMPTION RECORD, EXCLUSIVE CREATION IS THE CLAIM.
Consumption state lives at `.autoharness/gates/bootstrap-grant-consumption/{shipment_id}/{label}.json`. This tree is INTENTIONALLY under the ALREADY-GITIGNORED `.autoharness/gates/` prefix: it is node-local RUNTIME state, not authorization. The GRANT is the version-controlled, reviewable authorization (Deliverable 1); the CONSUMPTION RECORD is the local durable proof that the authorization was spent. Committing consumption state would make a merge conflict able to resurrect or destroy a spend, which is worse than the local-only bound below.
The CLAIM is a single atomic filesystem operation: `os.open(path, os.O_CREAT | os.O_EXCL | os.O_WRONLY, 0o600)`. `O_EXCL` create-if-absent is atomic on POSIX and maps to `CREATE_NEW` on Windows, so it is the exclusion primitive on both CI platforms. Directories along the path are created with `exist_ok=True`; ONLY the record file itself is created exclusively. The file descriptor is written and `fsync`'d, then closed, BEFORE the forced evaluation proceeds. NO advisory lock, NO lockfile-plus-rename, NO read-then-write check — a read-then-write `if not exists` is a TOCTOU race and is explicitly FORBIDDEN.

6b. ORDER OF OPERATIONS — CLAIM BEFORE FORCE, ALWAYS.
1. Evaluate the gate UNFORCED and obtain the observed payload.
2. Apply every NON-CONSUMPTION Deliverable 2 match condition (shipment, exit code, sole blocking check, token, predecessor, manifest digest) FIRST. A mismatch returns the ordinary exit-1 halt and MUST NOT create a consumption record — a non-matching grant must not burn a label.
3. Only if all of those pass, ATOMICALLY CLAIM the label per 6a.
4. Only if the claim SUCCEEDS, perform the force conversion (exit 1 -> exit 0, `forced: true`).
5. Emit the Deliverable 4 audit record FROM THE CLAIMED RECORD (see 6f).
Claiming before forcing is the fail-closed direction: a crash between claim and force spends a label without forcing (safe, recoverable by operator), whereas forcing before claiming could force without ever recording the spend (unsafe, unrecoverable).

6c. RECORD CONTENTS (JSON, written at claim time).
`schema_version: 1`; `grant_digest` (SHA-256 over the EXACT BYTES of the grant file as read for this evaluation); `grant_path` (repo-relative); `shipment_id`; `label`; `phase` (always `pre_claim`); `actor` (resolved invoking actor) and `session_id` (invoking process/session identity) ; `head_sha`; `manifest_digest`; `blocking_token`; `inferred_predecessor_id`; `claimed_at` (UTC, ISO-8601); `status` (`claimed` at creation, advanced to `consumed` after the audit write succeeds); `audit_ref` (path + offset or line identity of the emitted audit record, filled when status becomes `consumed`). The `status` advance is an in-place rewrite of an ALREADY-CLAIMED record; it is NEVER a re-create and NEVER an unlink.

6d. CONTENTION AND REPLAY ARE FAIL-CLOSED.
If the `O_EXCL` create raises `FileExistsError`, the label is ALREADY CLAIMED — by a concurrent process, by an earlier completed run, or by a crashed run. In EVERY one of those cases the result is IDENTICAL and FAIL-CLOSED: no force, ordinary exit 1, and a warning naming the existing record path. The CLI NEVER waits, NEVER retries, NEVER polls, NEVER breaks or steals a claim, and NEVER distinguishes "someone else holds it" from "it was already spent" in its EFFECT. There is no timeout and no TTL: a TTL would silently re-open consumption after an interval, which is at-most-once-per-interval, not at-most-once.
A record whose `grant_digest` does NOT match the digest of the grant file currently on disk is ALSO fail-closed. This specifically defeats "edit the grant to reset consumption": rewriting the grant changes its digest, the mismatch is detected, and the label stays spent.

6e. CRASH STATES AND OPERATOR RECOVERY.
- Crash AFTER claim, BEFORE evaluation/force: record persists with `status: claimed`, no `audit_ref`. Any later run fails closed (6d). The label is spent without a force having occurred. This is the DESIGNED conservative outcome.
- Crash BETWEEN force and audit emission: record persists with `status: claimed`. The record ITSELF carries every field the audit would have carried (6c), so the durable evidence of the spend survives even when the audit line does not. A later run still fails closed.
- Crash DURING the `claimed` -> `consumed` rewrite: the record is either the intact `claimed` form or the intact `consumed` form (write to a temp file in the SAME directory, `fsync`, then atomic `os.replace`). A torn or unparseable record is handled as malformed (6g).
- RECOVERY IS OPERATOR-ONLY AND OUT-OF-BAND. No agent and no CLI code path may delete, truncate, reset, or recycle a consumption record. The documented remediation is: the operator inspects the record, decides whether the spend was real, and if it was not, REMOVES the record by hand and records that removal alongside the grant. The CLI offers NO `--reset-consumption`, NO `--force-consume`, and no equivalent, because any such flag hands an agent the ability to re-open an exhausted grant, which is self-authorization (P-005/P-001).

6f. THE AUDIT IS EMITTED FROM THE CLAIMED RECORD.
The Deliverable 4 audit record's `invocation`, `head_sha`, `manifest`, `blocking_token`, `inferred_predecessor_id`, and `authorization` fields are populated FROM THE FIELDS PERSISTED IN THE CLAIMED CONSUMPTION RECORD, not recomputed from live state at audit time. Recomputation could observe a workspace that changed between claim and audit and would record a state that was never the one authorized. `authorization` additionally carries the `grant_digest` and the consumption record path, so an auditor can join the audit line to the exact spend.

6g. MALFORMED OR STALE RECORDS FAIL CLOSED — NOTE THE DELIBERATE ASYMMETRY WITH A MALFORMED GRANT.
A consumption record that is unparseable, carries an unknown `schema_version`, is missing a required field, or whose `shipment_id`/`label` disagree with its own path is treated as PRESENT AND DISQUALIFYING — i.e. exactly as if the label were consumed — plus a warning. It is NEVER treated as absent and NEVER overwritten.
This is the OPPOSITE default from a malformed GRANT (Deliverable 2), and deliberately so: both defaults resolve toward NO FORCE. A malformed grant means "no authorization exists" -> do not force. A malformed consumption record means "a spend may have occurred" -> do not force. Reading either one permissively would be the only fail-open reading available.

6h. CONTAINMENT AND RACE-SAFE PATH RESOLUTION (STRENGTHENED BY PR REVIEW-FIX CYCLE 3, staging PR #448, thread PRRT_kwDORzpWpM6h3ttF; the finding is VALID and ACCEPTED).
WHY THE CYCLE-2 RULE WAS INSUFFICIENT — TWO SEPARATE DEFECTS, BOTH REAL.
(1) ROOT-RELATIVE CONTAINMENT IS SELF-SATISFYING. The cycle-2 rule asserted only that the resolved CHILD lies inside the RESOLVED ROOT. If the consumption ROOT ITSELF — or `.autoharness/gates/`, or `.autoharness/` — is a symlink/junction pointing OUTSIDE the workspace, `Path.resolve()` resolves the child THROUGH that same link, so the child lands under the resolved-outside root and the assertion PASSES. The check therefore certifies nothing about where the bytes actually land: one planted directory link redirects every consumption record out of the workspace while containment still reports "contained". Child-under-root does NOT imply root-under-workspace, and the cycle-2 text asserted only the former.
(2) RESOLVE-THEN-OPEN IS A TOCTOU WINDOW. `Path.resolve()` yields a STRING; `os.open` then re-walks that path from scratch. Between the two, any intermediate component can be swapped for a symlink and the exclusive create follows the NEW link. Cycle 2 correctly forbade a read-then-write existence check as TOCTOU (6a) but left this resolve-then-open TOCTOU open — the same defect class one layer down.
BOTH ARE CLOSED BY 6h-1..6h-7 BELOW. NEITHER MAY BE WEAKENED OR DEFERRED.

6h-1. SYNTACTIC VALIDATION FIRST, NO FILESYSTEM CALL (UNCHANGED FROM CYCLE 2).
`shipment_id` must match `^\d+(?:\.\d+)*-[A-Z]+$` and `label` must be an exact member of the closed three-label set BEFORE either is used to build a path. Any value carrying a path separator (`/` or `\`), a `..` segment, a NUL, or a drive/UNC prefix is rejected as an argument error with NO filesystem operation performed.

6h-2. THE ROOT MUST ITSELF RESOLVE INSIDE THE RESOLVED WORKSPACE (CLOSES DEFECT 1).
Compute `resolved_workspace = Path(workspace).resolve()` and `resolved_root = (Path(workspace) / ".autoharness" / "gates" / "bootstrap-grant-consumption").resolve()`. `resolved_root` MUST be a descendant of `resolved_workspace`, compared on the RESOLVED forms (`Path.is_relative_to`, or `os.path.commonpath`) and NEVER on the unresolved strings. If it is not, the invocation is REJECTED, nothing is created, and no label is burned. This assertion is evaluated FIRST and is IN ADDITION TO — never instead of — the child-under-root assertion; both are required.

6h-3. NO COMPONENT ON THE PATH MAY BE A LINK (CLOSES DEFECT 2 STRUCTURALLY).
Every component from `resolved_workspace` down to and including the final `{label}.json` MUST be a real directory/file — never a symlink, junction, mount point, or any other reparse point. This is enforced AT OPEN TIME by the strategies below, not by a pre-check: a pre-check alone merely re-creates the TOCTOU window it is meant to remove.

6h-4. POSIX STRATEGY — DESCRIPTOR-RELATIVE NO-FOLLOW WALK.
Obtain an anchor descriptor with `os.open(resolved_workspace, os.O_RDONLY | os.O_DIRECTORY)`. Then descend ONE component at a time (`.autoharness`, `gates`, `bootstrap-grant-consumption`, `{shipment_id}`) with `os.open(component, os.O_RDONLY | os.O_DIRECTORY | os.O_NOFOLLOW, dir_fd=parent_fd)`, closing each parent as you go. `O_NOFOLLOW` makes the open FAIL (`ELOOP`) when the component is a symlink, so a mid-walk swap cannot be followed. Missing directories are created with `os.mkdir(component, 0o700, dir_fd=parent_fd)` tolerating `FileExistsError` (the `exist_ok=True` equivalent), followed by the same no-follow descend; a component that exists but is not a directory fails closed. The CLAIM is then the SAME single exclusive create as 6a, issued RELATIVE TO the final directory descriptor:
  `os.open("{label}.json", os.O_CREAT | os.O_EXCL | os.O_WRONLY | os.O_NOFOLLOW, 0o600, dir_fd=consumption_dir_fd)`
Because every component was opened no-follow and the create is descriptor-relative, there is NO re-walk between validation and creation and therefore NO TOCTOU window. `O_EXCL` still supplies at-most-once exactly as in 6a; `O_NOFOLLOW` additionally guarantees the create cannot be redirected through a symlink planted at the record name itself.

6h-5. WINDOWS STRATEGY — REPARSE-POINT EQUIVALENT.
`os.O_NOFOLLOW` does not exist on Windows and `os.open` is NOT in `os.supports_dir_fd` there, so 6h-4 is unavailable and MUST NOT be silently approximated by the naive resolve-then-open. The equivalent is:
  (i) Walk the SAME component list top-down from `resolved_workspace`. For each component call `os.lstat(partial_path)` and REJECT if `st_file_attributes & stat.FILE_ATTRIBUTE_REPARSE_POINT` is set. The reparse-point attribute is the Windows generalization of "is a link" and catches directory symlinks, NTFS JUNCTIONS (`IO_REPARSE_TAG_MOUNT_POINT`) and file symlinks alike. Checking only for symlinks would MISS junctions — and a junction is what `mklink /J` produces with NO elevation, making it the cheapest attack to mount and therefore the one that must not be missed.
  (ii) Create missing directories with `os.mkdir(partial_path)` tolerating `FileExistsError`, then re-`lstat` each newly-created component and reject on a reparse attribute.
  (iii) Claim with the same exclusive create: `os.open(full_path, os.O_CREAT | os.O_EXCL | os.O_WRONLY | os.O_BINARY, 0o600)` (`O_EXCL` maps to `CREATE_NEW`).
  (iv) POST-CREATE IDENTITY RE-VERIFICATION — this is what substitutes for the missing no-follow guarantee. IMMEDIATELY after a successful create, `os.fstat(fd)` the descriptor and `os.lstat(full_path)` the expected path, and require `st_dev` AND `st_ino` to be EQUAL (CPython populates both on Windows from the volume serial number and the 128-bit file index) AND require the `lstat` result to carry NO reparse attribute. On ANY mismatch: close the descriptor, FAIL CLOSED, and DO NOT force. Do NOT attempt to delete the created file — deleting through a path that may itself have been redirected is another unsafe write; surface the anomaly for operator inspection instead. This narrows the residual window to a swap that occurs AND is undone between create and fstat while preserving file identity, which is not reachable without already holding write access inside the workspace.

6h-6. CAPABILITY GATE — NO SILENT DOWNGRADE.
Select the strategy by CAPABILITY PROBE, never by platform string: use 6h-4 when `hasattr(os, "O_NOFOLLOW")` AND `os.open in os.supports_dir_fd` AND `os.mkdir in os.supports_dir_fd`; use 6h-5 when `st_file_attributes` is available on `os.lstat` results. If NEITHER strategy is fully available, FAIL CLOSED: reject with a diagnostic naming the missing capability, create NOTHING, burn NO label, and return the ordinary exit-1 halt. Falling back to `Path.resolve()` + plain `os.open` is EXPLICITLY FORBIDDEN — that fallback IS the defect this section removes, and a silent downgrade would make the guarantee unobservable at exactly the moment it stopped holding.

6h-7. 6a-6g SEMANTICS ARE PRESERVED EXACTLY. The claim remains ONE exclusive-create call, so at-most-once (6a), claim-before-force ordering (6b), the fail-closed and indistinguishable contention/replay effect (6d), the crash states (6e), the audit-from-the-claimed-record rule (6f) and the malformed-record disposition (6g) all hold unchanged. A containment rejection occurs BEFORE any create, so — exactly like a non-matching grant under 6b step 2 — it NEVER burns a label.

6i. SCOPE BOUND, STATED HONESTLY (residual risk, accepted).
This mechanism guarantees at-most-once PER WORKSPACE CLONE. Because the record tree is gitignored, a FRESH CLONE starts with no consumption state and could in principle re-spend a label. This is bounded and acceptable, and MUST be documented rather than hidden: (i) a grant is `expires_on_claim`, and once the shipment is claimed it is no longer `queued`, so the observed token changes and the exact-token match fails; (ii) the manifest digest and predecessor bindings also drift as the shipment progresses; (iii) BOOTSTRAP-A's own bounds already treat the successful claim as the expiry event. A cross-machine at-most-once guarantee would require committing consumption state or an external coordinator, both of which are out of scope for this task and MUST NOT be invented here. 165.009-T documents this bound.

TESTS FOR DELIVERABLE 6 (in the grant-matching unit suite; stdlib `unittest`-compatible, no pytest-only constructs):
- CONCURRENCY: N >= 8 processes (`multiprocessing`, not threads — threads would not exercise the cross-process create) race the SAME grant and label against a fixture that would otherwise match. EXACTLY ONE forces and exits 0; every other exits 1; exactly ONE consumption record exists afterwards.
- REPLAY: a second sequential invocation of the same label, in the same workspace, with an unchanged matching fixture, does NOT force and exits 1; the existing record is byte-for-byte unchanged.
- NON-MATCHING GRANT DOES NOT BURN A LABEL: a mismatch on each Deliverable 2 dimension leaves NO consumption record behind, and a subsequent matching invocation with the same label still succeeds.
- CRASH BETWEEN CLAIM AND EVALUATION: inject a failure immediately after the claim; assert the record persists with `status: claimed` and that a re-run fails closed with exit 1.
- CRASH BETWEEN FORCE AND AUDIT: inject a failure at the audit write; assert the record persists carrying the full 6c field set and that a re-run fails closed.
- GRANT-DIGEST MISMATCH: consume a label, then EDIT the grant file; assert a subsequent invocation of any label fails closed rather than re-forcing.
- MALFORMED RECORD: truncated JSON, unknown `schema_version`, missing required field, and a record whose `label` disagrees with its filename each fail closed with a warning, and the record is NOT overwritten.
- STALE RECORD HAS NO AUTO-EXPIRY: a record with a `claimed_at` far in the past still fails closed (guards against a TTL being added later).
- CONTAINMENT — SYNTACTIC (6h-1): crafted `shipment_id`/`label` values containing `..`, `/`, `\`, a NUL, or a drive/UNC prefix are rejected before ANY filesystem call.
- CONTAINMENT — ROOT ESCAPE (6h-2; THE CYCLE-3 REGRESSION, thread PRRT_kwDORzpWpM6h3ttF): make the consumption ROOT ITSELF a link to a directory OUTSIDE the workspace, then invoke with an otherwise FULLY MATCHING grant. Assert the invocation is REJECTED, exits 1, creates NOTHING at either the in-workspace or the out-of-workspace location, and BURNS NO LABEL (a later invocation with the link removed still succeeds). Repeat the fixture with the link planted at `.autoharness/gates/` and at `.autoharness/`. Under the retired child-under-resolved-root rule EVERY one of these fixtures PASSED containment, so each MUST fail against that rule.
- CONTAINMENT — INTERMEDIATE COMPONENT LINK (6h-3): an intermediate directory on the path (`{shipment_id}/`) replaced by a link out of the root is rejected by the no-follow descend (POSIX) / reparse-attribute check (Windows); nothing is written through it and no label is burned.
- CONTAINMENT — FINAL-NAME LINK: `{label}.json` pre-created as a symlink to a file outside the root is NOT followed and NOT written through — `O_NOFOLLOW` (POSIX) or the post-create identity re-verification (Windows) fails closed. This fixture is ALSO a 6d already-claimed shape; assert the effect is fail-closed under BOTH readings and that the link target is unmodified.
- CONTAINMENT — TOCTOU SWAP AT THE VALIDATE/OPEN SEAM (6h-3/6h-4): inject a swap of an intermediate component to an out-of-root link at the exact point between path validation and the claiming open (a patched hook at the seam, or a racing process reusing the concurrency harness). Assert the claim FAILS CLOSED and that no file is created outside the root. A test that only plants a link BEFORE the call does NOT cover this case and does not satisfy this requirement.
- CONTAINMENT — WINDOWS REPARSE VARIANTS (6h-5): assert the root-escape, intermediate-link and final-name-link cases over BOTH a directory symlink AND an `mklink /J` JUNCTION. The junction variant runs UNCONDITIONALLY (junction creation needs no elevation and is the cheapest attack); the symlink variants `skipTest` when `SeCreateSymbolicLinkPrivilege`/Developer Mode is unavailable. Also assert the post-create `fstat`/`lstat` `st_dev`+`st_ino` identity check rejects a mismatch and does NOT delete the created file.
- CONTAINMENT — CAPABILITY GATE (6h-6): with the no-follow/`dir_fd` capabilities AND the reparse-attribute capability both probed as unavailable, assert the invocation FAILS CLOSED with the capability diagnostic, creates nothing, and burns no label — and assert BY SOURCE INSPECTION that no `Path.resolve()` + plain `os.open` fallback path exists.
- CONTAINMENT — HAPPY PATH UNAFFECTED: with no links anywhere, the descriptor-relative (POSIX) or reparse-checked (Windows) claim creates EXACTLY ONE record at the expected path with mode `0o600`, and the concurrency, replay and at-most-once assertions above all still hold byte-for-byte unchanged.
- NO SILENT RE-USE: assert by source inspection AND by behaviour that no code path unlinks, truncates, or re-creates an existing consumption record, and that no CLI flag exists to reset one.
- NO-GRANT PATH UNAFFECTED: with no grant present, no consumption directory is created at all.

TESTS (`tests/test_gate_pipeline_topology_cli.py` plus the same grant-matching unit suite):
