AC: add a POST-CASCADE PUBLICATION step to the Cascade Close Sub-Procedure closure section, stated ONCE (plan D-5 single-statement rule) and REFERENCED rather than restated, that the closing agent performs:

(1) DETECT THE TRACKING CASE for .backlogit/logs/{shipment_id}.jsonl, mechanically, never by assumption. CASE A - ALREADY TRACKED: `git ls-files --error-unmatch <path>` exits 0. CASE B - UNTRACKED, NOT IGNORED: ls-files misses AND `git check-ignore -q --no-index <path>` exits non-zero. CASE C - UNTRACKED AND IGNORED: ls-files misses AND check-ignore --no-index exits 0.

(2) STAGE ACCORDINGLY: Case A - commit its mutation NORMALLY, no force-add is performed or authorized; Case B - ordinary `git add <path>`; Case C - `git add -f <path>` LIMITED TO THAT ONE SHIPMENT LOG. Never a bulk, wildcard, or directory-level add.

(3) VERIFY THE FIVE R1-12 CRITERIA against the closure commit: (i) PRESENCE - `git cat-file -e {closure_commit}:.backlogit/logs/{shipment_id}.jsonl` succeeds (this is the durable postcondition and it is CASE-INDEPENDENT); (ii) FIDELITY - APPEND-ONLY PREFIX RULE (CORRECTED BY R1-13; the earlier "the committed blob is BYTE-IDENTICAL to the engine log the gate read, any diff is a failure not a warning" criterion is SUPERSEDED AND UNSATISFIABLE, because the engine appends the cascade's own shipment_status_changed / commit_tracked / archived events to the SAME log AFTER L1's read and BEFORE the closure commit - observable in .backlogit/logs/150-S.jsonl - so the committed log is ALWAYS a strict append-extension of the bytes the gate read): the exact PRECASCADE_EVIDENCE_ANCHOR line and ALL PRE-CASCADE BYTES EVALUATED BY L1 MUST appear BYTE-UNMODIFIED and in UNCHANGED RELATIVE ORDER as the PREFIX of the committed engine log - or, where a leading prefix cannot be established mechanically, as a PROVABLY UNCHANGED ORDERED SEGMENT preceding every engine-written mutation event. ENGINE-WRITTEN POST-GATE MUTATION LINES ARE EXPECTED APPEND-ONLY EXTENSIONS and are NEVER a fidelity failure. ANY modification, deletion, truncation, rewriting or reordering of pre-existing bytes IS a failure, not a warning. This criterion is NOT merged with (iii): "were the earlier bytes left alone" and "did the later bytes land after the anchor" are two independently failing questions (the B57F9E24 never-merge rule); (iii) ORDERING SURVIVES PUBLICATION - in the COMMITTED bytes the PRECASCADE_EVIDENCE_ANCHOR line precedes the engine-written shipment_status_changed / commit_tracked / archived lines in APPEND ORDER; (iv) BOUNDEDNESS WITHOUT REFERENCE TO .gitignore - the closure commit adds AT MOST ONE newly-tracked path under .backlogit/logs/ and it is this shipment's own log, and the commit contains NO .gitignore modification (asserting the bound against the commit's own contents is what makes it hold in every tracking case); (v) CASE RECORD - the detected case (A, B or C) is recorded.

(4) RECORD THE OUTCOME in the reconcile report as an explicit published / not-published result plus the detected case, so a legitimate CASE-A no-op is distinguishable from an omitted publication.

(5) ON FAILURE EMIT RECONCILE_CLOSURE_INCOMPLETE_L2_EVIDENCE - a P-001 INCOMPLETE-CLOSURE REPORT, NOT a halt token. Its name DELIBERATELY OMITS the RECONCILE_FAIL_PRECASCADE_ prefix so that 163.003-T's "no fifth PRECASCADE token" negative assertion continues to fire on a genuine regression, and so no reader can mistake it for a gate input.

(6) REMEDIATION WHEN CLOSURE EVIDENCE IS MISSING (R1-13, MANDATORY - "incomplete" must have a defined exit). (a) CLOSURE REMAINS INCOMPLETE: the shipment's mechanical close stands, but the RELEASE UNIT does not reach P-001 completion while the evidence is unpublished. (b) REMEDIATE WITH A FOLLOW-UP CLOSURE COMMIT on the same branch containing the EXACT engine log for that shipment, satisfying the append-only prefix rule of (3)(ii) and the boundedness criterion of (3)(iv); re-run criteria (i)-(v) against THAT commit and record the result and detected case in the reconcile report. This must happen BEFORE P-001 release-unit completion. (c) NEVER AMEND, REWRITE OR FORCE-PUSH PUBLISHED HISTORY to insert the evidence - no amend, no force-push, no rebase over a published closure commit; a publication defect is fixed by ADDING a commit, never by editing one reviewers have already seen. (d) NEVER MARK CLOSURE DONE WHILE THE EVIDENCE IS MISSING: RECONCILE_CLOSURE_INCOMPLETE_L2_EVIDENCE stays reported until the follow-up commit exists and verifies, and it remains a P-001 INCOMPLETE-CLOSURE REPORT throughout - it still never authorizes a close, never re-runs or downgrades the L1 gate, and never blocks the cascade. (e) IF THE ENGINE LOG CANNOT BE PRODUCED AT ALL (deleted, or never written by the engine), report that explicitly as an UNREMEDIABLE L2 GAP with its reason - do NOT substitute an agent-authored transcription, excerpt or summary, which would reintroduce the R1-0 defect of evidence authored by the party whose compliance is being checked.

HARD CONSTRAINTS: adds NO halt token and NO PRECASCADE token - the pre-cascade gate surface stays at EXACTLY the four R1-2 tokens (EVIDENCE_MISSING, EVIDENCE_STALE, ANCHOR_MISSING, ANCHOR_NOT_PRE_MUTATION). Runs OUTSIDE AND AFTER the single-writer lock window on .backlogit/queue/{shipment_id}.md; introduces no new lock, no second writer, no new failure window; MUST NOT be hoisted into the lock window (the log is not complete until the cascade's own mutation events have been appended, and the committed bytes only exist after the lock is released). NEVER authorizes a close, NEVER downgrades or re-runs the L1 gate, NEVER acts as a fallback for a failed L1 check, NEVER blocks the cascade.
