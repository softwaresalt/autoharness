COVERS findings 4, 5, 6. Finding 4: release_lock.ps1 removes the lock with Remove-Item -Force UNCONDITIONALLY, never reading the agent/pid recorded inside the lock file. Finding 5: release_lock.sh L35 does `rm -f $LOCKFILE` with no ownership check. Finding 6: Split-Path -Parent returns an empty string for a root-level relative path such as AGENTS.md when the target file is missing, Join-Path then throws under Set-StrictMode, and the missing-file branch uses the RAW relative path while acquire used Resolve-Path - so the two can compute DIFFERENT LOCK PATHS FOR THE SAME TARGET. Finding 6 travels with 4/5 because fixing ownership requires reading the lock at the CORRECT path first. WHY 4 AND 5 ARE THE MOST SERIOUS: the shipped scripts CONTRADICT the shipped policy - concurrency.instructions.md says agents MUST NOT delete lock files they did not create - so any agent can silently break any other agent's lock and the mutual-exclusion guarantee the pack exists to provide DOES NOT HOLD. OWNERSHIP MODEL, CORRECTED (O1-O4, binding). Cycle 0 made the recorded `agent` identity the PRIMARY authorisation input. That was WRONG AS A SECURITY CLAIM and is WITHDRAWN: acquire_lock.ps1:38 reads `$agentName = if ($env:AGENT_NAME) { $env:AGENT_NAME } else { "unknown" }` and acquire_lock.sh:32 reads `AGENT_NAME="${AGENT_NAME:-unknown}"` - AGENT_NAME is a CALLER-CONTROLLED ENVIRONMENT VARIABLE WITH A DEFAULT. Any process may set it to any value, including another agent's. It is not an identity; it is a label the caller chose. O1: `agent` is an ANTI-ACCIDENT / COURTESY IDENTITY, NOT a security identity - its purpose is to make a MISTAKEN cross-agent release visible and diagnosable and to name a human-meaningful owner in the refusal message. It carries NO authorisation weight against a caller that wants to bypass it. O2 THE STRUCTURALLY STRONGER MECHANISM (ADOPTED, IN SCOPE): acquire generates a HIGH-ENTROPY RANDOM TOKEN, writes ONLY ITS DIGEST into the lock file as `owner_digest`, and returns the TOKEN ITSELF to the caller on stdout; release requires the caller to present the token (-Token / --token, or LOCK_TOKEN) and releases only when the digest matches. This is a CAPABILITY check - possession of a secret established at acquire time - not a self-asserted label, so it does NOT collapse under a spoofed AGENT_NAME. Storing the DIGEST rather than the token is what makes it stronger than `agent`: reading the lock file no longer yields the credential. No new infrastructure - one random value, one digest, one argument. O3 THE HONEST BOUND (MUST be preserved in every acceptance claim): these are ADVISORY locks - an ordinary file in a workspace the caller can write. A local process with write access can DELETE THE LOCK FILE DIRECTLY and never invoke release at all. NO SCRIPT-LEVEL MECHANISM CAN PREVENT THAT AND THIS TASK DOES NOT CLAIM TO. What O2 buys is precise and limited: breaking another agent's lock stops being TRIVIALLY AND ACCIDENTALLY POSSIBLE THROUGH THE SUPPLIED TOOLING and becomes A DELIBERATE BYPASS OF IT. That is a real integrity improvement against accident, confusion, and buggy automation. It is NOT a defence against a hostile local process. Tamper-evident / OS-enforced locking is DSE-S3-1, explicitly out of scope. O4: `pid` remains CORROBORATING EVIDENCE ONLY, used in the staleness report, NEVER as authorisation - pid reuse on Windows makes it unsound as an authority. DECISION (ii): REFUSE, with the existing 1-hour staleness heuristic honoured ONLY behind an explicit -Force/--force flag THE OPERATOR SUPPLIES; automatic age override would let an agent break a foreign lock without operator involvement. DECISION (iii): exit code on refusal is NON-ZERO - exit 0 would make refusal indistinguishable from success, the fail-open shape this run is removing. Automatic breaking remains FORBIDDEN: a DoS that halts loudly is strictly safer than a corruption that proceeds quietly.
