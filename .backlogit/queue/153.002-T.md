OWNERSHIP MODEL (O1-O4, binding). Cycle 0 made the recorded agent identity the PRIMARY authorisation input. That was WRONG AS A SECURITY CLAIM and is WITHDRAWN: acquire_lock.ps1:38 reads $agentName = if ($env:AGENT_NAME) { $env:AGENT_NAME } else { "unknown" } and acquire_lock.sh:32 reads AGENT_NAME="${AGENT_NAME:-unknown}" - AGENT_NAME is a CALLER-CONTROLLED ENVIRONMENT VARIABLE WITH A DEFAULT. Any process may set it to any value, including another agent's. It is not an identity; it is a label the caller chose. O1: agent is an ANTI-ACCIDENT / COURTESY IDENTITY, NOT a security identity - its purpose is to make a MISTAKEN cross-agent release visible and diagnosable and to name a human-meaningful owner in the refusal message. It carries NO authorisation weight against a caller that wants to bypass it. O2 THE STRUCTURALLY STRONGER MECHANISM (ADOPTED, IN SCOPE): acquire generates a HIGH-ENTROPY RANDOM TOKEN, writes ONLY ITS DIGEST into the lock file as owner_digest, and returns the TOKEN ITSELF to the caller; release requires the caller to present the token and releases only when the digest matches. This is a CAPABILITY check - possession of a secret established at acquire time - not a self-asserted label, so it does NOT collapse under a spoofed AGENT_NAME. Storing the DIGEST rather than the token is what makes it stronger than agent: reading the lock file no longer yields the credential. TOKEN CONTRACT, PINNED IN CYCLE 2 (TC1-TC6, all binding, all MANDATORY ACCEPTANCE - cycle 1 said only "high-entropy random token" and "digest", which is unimplementable as a cross-platform contract and would have let the two platforms ship different and possibly weak primitives). TC1 CSPRNG ONLY, MINIMUM 128 BITS: the token MUST be at least 128 bits (16 bytes) of entropy drawn from a CRYPTOGRAPHICALLY SECURE random source. PowerShell: System.Security.Cryptography.RandomNumberGenerator (GetBytes); POSIX: read from /dev/urandom, or openssl rand. FORBIDDEN on both platforms: Get-Random, $RANDOM, awk rand(), date/time or pid-derived values, process-ID mixing, and any non-CSPRNG PRNG. A non-CSPRNG token is guessable and destroys the capability property O2 depends on. TC2 ENCODING: encode the raw bytes as lowercase hexadecimal (or unpadded base64url) with a FIXED length, so the token is a single shell-safe word with no quoting or whitespace hazards; both platforms MUST emit the SAME encoding and the SAME length. TC3 DIGEST - SHA-256 OR EQUIVALENT-OR-STRONGER: the value written to the lock file as owner_digest is SHA-256 (or a stronger member of the SHA-2/SHA-3 family) of the token's canonical encoded form, hex-lowercase. MD5 and SHA-1 are FORBIDDEN. PowerShell: Get-FileHash -Algorithm SHA256 over the canonical bytes, or System.Security.Cryptography.SHA256; POSIX: sha256sum with a documented fallback to shasum -a 256 (macOS) - and if NEITHER is available the script MUST FAIL CLOSED with a named remedy rather than silently downgrading to a weaker digest or to a plaintext token. TC4 IDENTICAL CROSS-PLATFORM SEMANTICS (extends H5): the PowerShell and POSIX variants MUST produce interoperable values - a token acquired by one variant MUST verify under the other, so canonical encoding, trailing-newline handling, and character case MUST be specified exactly and covered by a cross-variant test vector in 153.004-T's matrix. TC5 EXPOSURE AND SAFE HANDLING (documented, not assumed): the token is a SHORT-LIVED SECRET and the contract MUST state, in shipped documentation, exactly where it is exposed and how to handle it. It is returned on STDOUT so a caller can capture it (LOCK_TOKEN=$(acquire_lock.sh ...) / $token = ./acquire_lock.ps1 ...). CONSEQUENCES THAT MUST BE DOCUMENTED AND HONOURED: (a) stdout capture means the token can land in CI logs, transcripts, shell history, and agent conversation logs whenever the caller echoes or does not capture it - callers MUST capture rather than print, and the scripts MUST NOT echo the token again in any status, verbose, or error message; (b) the token MUST NOT be written to the lock file, to any log file the scripts create, or to telemetry - only its digest is persisted; (c) when passed via the LOCK_TOKEN environment variable it is visible to child processes and, on some systems, to other processes of the same user - the -Token/--token argument and LOCK_TOKEN are BOTH supported and their exposure difference MUST be stated so a caller can choose; (d) refusal, staleness, and diagnostic messages MUST print the lock path, agent, pid and age but MUST NEVER print owner_digest or the token; (e) the documentation MUST state plainly that these exposure paths are ACCEPTABLE ONLY BECAUSE the token is an anti-accident capability for an ADVISORY lock (O3) and is NOT a defence against a hostile local process, so leakage degrades the anti-accident property without creating a new adversarial exposure that did not already exist. TC6 NO NEW LOCK-FILE FIELD BEYOND owner_digest, and no change to the acquire race handling. O3 THE HONEST BOUND (MUST be preserved in every acceptance claim): these are ADVISORY locks - an ordinary file in a workspace the caller can write. A local process with write access can DELETE THE LOCK FILE DIRECTLY and never invoke release at all. NO SCRIPT-LEVEL MECHANISM CAN PREVENT THAT AND THIS TASK DOES NOT CLAIM TO. What O2 buys is precise and limited: breaking another agent's lock stops being TRIVIALLY AND ACCIDENTALLY POSSIBLE THROUGH THE SUPPLIED TOOLING and becomes A DELIBERATE BYPASS OF IT. That is a real integrity improvement against accident, confusion, and buggy automation. It is NOT a defence against a hostile local process. Tamper-evident / OS-enforced locking is 13F5EEF0, explicitly out of scope. O4: pid remains CORROBORATING EVIDENCE ONLY, used in the staleness report, NEVER as authorisation - pid reuse on Windows makes it unsound as an authority. DECISION (iii): exit code on refusal is NON-ZERO - exit 0 would make refusal indistinguishable from success, the fail-open shape this run is removing.
