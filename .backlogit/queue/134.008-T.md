<!-- BEGIN:description -->
Stage is the consumer of a P-021 capture; without this task the policy produces entries that nothing is obliged to deliberate on.

templates/agents/_stage.agent.md.tmpl '### Step 1: Stash Triage and Entry Classification' (~line 224) classifies entries as Feature-shaped or Task-shaped. Task-shaped entries flow through Step 1.5 grouping and can reach Step 3 planning directly. A deferred-expansion entry is frequently task-shaped and looks trivial, so the existing routing will carry it straight to a plan and defeat the operator's MANDATORY deliberation requirement.

Hardening H8: the fix must be a PRECEDENCE rule, not a fourth shape category.

LATE-IDENTIFIER RECONCILIATION (added by operator-directed contract replanning, 2026-08-19). 134.004-T's LATE-SURFACING THREAD criterion deliberately routes the reconciliation duty away from Ship: when a threadless-captured finding later surfaces on a review thread, Ship posts the reply and records the newly available identifiers in its own residual-risk record, but MUST NOT touch the entry, because the C5 carve-out grants creation only and the SINGLE-WRITE CAPTURE INVARIANT forbids a second write. That criterion names 'Stage's C6 intake responsibility' as the destination for the duty -- but until this replan, no task in the feature actually DEFINED that responsibility. The obligation was dangling: Ship correctly refused to reconcile, and nothing else was required to. The practical consequence is that every `N/A` recorded on the threadless path would become permanent, silently discarding a review-thread ID (and, for pre-PR findings, a PR number) that later became known. This task is the designated consumer, so the workflow is defined here.

Reconciliation is deliberately specified as retrieval-from-residual-risk-records rather than as a Ship hand-back: the residual-risk records are already mandated by C3 on both paths and already cite the deferred entry ID, so the join key exists with no new contract surface and no relaxation of Ship's role boundary.

Atomic three-part unit (hardening H3): template edit + byte-identical dogfood re-render + manifest checksum refresh + note provenance.
