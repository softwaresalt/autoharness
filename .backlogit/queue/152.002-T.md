Extract the probe body into an importable helper so it is testable at all (an inline heredoc in YAML is untestable by construction; the workflow keeps calling it as a step and no behaviour moves). Assert SIX cases against INJECTED responses (C1-C3 from cycle 0; C4-C6 ADDED IN ORCHESTRATOR REVIEW-FIX CYCLE 1, FINDING 15). C1 - HTTPError 404 => probe PROCEEDS. C2 - 200 from pypi.org whose body identifies the REQUESTED version => NON-ZERO EXIT with the version AND the remedy in the message. C3 - URLError => PROPAGATES, never treated as "not present". C4 - WRONG-HOST REDIRECT: a 200 whose FINAL RESOLVED URL host is NOT pypi.org (a mirror or interception proxy) => RE-RAISED AS A TRANSPORT ERROR, explicitly NOT "present". Assert on the FINAL response URL after redirects, not on the requested URL. This is the case that would otherwise hard-fail a legitimate release, and binding H2a's host assertion is unverified without it. C5 - MALFORMED JSON: a 200 from pypi.org whose body is not decodable JSON, OR is valid JSON lacking info.version => RE-RAISED AS A TRANSPORT ERROR. Cover BOTH shapes as separate cases; H2a says "if the body cannot be parsed, treat it as a transport error" and without these that clause is prose. C6 - MISMATCHED VERSION (OUTCOME REVERSED IN REVIEW-FIX CYCLE 2, FINDING 6; binding H2b): a 200 from pypi.org whose body identifies a version DIFFERENT from the one requested => RE-RAISED AS A TRANSPORT/INTEGRITY ERROR. FAILS CLOSED; the probe does NOT proceed and publication does not occur. WHY THIS REVERSED: the probe requests the EXACT-VERSION endpoint https://pypi.org/pypi/autoharness/{version}/json, which names the version IN THE PATH. A conforming PyPI can return only two things from that URL - 404 when the version does not exist, or 200 with a body identifying THAT version. A 200 naming a DIFFERENT version is a response the protocol does not permit, so it is not weak evidence of absence; it is POSITIVE EVIDENCE that something between the requester and PyPI is not behaving as PyPI (a cache serving a stale or mismatched object, a mirror synthesising responses, or an interception proxy - the same class of condition the version-ceiling spike measured for C4). Cycle 1 required "probe PROCEEDS" here, which detected an anomaly and then discarded it. That is fail-open reasoning inside a fail-closed shipment, and it is WORSE than the original else: branch, because the anomaly had already been observed before being thrown away. ABSENCE IS PROVED BY 404 AND NOTHING ELSE (C1). DISCRIMINATING POWER IS PRESERVED: C2 and C6 remain distinguishable because their outcomes differ IN KIND - C2 exits non-zero with an "already published, bump and re-tag" message, while C6 raises a transport/integrity error naming the mismatch. A probe that merely checks "did the request succeed" still passes C2 and STILL FAILS C6, because such a probe would proceed or report "present" instead of raising an integrity error. The body-versus-request-success discrimination H2a demands is fully retained; only the verdict for the anomalous branch changed. HERMETIC EXPECTATION FOR C6: inject a 200 from the pypi.org host whose decoded body carries an info.version differing from the requested version, and assert the helper RAISES (the same error type asserted by C4 and C5), and assert it does NOT return a "proceed" outcome and does NOT exit with the C2 already-published code. BINDING H4: no network I/O - every case is hermetic, injected responses only. RED BEFORE GREEN: the C2 case must be demonstrated failing against the pre-fix workflow content; C4, C5 and C6 are ALSO expected red pre-fix because the current else: branch is reached on any 2xx, and each observed red result must be recorded.
