EXCEPTION ORDERING IS PART OF THE CONTRACT, NOT A STYLE CHOICE (CYCLE 6, FINDING 9). urllib.error.HTTPError IS A SUBCLASS OF URLError. An `except URLError` clause placed FIRST therefore swallows EVERY 404 and EVERY non-404 HTTP error and reports them all as transport failures, silently defeating C1, C2 and C3 at once. THE HELPER CATCHES HTTPError FIRST AND URLError SECOND, and a test asserts that ordering holds by injecting a 404 and requiring it to reach the C1 outcome rather than the C3 outcome.

TYPED OUTCOMES AND NAMED EXCEPTIONS - NO AMBIGUOUS "RAISE vs EXIT" (CYCLE 6, FINDING 9). The case table below is stated in terms of the HELPER'S RETURN VALUE AND EXCEPTIONS; exit codes belong to the THIN CLI WRAPPER, not to the helper, and the two must never be conflated in a case description.
- The helper returns a ProbeResult carrying status ABSENT or PRESENT.
- It raises ProbeIntegrityError for a well-formed HTTP response that is WRONG (the C6 mismatched-version case, and the C5 malformed/incomplete-body cases), and ProbeTransportError for URLError, the C4 wrong-host redirect, and other transport failures. Both derive from a common ProbeError.
- `python -m build_support.pypi_probe` is a THIN mapping containing NO probe logic: ABSENT -> exit 0; PRESENT -> exit 2 (the fail-closed outcome, DISTINCT from an error so an operator can tell "already published" from "the probe broke"); ProbeIntegrityError and ProbeTransportError -> exit 1 with the message on stderr.
- Cases assert against the TYPED OUTCOMES (returns/raises), plus exactly ONE case per exit code asserting the CLI mapping. No test may have to guess whether a row means "raises" or "exits". Assert SIX cases against INJECTED responses (C1-C3 from cycle 0; C4-C6 ADDED IN ORCHESTRATOR REVIEW-FIX CYCLE 1, FINDING 15). C1 - HTTPError 404 => probe PROCEEDS. C2 - 200 from pypi.org whose body identifies the REQUESTED version => NON-ZERO EXIT with the version AND the remedy in the message. C3 - URLError => PROPAGATES, never treated as "not present". C4 - WRONG-HOST REDIRECT: a 200 whose FINAL RESOLVED URL host is NOT pypi.org (a mirror or interception proxy) => RE-RAISED AS A TRANSPORT ERROR, explicitly NOT "present". Assert on the FINAL response URL after redirects, not on the requested URL. This is the case that would otherwise hard-fail a legitimate release, and binding H2a's host assertion is unverified without it. C5 - MALFORMED JSON: a 200 from pypi.org whose body is not decodable JSON, OR is valid JSON lacking info.version => RE-RAISED AS A TRANSPORT ERROR. Cover BOTH shapes as separate cases; H2a says "if the body cannot be parsed, treat it as a transport error" and without these that clause is prose. C6 - MISMATCHED VERSION (OUTCOME REVERSED IN REVIEW-FIX CYCLE 2, FINDING 6; binding H2b): a 200 from pypi.org whose body identifies a version DIFFERENT from the one requested => RE-RAISED AS A TRANSPORT/INTEGRITY ERROR. FAILS CLOSED; the probe does NOT proceed and publication does not occur. WHY THIS REVERSED: the probe requests the EXACT-VERSION endpoint https://pypi.org/pypi/autoharness/{version}/json, which names the version IN THE PATH. A conforming PyPI can return only two things from that URL - 404 when the version does not exist, or 200 with a body identifying THAT version. A 200 naming a DIFFERENT version is a response the protocol does not permit, so it is not weak evidence of absence; it is POSITIVE EVIDENCE that something between the requester and PyPI is not behaving as PyPI (a cache serving a stale or mismatched object, a mirror synthesising responses, or an interception proxy - the same class of condition the version-ceiling spike measured for C4). Cycle 1 required "probe PROCEEDS" here, which detected an anomaly and then discarded it. That is fail-open reasoning inside a fail-closed shipment, and it is WORSE than the original else: branch, because the anomaly had already been observed before being thrown away. ABSENCE IS PROVED BY 404 AND NOTHING ELSE (C1). DISCRIMINATING POWER IS PRESERVED: C2 and C6 remain distinguishable because their outcomes differ IN KIND - C2 exits non-zero with an "already published, bump and re-tag" message, while C6 raises a transport/integrity error naming the mismatch. A probe that merely checks "did the request succeed" still passes C2 and STILL FAILS C6, because such a probe would proceed or report "present" instead of raising an integrity error. The body-versus-request-success discrimination H2a demands is fully retained; only the verdict for the anomalous branch changed.
