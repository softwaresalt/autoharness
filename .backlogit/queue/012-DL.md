# Mechanical serial Stage->Ship topology enforcement (autoharness gate pipeline-topology)

## Problem Frame

<!-- BEGIN:problem-frame -->
P-001 (serial Stage->Ship) and P-016 (single implementation branch/worktree) are today enforced primarily by AGENT PROSE in the Stage/Ship templates plus a partial Ship intake gate (060-F/061-S). Prose is bypassable and non-deterministic. E3C25E6D asks for a fail-closed `autoharness gate pipeline-topology` invoked before the topology-sensitive operations (shipment claim, branch/worktree creation, build, push, PR, closure) that mechanically verifies: (1) at most one active shipment; (2) queue/dependency + prior-closure readiness; (3) branch-to-claimed-shipment ownership; (4) exactly one implementation worktree, honoring only the explicit time-boxed Stage spike/research exception (P-016). It must be backed by backlogit claim/status as the shared lease, define atomicity/race behavior, add topology-aware pre-commit + extend pre-push hook templates with explicit install/activation and audited bypass, and evaluate required-vs-advisory CI enforcement. The deliberation must resolve five hard questions: autoharness/backlogit authority boundary, race/atomicity, manual-developer compatibility, bypass auditing, failure recovery, and rollout. This is the MECHANICAL enforcement layer on top of the 060-F prose policy — distinct, not duplicative.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
A) Put enforcement inside backlogit (mutate transition rules) — REJECTED: violates the global-tool/local-output boundary and the external-guard pattern (cf. 936C68F3/2970FA4E where the backlogit-internal transition guard was routed UPSTREAM, not patched here). autoharness must not own backlogit's internal state machine. B) Keep prose-only + expand Ship intake checks — REJECTED: prose is bypassable, non-deterministic, and does not cover Stage-side or pre-worktree operations; the whole point of E3C25E6D is mechanization. C) (CHOSEN) A fail-closed autoharness CLI gate `gate pipeline-topology` that READS backlogit claim/status as the authoritative shared lease and inspects LOCAL git branch/worktree state, enforcing the four topology invariants, wired into pre-commit + pre-push hook templates (opt-in install) and evaluated for a required CI backstop, with an audited --force bypass mirroring the existing copilot-review force-audit pattern. autoharness enforces; backlogit remains the source of truth for the cross-machine lease.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Option C. Resolutions to the five hard questions:

1) AUTHORITY BOUNDARY (autoharness vs backlogit): backlogit is the AUTHORITATIVE shipment claim/status store, but its ClaimShipment (queued->active) is NOT a compare-and-swap, lock, or lease at ANY scope. It performs an UNLOCKED read/check/write (read shipment -> MoveShipmentStatus active -> re-read -> activate manifest items) whose ONLY atomicity guarantee is PER-SHIPMENT ALL-OR-NOTHING PERSISTENCE WITH ROLLBACK: if any item fails mid-flight, the shipment and every already-activated item are reverted to their pre-claim queued state so no partial/torn activation is left behind. That all-or-nothing property prevents TORN WRITES within a SINGLE claim; it does NOT provide mutual exclusion between concurrent claims and there is NO serialization guarantee even within one synchronized checkout: two concurrent claims in the SAME checkout can both read 'zero active' and both proceed (LOCAL TOCTOU), and divergent not-yet-synced checkouts on different machines can likewise both claim, the conflict surfacing only at git sync/merge/CI (CROSS-MACHINE TOCTOU). So 'at most one active shipment' is NOT enforced by backlogit at claim time at ANY scope; it is provided ONLY by the gate's pre/post DETECTION plus fail-closed remediation, never by atomic exclusion. A true workspace-global lock or centralized remote lease is explicitly OUT OF SCOPE / future work; this feature invents no such infrastructure. autoharness `gate pipeline-topology` is a fail-closed READER/VALIDATOR: it queries backlogit status (CLI-preferred re-read per 106-S, MCP being the flaky surface) as observed in the current checkout and inspects LOCAL git branch/worktree topology. autoharness NEVER mutates backlogit's internal transition rules — the backlogit-internal active->queued guard is already satisfied upstream (backlogit 1.8.0 isValidShipmentTransition; 061-F all-or-nothing claim with rollback). A true centralized remote lease (server-side CAS) is explicitly OUT OF SCOPE for this feature and recorded as separate future work; this feature does NOT invent speculative cross-machine infrastructure. Do not mutate C:/Source/GitHub/backlogit.

2) RACE / ATOMICITY: backlogit ClaimShipment (queued->active) is per-shipment ALL-OR-NOTHING PERSISTENCE with rollback — it prevents torn/partial activation for a SINGLE claim but is NOT an atomic lease, lock, or CAS and does NOT serialize concurrent claims at ANY scope (LOCAL same-checkout races AND cross-machine divergence are both live TOCTOU windows). The gate does not attempt its own locking and provides no lock/lease of its own. Because the entire claim path is check-then-act with no exclusion, the gate MUST run immediately before each guarded op AND re-verify after claim by re-running the GLOBAL active-shipment invariant — not merely the target's own status — requiring EXACTLY ONE active shipment that IS the selected target (mirror/extend 106-S CLAIM_VERIFY_FAILED: post-claim CLI re-read; sole-active-target proceeds; target-still-queued retries once ONLY after re-running full topology + the pre-claim ZERO-active precondition + detect-before scan; target blocked / any other active shipment / inconsistency halts no-reclaim). The pre-claim invariant requires ZERO active shipments; post-claim allows exactly one, and only the target. Detect-before pattern (106-S SHIPMENT_STATE_INCONSISTENT) runs before validation/claim. CROSS-MACHINE + LOCAL TOCTOU SCOPE (documented limitation, NOT a guarantee): the 'at most one active shipment' invariant is NOT serialized by backlogit at ANY scope. Within a single synchronized checkout concurrent claims race (LOCAL TOCTOU: unlocked read/check/write); across machines divergent checkouts can both claim, the conflict detected only at sync/CI (CROSS-MACHINE TOCTOU). Both are BEST-EFFORT and DEGRADED — the gate DETECTS violations pre/post and fails closed on ambiguity/unreachable state, but does NOT PREVENT concurrent claims in real time. 'exactly one implementation WORKTREE' is machine-LOCAL only (git cannot see other machines' worktrees). The gate must state this boundary explicitly — worktree uniqueness is per-checkout (machine-local), the active-shipment invariant is DETECTION-ONLY (no serialization locally or cross-machine), and neither is a lock or lease.

3) MANUAL-DEVELOPER COMPATIBILITY: the gate is opt-in (never silently installed; mirrors pre-push template install prose). It is invocable manually (`autoharness gate pipeline-topology --json`). Local hooks are bypassable by design (git --no-verify); a manual developer doing ordinary git work is not blocked when no shipment is claimed (existence-guarded checks, per 106-S 'apply only when a shipment exists'). The gate degrades to advisory when backlogit is unreachable in a manual context, but fail-closed in agent/CI context — governed by an explicit mode flag, not silent inference.

4) BYPASS AUDITING: an operator-only `--force` writes a structured audit entry to `.autoharness/gates/pipeline-topology-force-audit.log` (reuse the copilot-review force-audit pattern), AND every gate RUN emits a telemetry event (pass/fail/forced) — so an operator `--force` bypass is auditable WHENEVER THE GATE EXECUTES. Distinguish two different bypasses: (a) an audited gate `--force` runs the gate and is fully observable via the force-audit log + telemetry; (b) a hook-level `git --no-verify` cannot be prevented by git and SKIPS the gate ENTIRELY — a skipped gate runs no code and emits no telemetry, so a `--no-verify` hook skip is INHERENTLY UNOBSERVABLE to local audit/telemetry (there is no local observer at skip time; the gate cannot record its own non-execution). The required CI backstop (see rollout) is therefore INDEPENDENT enforcement that re-validates topology server-side; it is the non-bypassable enforcement point, NOT proof that the local hook ran.

5) FAILURE RECOVERY: on a detected topology violation (e.g., two active shipments, branch/shipment mismatch, extra worktree) the gate halts fail-closed with a specific token and a remediation hint (return-blocked / abandon the stray shipment; remove the stray worktree; align branch). It is idempotent and re-runnable; it performs NO mutation, so re-running after remediation is safe. Recovery mutations are the operator's/Ship's responsibility, never the gate's.

6) ROLLOUT: staged advisory->required. Local pre-commit/pre-push hooks ship opt-in and default to advisory-warn, then required. Because Git has NO pre-worktree-add hook and local hooks are bypassable, a REQUIRED remote CI check is the authoritative SERVER-SIDE backstop for the at-most-one-active-shipment + branch-ownership invariants (the CI runner re-reads backlogit state from the SYNCED repo). This CI re-validation is an honest DETECT-AT-SYNC backstop — it catches divergence when checkouts converge in CI — but it is still NOT a lock or lease and does NOT serialize claims; genuinely concurrent claims (same-checkout OR on unsynced machines) are DETECTED at merge/CI, not prevented at claim time (fail-closed on ambiguity). CI is Linux-only/minimal per the pre-push template's P-019 note, so CI provides the server-side detect-at-sync backstop for the active-shipment invariant while local hooks enforce the fast-feedback + worktree-local invariants. Rollout order matches the operator-approved serial sequence: (A) deterministic gate core; (B) hooks/install adapters; (C) remote CI validation.

DAG informing input (spike 001-SP): the 'at most one active shipment' invariant is the mechanical enforcement of a SINGLE-ACTIVE linearization of backlogit's existing shipment-blocks DAG, realized by gate DETECTION (backlogit provides no serialization at any scope), not by a lock or lease. No parallel scheduler is introduced; DAG parallel execution is a permanent NON-GOAL under P-001/P-016. Any DAG readiness/critical-path visibility is a deferred, separately-scoped follow-up (001-SP Phase 1+), NOT harvested this turn.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
1) Should the required CI backstop hard-fail a PR when backlogit shows >1 active shipment in the SYNCED repo state (detect-at-sync, per the documented local+cross-machine TOCTOU limitation — not a lock, lease, or real-time serialization), or warn? Recommendation: hard-fail in required mode; this is an operator rollout toggle (default advisory in first release, flip to required after bake-in). 2) Gate config schema: reuse the existing gates config surface (gates/config.py) or a dedicated topology block? Recommendation: extend the existing gate config family to avoid a new schema blast radius — to be confirmed in impl-plan/hardening. 3) Cross-machine worktree uniqueness is fundamentally unobservable to local git; is documenting the limitation sufficient, or does the operator want a backlogit-recorded worktree-owner token? Deferred as a possible future enhancement — NOT in this bounded scope. These are rollout/design-refinement toggles, not blockers; defaults chosen above are safe (fail-closed, advisory-first).
