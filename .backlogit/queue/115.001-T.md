<!-- BEGIN:description -->
WIDTH: analyzer/pure-logic ONLY. Files: src/autoharness/gates/topology.py + tests/test_gates_dag_readiness.py. Does NOT touch cli.py and does NOT touch docs (115.002-T / 115.003-T own those).

Add a NEW pure function `compute_next_eligible(shipments, readiness)` (plus a frozen `NextEligibleResult` dataclass with a `to_dict()`) beside the existing `compute_dag_readiness`. It consumes already-read `ShipmentState` values and the existing `DagReadinessResult` and performs NO I/O and NO mutation whatsoever.

SCOPE — SUCCESSFULLY-READ DATA ONLY (six branches, gate outcomes 2-7). The gate exposes SEVEN observable outcomes, but ownership is split by REACHABILITY and the split is normative:
- Outcome 1 `degraded` is CLI-ONLY. `BacklogUnavailableError` is raised by `readers.list_shipments()`; when it is raised the `shipments` tuple never comes into existence, `compute_dag_readiness` is never called, and no `DagReadinessResult`/`ready_set` exists. Both of this analyzer's inputs are therefore absent on exactly the path that would signal degradation, so a `degraded` branch here is UNREACHABLE BY CONSTRUCTION. Do NOT implement it, do NOT claim it, do NOT test it here. 115.002-T synthesizes the degraded payload deterministically in the `BacklogUnavailableError` handler BEFORE this analyzer is invoked.
- Adding an explicit `is_degraded` input just to reach that branch was CONSIDERED AND REJECTED (see plan): it would let a caller assert degradation while simultaneously passing successfully-read data, creating a self-contradictory input space for no benefit. Separation is simpler and is the chosen design.

RESOLUTION ORDER — this analyzer evaluates gate outcomes 2-7 against the FULL UNFILTERED shipment enumeration, in exactly this order (numbering is the canonical gate-level numbering, retained so plan/task/docs agree): (2) `readiness.cycle_detected` -> null / `cycle_detected`; (3) ANY shipment with ambiguous live/archive provenance (reuse the EXISTING `_has_ambiguous_shipment_records`) -> null / `ambiguous_provenance` + offending ids; (4) more than one `active` shipment -> null / `multi_active_anomaly` + offending ids; (5) exactly one `active` shipment -> that id is the cursor, reason `resume_active`; (6) zero `active` -> tie-broken head of `readiness.ready_set`, reason `ready_set_head`; (7) zero `active` and empty ready_set -> null / `no_candidates`.

STRUCTURAL PATTERN (compound learning 2026-08-07-copilot-review-fix-introduces-new-filter-bug): enumerate UNFILTERED -> check anomalies FIRST -> only THEN partition into active/ready. Do NOT introduce any early narrowing filter; branches 3 and 4 must run before any active/ready partitioning so a corrupt or anomalous record can never be silently excluded.

TIE-BREAK — BRANCH 6 (`ready_set_head`) ONLY: sort by DESC `len(readiness.downstream_dependents[id])`, then ASC shipment id. Shipment ids are unique so the ordering is TOTAL — never ambiguous, never dependent on dict/filesystem iteration order. Reuse the already-computed `downstream_dependents`; add NO new graph traversal. The tie-break does NOT apply to branch 5 (`resume_active`), which has exactly one `active` shipment and therefore nothing to tie-break.

DETAIL SHAPE: `to_dict()` always emits `next_eligible_detail` as `{"candidate_ids": [...], "offending_ids": [...]}` with BOTH keys present as arrays — empty arrays when not applicable, never the empty object `{}` and never null.

H1 NON-REGRESSION: `compute_dag_readiness`, the existing `DagReadinessResult` fields, `_dag_all_predecessors_finished`, `_shipment_map`, `_dag_successors`, `_dag_detect_cycle`, `_dag_downstream_dependents` and every symbol the pipeline-topology gate depends on MUST NOT be modified. This is strictly additive to the module.
