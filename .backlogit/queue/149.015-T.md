Tests for epoch-key determinism, refresh at unchanged HEAD after a tool-version change, stale sibling rejection, and concurrent/idempotent same-key writes. Domain: tests. Files: 1.

<!-- BEGIN:acceptance-criteria -->
* **Scenario 2 is the direct regression test for the reported bug** — it must fail against the old `<head_sha>.json`-only design and pass against `<head_sha>-<fingerprint>`.
* Determinism is asserted **across input orderings** and across processes, not merely twice in one process — a fingerprint that depends on dict iteration order would otherwise pass a naive test.
* Stale sibling rejection is asserted **structurally** (the computed current key does not match the sibling), not by a hand-written staleness comparison.
* The concurrency test asserts exactly one well-formed report: no torn/partial JSON, no duplicate entries, no exception escaping.
* No prior report is overwritten or deleted in any scenario.
* No network access.
<!-- END:acceptance-criteria -->

<!-- BEGIN:description -->
Plan unit **U10c**. Create `tests/test_detectors_report_epoch.py`.

**4 scenarios**, all targeting the D-11 defect class directly:

1. **Deterministic fingerprinting** — identical freshness dimensions produce an identical epoch key across processes and across input orderings; changing any single dimension produces a different key.
2. **Refresh at unchanged HEAD** — after a `tool_version_dims` change at the **same** HEAD, a rerun writes a **new fresh report under a new key**, the prior file is **not** overwritten, and the consumer is **not** left at `insufficient_evidence`. **This is the regression test for the reported bug.**
3. **Stale sibling rejection** — a sibling report at the same HEAD with a different fingerprint is retained as history and is **never** selected as the current fresh report; rejection follows from key mismatch.
4. **Concurrent / idempotent same-key writes** — two writers at the same epoch key yield exactly one well-formed, non-corrupt, non-duplicated report.

**Gate command (Q5)**: `PYTHONPATH=src python -m unittest discover -s tests`
<!-- END:description -->

<!-- BEGIN:implementation-notes -->
**Depends on U7.**

**Why this unit exists**: the PR #414 finding (thread `PRRT_kwDORzpWpM6dGx-1`) was that a HEAD-only epoch key deadlocks evidence refresh — the sole persisted report goes stale on a tool-version change while append-only-never-overwrite prevents writing a fresh one at that same HEAD. Scenario 2 encodes exactly that situation, so a regression to HEAD-only keying fails loudly rather than silently stranding consumers at `insufficient_evidence`.

**Testing selection without a read-back API**: S1 ships no production read-back path (INV-2, Q1 containment). Scenarios 2 and 3 therefore exercise the **pure key-computation function** against a fixture directory — computing the expected key and checking which file it designates — rather than calling a consumer API that does not exist in this shipment. This preserves the Q1 boundary while still proving the selection rule.

**Concurrency**: exercise real concurrent writers (threads or subprocesses) rather than simulating; the failure mode is a torn file, which a mocked write cannot reproduce.
