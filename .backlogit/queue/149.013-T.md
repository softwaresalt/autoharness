Security tests for option-safe Git ref resolution: option-like refs, invalid refs, valid symbolic refs, and full-SHA pass-through. Domain: tests. Files: 1.

<!-- BEGIN:acceptance-criteria -->
* **The no-side-effect assertion is the gating one**: after a rejected `--output=<tmp>` base, the test asserts the would-be output file **does not exist**. Without this assertion the P0 argument-injection mitigation is unproven.
* Option-like refs produce the invalid-input exit class (exit 2), not a silent empty diff.
* Invalid refs are rejected with the same class; no `git diff` is invoked.
* Valid symbolic refs resolve to a full 40-char hex SHA.
* An already-full SHA resolves to itself, and `discover_modified_files` is shown to receive only validated hex SHAs.
* No network access.
<!-- END:acceptance-criteria -->

<!-- BEGIN:description -->
Plan unit **U8c**. Create `tests/test_gate_ref_safety.py`.

**4 scenarios**:

1. **Option-like refs are rejected with no side effect** — `--output=<tmp>`, `--upload-pack=...`, and a leading-dash ref each resolve to `None`, produce the invalid-input exit class, and — asserted explicitly — leave **no file created at the would-be output path**.
2. **Invalid refs** (nonexistent branch, nonexistent SHA) are rejected with the invalid-input class and no `git diff` invocation.
3. **Valid symbolic refs** (`HEAD`, `HEAD~1`, a branch name, a tag) resolve to a full 40-char hex SHA.
4. **Full-SHA pass-through** — an already-full 40-hex SHA resolves to itself unchanged, and `discover_modified_files` receives only validated hex SHAs.

**Gate command (Q5)**: `PYTHONPATH=src python -m unittest discover -s tests`
<!-- END:description -->

<!-- BEGIN:implementation-notes -->
**Depends on U8b.**

This suite is what makes the cycle-1 P0 disposition (thread `PRRT_kwDORzpWpM6dGx_a`) valid. Scenario 1's filesystem assertion is not decorative: the whole finding is that a read-only gate could be induced to **write a file**, so proving absence of that file is the actual proof of mitigation. Asserting only the exit code would leave the vulnerability untested.

**Why not folded into U11**: U11 already carries 4 scenarios (ART-01 fixture, RK1 retro-validation, --json exit-0-on-failed, --base honored). Adding 4 more would put 8 scenarios in one unit and breach both the plan's max-4-scenario granularity budget and the 2-hour rule.

Use a temp directory for the would-be output path so the test cannot pollute the repository even if the mitigation regresses.
