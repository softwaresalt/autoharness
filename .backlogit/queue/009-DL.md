# Mandatory post-merge context compaction as a first-class workflow policy

## Problem Frame

<!-- BEGIN:problem-frame -->
Stash 9940C563 asks whether post-merge context compaction should be a MANDATORY workflow step (Ship post-merge closure / P-017 dark-mode closure / two-agent Stage↔Ship handoff) so context is consolidated after every merge, and flags likely touch points: workflow-policies (new P-0xx), compact-context skill wiring, and Ship/Orchestrator closure sequencing.

CORE DESIGN CONSTRAINT (autoharness-specific): autoharness is ENVIRONMENT-AGNOSTIC (VS Code+Copilot, Copilot CLI, Codex, Cursor, Claude Code). `/compact` is a Copilot-CLI-specific command and MUST NOT be hard-wired into the harness. The environment-agnostic mechanism already exists: the `compact-context` skill (Primitive 1) which consolidates memory/plan/closure artifacts into durable docs-root files and archives verbose originals. Enforcement must be framed around invoking that skill, never a literal `/compact`.

CURRENT STATE (discovered):
1. The Ship TEMPLATE (`templates/agents/_ship.agent.md.tmpl`) Step 6 closure step 8 ALREADY says: 'Mandatory: Invoke compact-context with target: all ...'. So per-merge invocation of the env-agnostic skill is already the intended design — it invokes the skill, not `/compact`.
2. BUT it is only a bare 'Mandatory' bullet: it is NOT a first-class workflow policy (no precondition/postcondition/gate-point/violation-action), is NOT verify-harness asserted, and is NOT tune drift-detectable.
3. DRIFT: the installed dogfood copy `.github/agents/_ship.agent.md` Step 5 closure tasks OMIT the compact-context step entirely (close shipment → compound → docs → session memory → dark-mode summary → index resync). The non-policy bullet already drifted out of the installed copy — direct evidence that doc-only guidance is insufficient.
4. compact-context skill uses threshold-based INTERNAL candidate selection (threshold_days=14, max_files=40, max_size_kb=500; never compacts active checkpoints) and is Tier 1 (fast/cheap). It is idempotent — a no-op scan when nothing qualifies.
5. Prior spike 022-S (docs/exec-plans/2026-05-09-context-window-compaction-spike.md) established that autoharness CANNOT hook `/compact` or in-conversation summarization (environment-controlled); compact-context is the file-level, env-agnostic analog.</problem_frame>
<parameter name="options">OPTION 1 — Do nothing / leave as-is: rely on the existing bare 'Mandatory' bullet in the Ship template.
  + Zero work. − Already proven insufficient: it drifted out of the installed dogfood copy; not enforceable, not verified, not drift-detectable. Does not satisfy the item's intent. REJECTED.

OPTION 2 — Tighten wiring only (no new policy): re-add the compact-context step to the installed Ship copy and strengthen the template bullet, but do NOT add a P-0xx.
  + Smaller change. − Leaves the same structural weakness that caused the drift: mandatory sequencing that is neither policy-enforced nor verify-asserted. Inconsistent with how autoharness formalizes cross-agent sequencing (P-016/P-017/P-018/P-019 are all first-class). REJECTED as primary, but its drift-fix is subsumed into Option 3.

OPTION 3 (CHOSEN) — Formalize as a first-class policy P-020 + wire consistently + fix drift + verify:
  * Add P-020 'Post-Merge Context Compaction' to `templates/policies/workflow-policies.md.tmpl` (+ amendment log 1.15.0) with precondition/postcondition/gate-point/violation-action and explicit relationship to P-001 (closure) and P-017 (dark-mode closure).
  * KEY DESIGN: decouple mandatory INVOCATION (guaranteed at the post-merge closure boundary — Ship Step 6) from threshold-based CANDIDATE SELECTION (skill-internal, unchanged). Mandating invocation != mandating heavy compaction; the skill remains an idempotent Tier-1 no-op when nothing qualifies. This directly neutralizes the cost/latency objection.
  * Frame strictly around the compact-context skill (env-agnostic), NEVER `/compact`.
  * Wire P-020 into Ship template step 8 (policy reference + non-blocking failure semantics), Orchestrator closure-sequencing + DARK_MODE_COMPLETE content, compact-context skill 'When to Use', and Primitive 1/10 of harness-architecture instruction.
  * Fix the installed dogfood drift (`.github/agents/_ship.agent.md` add the missing step; mirror into Orchestrator/instruction/foundation enumeration sites), per P-016/P-017 dogfood-weave precedent.
  * Add a verify_workspace assertion (`ship_post_merge_compaction_gate`) + unittest, per the 010-S precedent, so the gate is machine-verified and drift-detectable henceforth.

OPTION 4 — Make it a hard MERGE gate (block merge until compaction done):
  − Wrong ordering: compaction is a POST-merge closure activity; the merge already happened. Blocking would be nonsensical and risky. REJECTED.

## Chosen Direction

<!-- BEGIN:chosen-direction -->
DECISION: (A) SHIPPABLE — proceed with the full Stage pipeline for Option 3.

Justification:
1. The environment-agnostic path is clear and already partially implemented: the compact-context skill is the canonical mechanism and the Ship template already invokes it (not `/compact`). No open environment-portability question remains.
2. The apparent 'mandatory-per-merge vs threshold-based' tension is resolvable, not a genuine tossup: decouple mandatory INVOCATION (per-merge, at Ship Step 6 closure) from threshold-based CANDIDATE SELECTION (skill-internal, unchanged). This guarantees a consolidation opportunity at every merge while keeping actual work bounded and idempotent. Cost is ~one Tier-1 directory scan per merge — negligible.
3. This is primarily FORMALIZATION + DRIFT-FIX of an already-intended behavior, not a speculative new capability. The installed dogfood Ship copy has already LOST the step — concrete proof that non-policy guidance is insufficient and that first-class P-020 + verify assertion is the correct remedy (matches P-016/P-017/P-018/P-019 convention).
4. Low blast radius on runtime behavior (docs/templates + one verify assertion + tests); no source logic change; non-destructive skill; non-blocking failure semantics.

The (B) human-decision path was evaluated and rejected: the only debatable points — 'force invocation even for tiny merges?' and 'policy vs. mere guidance?' — both resolve clearly (negligible no-op cost; and the observed drift proves guidance-only is inadequate). No material, unresolvable product judgment remains.

Because this touches workflow policy + closure sequencing (high blast radius), P-006 plan hardening is REQUIRED before plan-review; target plan-review P0=0/P1=0.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
RESOLVED IN PLAN (not blocking): (1) Failure semantics — compact-context failure at post-merge closure is NON-BLOCKING (merge already landed; Tier-1 non-destructive skill). The VIOLATION is SKIPPING invocation, not a failed run; codify in P-020 violation-action. (2) 'Per-merge' anchor — the Ship Step 6 post-merge closure boundary is the per-merge anchor; Orchestrator treats required compaction as part of the closure set that blocks next-shipment routing (composes with P-001, does not duplicate it). (3) Policy-vs-guidance — resolved to P-020 (first-class) given observed drift. (4) Whether to also add a Stage-side per-handoff trigger — NO; Stage already invokes compact-context at checkpoint threshold (Step 6 continuity); the 'after every merge' concern is a Ship-closure concern, so no new Stage obligation is added beyond existing behavior.
