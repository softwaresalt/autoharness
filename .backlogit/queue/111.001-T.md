ZERO-CANDIDATE NO-OP + EXPLICIT SELECTION + OWNERSHIP + OWNER-EXCLUSIVE ROUTING (re-review 2026-08-05, 111.001-R P1-6 — role-ownership recovery contract; publication-review 2026-08-05, 111.001-R P1-7 — zero-candidate = no-recovery-needed, not failure): at session start the ORCHESTRATOR ENUMERATES unresolved/ACTIVE recovery candidates (list_checkpoints status=active). ZERO-CANDIDATE CASE: if NO active recovery candidate exists there is NOTHING to recover — the Orchestrator CONTINUES NORMAL ORCHESTRATION. Zero candidates is the EXPECTED STEADY STATE and is EXPLICITLY NOT a failure and NOT an operator handoff. ONLY WHEN ONE OR MORE valid recovery candidates exist does the recovery contract engage: MORE THAN ONE checkpoint may be active concurrently across agents (a `stage`-owned and a `ship`-owned checkpoint can both be active at once), so the Orchestrator NEVER auto-picks — it REQUIRES the operator to EXPLICITLY SELECT a SINGLE checkpoint by filename. It then VALIDATES the selected checkpoint's CheckpointV1 `agent` ownership, which MUST be exactly `stage` or `ship` (backlogit CheckpointV1: `agent` is `required,oneof=ship stage`), and ROUTES all restore/resume/prune work EXCLUSIVELY to that owning agent: a `stage`-owned checkpoint is restored/resumed ONLY by the Stage subagent, a `ship`-owned checkpoint ONLY by the Ship subagent. The Orchestrator MUST NEVER execute Stage/Ship-owned restore/resume/prune work itself directly (preserves P-001 role separation / persona isolation). 2. FAIL CLOSED on selection/ownership AMONG EXISTING CANDIDATES (does NOT apply to the zero-candidate case in AC#1): WHEN ONE OR MORE candidates exist but a single checkpoint cannot be UNIQUELY selected (MULTIPLE active candidates without an explicit operator selection, or ANY selection ambiguity), OR the selected checkpoint's `agent` is missing/empty/invalid/any value other than `stage`/`ship`, the protocol FAILS CLOSED => operator handoff; NO restore/resume/prune and NO resolve. Zero candidates NEVER triggers this fail-closed path — it is the no-recovery-needed continuation (AC#1), not an ambiguous selection. 3. OPERATOR-CONFIRMED RESTORE (H1): after a valid UNIQUE selection + owner routing, the OWNING agent PRESENTS the checkpoint and REQUIRES EXPLICIT OPERATOR CONFIRMATION before ANY restore/prune -> ONLY on explicit operator confirmation restore state_dump (get_checkpoint) and resume from the recorded SINGLE-ACTIVE cursor -> resolve_checkpoint ONLY after confirmed successful resume (H3 ordering). NO automatic resume under ANY condition; ambiguous/torn/partial state => operator handoff with the anomaly surfaced. 4. NO DEAD-SESSION AUTO-RECOVERY (re-review 2026-08-05, 111.001-R P1-5 CORRECTED — supersedes the prior heartbeat/liveness-threshold wording): checkpoint schema V1 exposes NO heartbeat/session-lock/lease and only `created_at`/`updated_at`, so age ALONE cannot distinguish a live from a dead session and there is NO concrete liveness source to prove a session is dead (the spike 002-SP explicitly excluded new checkpoint-schema fields / runtime plumbing). Therefore the protocol NEVER auto-resumes and NEVER hijacks a possibly-live session; restore/prune proceeds ONLY after explicit operator confirmation. 5. SINGLE-ACTIVE (H2): on operator-confirmed resume, pick up the SAME single-active cursor (109-F linearization); NO parallel resume, NO new worktree (P-001/P-016).
