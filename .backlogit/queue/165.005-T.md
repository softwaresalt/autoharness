Turn 165.004-T's expected-failure parity tests into ordinary passing assertions. Align `compute_dag_readiness` (L1968) and `_dag_all_predecessors_finished` (L1873) with the authoritative `pre_claim` model across EVERY derivation state.

HARDENING F3 (ARCHITECTURALLY MANDATORY): derivation AND closure evidence MUST be implemented as a SINGLE SHARED HELPER consumed by BOTH gates, reusing `FilesystemTopologyReaders.closure_complete` (L654) READ-ONLY through one common path. A PARALLEL reimplementation is a REVIEW-BLOCKING DEFECT: independent logic is the architectural root cause of the original divergence and would let the two gates re-diverge on a future dimension. State in the task record whether the shared helper lives in `topology.py` or a new module (plan-review P3-1).

ONE SNAPSHOT, ONE ANSWER (plan-review cycle 2 P2-3, reinforced by review-fix cycle 2 finding 2): the genesis determination is derived from WORKSPACE-WIDE properties, not per-shipment ones, and it now has THREE of them, all of which must be computed from ONE snapshot inside the shared helper and handed to both gates:
- G2: does any shipped-terminal shipment exist, LIVE or ARCHIVED;
- G3: how many extant NONTERMINAL (queued/active) shipment records exist, live or archived — genesis requires the candidate to be the SOLE one;
- G4: does any ABANDONED shipment record exist, live or archived.
Genesis is granted ONLY when the candidate has no edges, carries no `dag-root`, and G2/G3/G4 all clear. If `pre_claim` and `dag-readiness` each probe these facts independently, they can observe different snapshots mid-mutation and re-diverge on exactly the dimension this task exists to unify — the same class of defect, one abstraction level up. Three independent facts multiply that risk, so single-snapshot computation is not optional.
DO NOT reimplement a broader genesis notion on the advisory side. The advisory gate must consume the SAME narrow rule; a `dag-readiness` that still treats "nothing shipped yet" as genesis would advertise as ready a shipment `pre_claim` blocks as `unsequenced` — reintroducing the exact contradiction this task removes.

DELIVERABLES:
1. Advisory readiness resolves the SAME four states (`explicit` / `declared_root` / `genesis` / `unsequenced`) as `pre_claim`, under the same narrow genesis rule, and models the same closure-evidence requirement for the `explicit` state.
2. POLICY-BLOCKED EXCLUSION (review-fix cycle 1, finding 4): a shipment blocked as `unsequenced` MUST be excluded from `ready_set` and from `next_eligible` in `compute_next_eligible` (L2075). `dag-readiness` must never advertise as "next" something `pre_claim` will refuse to authorize.
3. A `declared_root` must NOT be reported advisory-blocked — parity is required in BOTH directions.
4. Advisory output carries an EXPLICIT non-authorizing label.
5. `next_eligible` / cursor output is disambiguated so it cannot read as authorization.
6. `pre_claim` remains the SOLE claim authority; `dag-readiness` NEVER authorizes, under any state or configuration.

DO NOT weaken, relax, or bypass the closure-evidence check to achieve parity. Parity is achieved by making the ADVISORY side model the SAME requirement, never by lowering the authoritative side. The closure-evidence NAMING defect is out of scope here (stash FD0CCB42).
