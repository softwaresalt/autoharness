Wire the Python wheel channel to the payload manifest, replacing the ad-hoc `[tool.hatch.build.targets.wheel.force-include]` table with the manifest-derived table.

GREEN RESPONSIBILITY (assigned by the RED harness 160.005-T): this task turns the WHEEL-COMPOSITION cases green - test_wheel_excludes_backlogit_explicitly (AC3), test_wheel_excludes_dev_directories (AC3), test_wheel_contains_required_runtime_set (AC4), test_docs_root_guides_only (AC4). It does NOT own the release-path case (160.015-T) or the generation/drift cases (160.014-T).

APPROACH - hardening decision H1 (generated-and-asserted, NOT a dynamic build hook): hatchling's force-include is static TOML and cannot read the YAML manifest without a custom `hatch_build.py` hook. A build hook would add a new failure mode into the release pipeline - the hardest place to debug. Instead: the manifest is the source of truth, the pyproject include table is GENERATED from it by the single command `python -m build_support.payload generate --channel wheel` (160.014-T), and a test asserts the two are equal. The table is a DERIVED artifact; hand edits are prohibited and detected by `generate --check`.

RELEASE-PATH GATE IS A SEPARATE TASK (Orchestrator review-fix cycle 1, findings 6 and 7): AC2b - the unbypassable in-job payload-composition gate added to `.github/workflows/release.yml` - is delivered by 160.015-T. Editing a CI workflow is a different surface with a different blast radius than editing packaging config, and folding it in here mixed CI work with packaging work and pushed this task past the 2-hour rule. This task MUST NOT edit release.yml.

REMOVES: the `"docs" = "src/autoharness/data/docs"` force-include (all 642 files / 6.9 MB). Proven dead weight - verify_workspace.py resolves every docs/* path against workspace_path (the target workspace), never the packaged data dir. That "referenced != required payload" judgment is centralized in `build_support.payload.classify_target_workspace_path` (160.004-T) and must not be re-derived here.

INVARIANT I4 - NON-NEGOTIABLE: preserve `core-metadata-version = "2.4"` on BOTH the wheel AND sdist targets. These pins exist because hatchling 1.32.0 defaults to Metadata-Version 2.5, which the SHA-pinned pypa/gh-action-pypi-publish action's bundled twine < 7.0.0 REJECTS. See docs/compound/2026-08-30-unpinned-hatchling-metadata-version-vs-pinned-publish-action.md. Dropping either pin breaks publishing. Add test_core_metadata_version_pins_preserved.

WARNING (verification V2): a local `uvx twine check` CANNOT reproduce the metadata failure - it always resolves the latest twine. Local build success is NOT evidence that publishing will succeed. Metadata compatibility remains an explicit CP2 pre-publication check.

SAFETY MODE (SHIP-10 plan H2): careful + freeze-scope. ELEVATED - this task edits a release-critical file.
- pyproject.toml: build tables ONLY. Project metadata, dependencies, version, entry points, and BOTH `core-metadata-version` pins are behaviour-preserving and must be asserted unchanged.
- .github/workflows/release.yml is OUT OF SCOPE for this task and must not be touched (see 160.015-T).
- ROLLBACK CHECKPOINT: before this task lands, record the exact pre-change bytes of pyproject.toml so revert is a single-file restore that returns the payload to the untrimmed superset (degraded but functional).
- NO-PUBLISH CHECKPOINT: this task MUST NOT run `twine upload`, `gh release create`, or trigger release.yml's publish path. Publication is Ship/Orchestrator scope (CP2).
- FREEZE-SCOPE: `src/autoharness/` is read-only (invariants I1/I2).
