updated_at: 2026-09-03T08:25:02.000273Z

Wire the Python wheel channel to the payload manifest, replacing the ad-hoc `[tool.hatch.build.targets.wheel.force-include]` table.

APPROACH — hardening decision H1 (generated-and-asserted, NOT a dynamic build hook): hatchling's force-include is static TOML and cannot read the YAML manifest without a custom `hatch_build.py` hook. A build hook would add a new failure mode into the release pipeline — the hardest place to debug. Instead: the manifest is the source of truth, the pyproject include table is GENERATED from it, and a test asserts the two are equal. Same fail-closed guarantee, failure surfaces in CI rather than at publish.

REMOVES: the `"docs" = "src/autoharness/data/docs"` force-include (all 642 files / 6.9 MB). Proven dead weight — verify_workspace.py resolves every docs/* path against workspace_path (the target workspace), never the packaged data dir.

INVARIANT I4 — NON-NEGOTIABLE: preserve `core-metadata-version = "2.4"` on BOTH the wheel AND sdist targets. These pins exist because hatchling 1.32.0 defaults to Metadata-Version 2.5, which the SHA-pinned pypa/gh-action-pypi-publish action's bundled twine < 7.0.0 REJECTS. See docs/compound/2026-08-30-unpinned-hatchling-metadata-version-vs-pinned-publish-action.md. Dropping either pin breaks publishing.

WARNING (verification V2): a local `uvx twine check` CANNOT reproduce the metadata failure — it always resolves the latest twine. Local build success is NOT evidence that publishing will succeed. Add test_core_metadata_version_pins_preserved.

ACCEPTANCE: AC1, AC3, AC4, I4. Composition tests (prior task) pass against the newly built wheel.
