Wire the Python WHEEL channel to the payload manifest, replacing the ad-hoc `[tool.hatch.build.targets.wheel.force-include]` table with the manifest-derived table.

SCOPE CLARIFIED IN REVIEW-FIX CYCLE 2 (finding 3): this task wires THE WHEEL ONLY. The SDIST is a separate published channel and is wired by 160.019-T. Cycle 1 treated "Python packaging" as one surface, which silently left the sdist untrimmed while claiming the disclosure risk was closed.

CLASS OWNERSHIP - TWO DIFFERENT DUTIES (corrected in cycle 2, finding 1). Cycle 1 assigned this task four "red to green" cases, two of which ALREADY PASS on the baseline, so no honest red observation was ever possible for them.
- RED-FIRST cases this task turns RED to GREEN (authored red by 160.005-T): test_wheel_generated_table_matches_manifest (AC2c - the COMMITTED wheel table equals the manifest-derived table; this is a property of the WIRING, which is why it is owned here and not by the generator task, see finding 2), and test_docs_root_guides_only (AC4 - genuinely red today: the wheel currently ships all 642 docs files).
- CHARACTERIZATION cases this task must PRESERVE GREEN (authored green by 160.016-T): test_wheel_excludes_backlogit_explicitly, test_wheel_excludes_dev_directories, test_wheel_contains_required_runtime_set, test_core_metadata_version_pins_preserved (wheel pin). These are green on the baseline because the existing force-include table already lists only templates, schemas, four .github/ subtrees, two instruction files, docs and AGENTS.md - so .backlogit/, tests/ and experiments/ are ALREADY absent from the wheel. They are INVARIANTS THIS TASK MUST NOT BREAK while rewriting the table, not behaviours it introduces. Recording a red observation for them would require deliberately breaking the wheel first, which is fabricated evidence. If any of them goes red during this task, THAT IS A REGRESSION IN THIS TASK, not progress.
This task does NOT own the release-path case (160.015-T), the generator cases (160.014-T), the sdist cases (160.019-T), or the plugin cases (160.007-T).

APPROACH - hardening decision H1 (generated-and-asserted, NOT a dynamic build hook): hatchling's force-include is static TOML and cannot read the YAML manifest without a custom `hatch_build.py` hook. A build hook would add a new failure mode into the release pipeline - the hardest place to debug. Instead: the manifest is the source of truth, the pyproject wheel include table is GENERATED from it by the single command `python -m build_support.payload generate --channel wheel` (160.014-T), and a test asserts the two are equal. The table is a DERIVED artifact; hand edits are prohibited and detected by `generate --check`.

RELEASE-PATH GATE IS A SEPARATE TASK (Orchestrator review-fix cycle 1, findings 6 and 7): AC2b - the unbypassable in-job payload-composition gate added to `.github/workflows/release.yml` - is delivered by 160.015-T. Editing a CI workflow is a different surface with a different blast radius than editing packaging config, and folding it in here mixed CI work with packaging work and pushed this task past the 2-hour rule. This task MUST NOT edit release.yml.

REMOVES: the `"docs" = "src/autoharness/data/docs"` force-include (all 642 files / 6.9 MB). Proven dead weight - verify_workspace.py resolves every docs/* path against workspace_path (the target workspace), never the packaged data dir. That "referenced != required payload" judgment is centralized in `build_support.payload.classify_target_workspace_path` (160.004-T) and must not be re-derived here.

INVARIANT I4 - NON-NEGOTIABLE: preserve `core-metadata-version = "2.4"` on BOTH the wheel AND sdist targets. These pins exist because hatchling 1.32.0 defaults to Metadata-Version 2.5, which the SHA-pinned pypa/gh-action-pypi-publish action's bundled twine < 7.0.0 REJECTS. See docs/compound/2026-08-30-unpinned-hatchling-metadata-version-vs-pinned-publish-action.md. Dropping either pin breaks publishing. This task rewrites the WHEEL build table and MUST leave the sdist target's pin byte-identical - 160.019-T rewrites the sdist table and carries the mirrored obligation for the wheel pin. Both are covered by the CHARACTERIZATION case test_core_metadata_version_pins_preserved, which asserts BOTH pins in one place precisely so neither task can drop the other's.

WARNING (verification V2): a local `uvx twine check` CANNOT reproduce the metadata failure - it always resolves the latest twine, and it checks whatever is in dist/, which after `uv build` is wheel AND sdist. Local build success is NOT evidence that publishing will succeed. Metadata compatibility remains an explicit CP2 pre-publication check covering both artifacts.
