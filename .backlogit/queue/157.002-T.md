PART A: parity test comparing INSTALLED superset-of TEMPLATE for the active tool's operations and feature keys. BINDING H3: FAIL CLOSED if either file is unreadable or unparseable - a parity test that skips on a missing file is the same fail-open shape being removed. BINDING H3a (ADDED IN ORCHESTRATOR REVIEW-FIX CYCLE 1, FINDING 13) - KEY-SET CONTAINMENT IS NOT ENOUGH; TEMPLATE-OWNED MAPPINGS REQUIRE VALUE EQUALITY. H2 halts on a value-changed key, but H2 RUNS ONCE, inside 157.001-T's regeneration. A key-set-only parity test means that AFTER 157.001-T completes, a later edit silently changing mcp_tool: backlogit_create_item to something else keeps every key present and passes forever - the drift class this shipment exists to close would be detected on day one and never again. The parity test MUST therefore assert VALUE EQUALITY, not merely key presence, over the TEMPLATE-OWNED surface: RECURSIVE VALUE PARITY OVER EVERY TEMPLATE-OWNED PATH, NOT AN ENUMERATED FIELD LIST (REWRITTEN IN REVIEW-FIX CYCLE 2, FINDING 8). THE RULE: walk the PARSED template registry document recursively and, for EVERY leaf path present in it, assert the installed registry carries an EQUAL value at the SAME path - UNLESS that exact path appears in the closed override allow-list of H3b below. Default is ASSERT; exemption is by explicit path only. WHY THE ENUMERATION WAS REPLACED: a list of selected fields is a DENYLIST WEARING AN ALLOWLIST'S CLOTHES - it protects exactly what someone remembered on the day it was written, and every field added to the registry template AFTERWARDS is unprotected by default and silently so. Cycle 1's list omitted top-level schema_version, which this workspace's registry declares as "1.0.0" and which is precisely the field whose silent divergence would make every other parity result meaningless (a v1 installed registry compared against a v2 template is comparing two different contracts). It would equally omit any future template-owned key - a new operation, a new feature flag, a new status value - so the drift class this shipment exists to close would reopen on the next registry template change, with NO test failing to announce it. THE RECURSION IS THE POINT: a new template-owned field is protected THE MOMENT IT IS ADDED TO THE TEMPLATE, with no test edit and no one remembering.
SCOPE OF THE WALK, PRECISELY: (a) the walk is driven by the PARSED TEMPLATE document, so it covers exactly the template-owned surface and cannot be defeated by an installed registry omitting a key - a path present in the template and ABSENT from the installed registry is a FAILURE (missing is not equal), which is what catches a field silently dropped during regeneration. (b) It is driven by the PARSED structure, never by raw text, so key ordering, comment placement, quoting style, and YAML formatting are irrelevant and cannot produce false failures. (c) Every leaf is compared, at every depth: scalars, and members of nested maps and sequences, INCLUDING paths nobody has thought of yet. (d) A path present ONLY in the installed registry (not in the template) is reported as INFO and does NOT fail - the template is the authority over what it owns, and it does not own what it never declared; that is what keeps genuinely local additions possible. (e) Interior-whitespace normalization is applied to cli_command values only, where it is a formatting artifact of the declared CLI fallback P-012 degraded mode depends on; it is NOT applied globally, because whitespace inside an mcp_tool name or a status value IS a difference.
PATHS THE WALK NECESSARILY COVERS - stated as CONSEQUENCES of the rule, NOT as the definition of it, and NOT as a list to be maintained: operations.*.mcp_tool (a wrong value fails at call time inside an agent run, never in CI); operations.*.cli_command (the P-012 CLI fallback); operations.*.params, per key (a wrong param mapping silently writes the wrong field); field_mapping.* and status_values.* (pure template-owned translation tables with no legitimate local meaning); features.* (see the additional flip assertion below); tool_name and tool_type (identity; H7 already forbids changing tool names and this makes it testable); and TOP-LEVEL schema_version, which the cycle-1 enumeration missed entirely. If a future template adds a path not named here, it is STILL COVERED - that is the whole difference between this rule and the list it replaces.
ONE ADDITIONAL ASSERTION ON TOP OF PARITY: for every features.* leaf, assert NO TRUE-TO-FALSE FLIP specifically, in addition to value equality. Plain equality already fails a flipped flag, but the dedicated assertion makes the DIAGNOSTIC name the real hazard - a flag is a capability claim, and a silently downgraded flag disarms a gate rather than merely diverging.
DIRECTORY - CONTRADICTION RESOLVED (cycle 2): cycle 1's enumeration listed `directory` under value equality while H3b listed it as override-eligible, so the two clauses disagreed about the same field and an implementer had to guess. `directory` IS OVERRIDE-ELIGIBLE - it encodes where THIS MACHINE keeps the backlog root (this workspace uses the legacy .backlogit root while new installs default to .backlog), which is exactly the machine-local class H3b exists for. It is exempted by the allow-list below and is NOT asserted for equality.
BINDING H3b - THE PERMITTED WORKSPACE-OVERRIDE LIST IS EXPLICIT, ENUMERATED AND CLOSED. Value equality is useless if "workspace customization" is an open-ended excuse, and H2's P0 concern (blind regeneration destroying deliberate local customization) is real. Reconcile the two with an ALLOW-LIST OF OVERRIDE-ELIGIBLE FIELDS DECLARED IN THE TEST ITSELF. OVERRIDE-ELIGIBLE (installed MAY differ from template; the test reports the delta as INFO and PASSES): mcp_server.command, mcp_server.transport, cli.binary, and directory - the four fields that legitimately encode where THIS MACHINE finds the tool. NOT OVERRIDE-ELIGIBLE (installed MUST equal template; any difference FAILS): everything else in the value-equality list above. A field is override-eligible ONLY by appearing in that enumerated list; an unlisted difference is a FAILURE, never a tolerated customization - so widening the exemption becomes a VISIBLE EDIT to the allow-list under review, which is exactly the property H2's halt-for-review rule wants and cannot provide on its own once 157.001-T has finished. ASSERT THE ALLOW-LIST ITSELF: a fixture adding an unlisted differing field MUST FAIL, and a fixture differing only in an override-eligible field MUST PASS, so an accidental "allow everything" regression is caught in both directions. PLAN REVIEW FINDING 3 (P1, partially accepted): this converts the symptom into a DETECTED condition, which is the honest fix available inside this scope; diagnosing WHY the install/tune path emitted a truncated registry is a different contract surface, captured as compliant P-021 deferred entry CE441101 and explicitly not attempted here. The parity test guarantees the question cannot be forgotten because the next drift fails a test instead of passing silently.
