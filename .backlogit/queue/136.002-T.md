Sweep every YAML frontmatter block under docs/ for the same unquoted-colon hazard fixed in the preceding task, and quote each value found, preserving content verbatim.

SCOPE (narrow — read before sweeping)
This task owns exactly ONE hazard: a YAML frontmatter value written as an UNQUOTED PLAIN SCALAR whose text contains `: ` (colon followed by a space), which YAML then reads as a mapping key/value split. Nothing else.

METHOD
1. Parse each docs/**/*.md frontmatter block. A decode failure is a CANDIDATE, not a confirmed hit — a YAML decode error is NOT by itself evidence of this specific unquoted-colon hazard.
2. CONFIRM BEFORE EDITING: read the parser's reported error location (line/column) and the source line it points at, and verify that line is an unquoted plain scalar whose value contains `: `. Only a confirmed candidate is in scope for this task.
3. Correct a confirmed hit by quoting that value verbatim, and change nothing else.
4. Do not rely on a regex alone as ground truth — it both misses cases and produces false positives. Use a regex only to LOCATE the candidate line inside a file the parser has already flagged, never to DECIDE that a file is a hit.
5. ANY OTHER decode failure (tab indentation, duplicate key, malformed block scalar, unterminated quote, bad list or indentation, encoding fault, and so on) is OUT OF SCOPE. Leave that file byte-unmodified and capture it SEPARATELY as a deferred stash entry under P-021 C1, naming the file path, the parser error text, and the reported location. This is the same capture-only boundary the plan applies to newly surfaced docline findings.

ACCEPTANCE
- Every docs/**/*.md frontmatter block that fails to decode is triaged and given exactly ONE recorded disposition: (a) CONFIRMED unquoted-plain-scalar-containing-`: ` hazard, corrected by quoting only; or (b) OTHER decode failure, left unmodified and captured as a deferred stash entry under P-021 C1.
- Every file corrected under (a) decodes successfully after the change.
- Both counts — (a) corrected and (b) captured — are reported in the PR description. Zero additional (a) files beyond the preceding task is a legitimate outcome, and so is zero (b).
- Only quoting changes. No semantic edits to any frontmatter value. No file classified (b) is modified by this task.
- Historical records under docs/closure/ and docs/memory/ are corrected ONLY if they genuinely fail to decode AND that failure is confirmed under (a), and then only by quoting — never by rewording. These are immutable records of what was decided and done.
- If any (b) file exists, state so explicitly in the report and note that the 136.003-T regression guard cannot pass repo-wide until those separately captured findings are resolved. Do NOT absorb a (b) file into this task to make that guard green.

ADVISORY (from plan review)
If the sweep turns up more than a handful of files, report the count and confirm the change remains quoting-only before proceeding.
