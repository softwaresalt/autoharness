Surface deterministic predecessor provenance and the migration surfaces in `pipeline-topology` CLI output so operators and agents can audit WHY a shipment is claimable or blocked.

DELIVERABLES:
1. `--json` output exposes `predecessor_source` (one of `explicit` / `declared_root` / `genesis` / `unsequenced`) and the selected predecessor IDs on the `shipment_readiness` check, on BLOCKED and PASSED paths alike.
2. Human-readable output states the provenance alongside the outcome.
3. UNSEQUENCED_SHIPMENT rendering NAMES BOTH REMEDIES explicitly (record the real `blocks` edge, or declare the shipment a root). An operator reading only CLI output must be able to resolve the block without reading the source — a block with no visible exit is the deadlock defect this design corrects. Where the engine reports WHY genesis did not apply, render that too: under the SOLE-RECORD rule (PR review-fix cycle 2, thread PRRT_kwDORzpWpM6h3frF) the disqualifier is "another shipment record exists in this workspace", so the rendering NAMES the disqualifying record(s) — id, whether live or archived, and the status AS READ (including `blocked`, and including a status reported as missing/unrecognized, which disqualifies fail-closed). An operator in a workspace that has never shipped must be able to see WHICH record denied genesis, not merely that genesis was denied. Do NOT render the retired G2/G3/G4 probe labels.
4. `--phase audit_sequencing` output (165.003-T) renders readably in both JSON and human modes. THIS IS PURE AUDIT OUTPUT (review-fix cycle 3, finding 9): the rendering reads the in-memory audit report and prints it. It does NOT render, reference, link to, or imply a durable ledger, a persisted audit artifact, or a future-remediation record — because 165.003-T emits none. Any wording implying the audit run leaves a durable trace is a defect in this task.
5. Assertions added in `tests/test_gate_pipeline_topology_cli.py` covering each provenance value, the remedy text, the disqualifier text, and the audit rendering.

AUDIT-RENDER PURITY IS SCOPED, NOT ABSOLUTE (PR review-fix cycle 2, staging PR #448, thread PRRT_kwDORzpWpM6h3frY — the finding is VALID and ACCEPTED). The cycle-1 deliverable 5 reintroduced an absolute ZERO-WRITE assertion here — "an assertion that the audit render path performs NO WRITE — no file created, no record mutated" — the EXACT claim that PR review-fix cycle 1 had already retracted from 165.003-T, 165-F, 165.008-T, and 165.009-T on thread PRRT_kwDORzpWpM6h3Tgi. It is FALSE BY CONSTRUCTION for the same verified reason: `_gate_pipeline_topology_command` (src/autoharness/cli.py) calls `_emit_pipeline_topology_telemetry` UNCONDITIONALLY on EVERY run of EVERY phase, appending a structured tool-telemetry event to the workspace telemetry journal whenever telemetry is enabled in the workspace config. An `audit_sequencing` render is such a run. A test encoding "no file is created" would FAIL on any telemetry-enabled workspace, or — far worse — would drive an implementer to SUPPRESS telemetry for this one phase, breaking parity with `pre_claim`, `post_claim`, `lifecycle`, and `ambient` in order to satisfy a claim that was never true. THE ABSOLUTE ASSERTION IS REMOVED.
REQUIRED INSTEAD — assert exactly what 165.003-T's contract states, no more:
  a. NO BACKLOG MUTATION — no item, feature, shipment, manifest, status, label, or dependency write occurs on the audit render path.
  b. NO MIGRATION-STATE OR LEDGER WRITE — no durable migration record, persisted audit artifact, state file, or new file format is created anywhere by the render.
  c. TELEMETRY IS EXPLICITLY ALLOWED AND POSITIVELY TESTED — with telemetry ENABLED, assert the ordinary `pipeline-topology` telemetry event IS EMITTED for the audit render, and that the rendered output and the exit code are IDENTICAL to a telemetry-DISABLED run. The emission is OBSERVATIONAL ONLY and pre-existing; this task adds no new field, journal, or emission site.
  d. FAIL-OPEN IS PRESERVED — assert that a telemetry failure during an audit render changes NEITHER the rendered output NOR the exit code. Do not narrow, harden, or make load-bearing the existing `except Exception` fail-open handler.
DO NOT ASSERT "zero filesystem writes", "no file created", or "nothing is written". Any future edit to this task that reintroduces an absolute no-write claim is a regression of this finding.

DEPENDENCY CORRECTION (review-fix cycle 2, finding 4; RETAINED in cycle 3 per finding 9): this task depends on 165.003-T AS WELL AS 165.002-T. Deliverable 4 renders the `audit_sequencing` output that 165.003-T produces — it CONSUMES that task's output surface. The cycle-1 edge set omitted it, which would have permitted this task to start (and its audit-rendering assertions to be authored) against a phase that does not yet exist. Removing the ledger (cycle 3, finding 2) does NOT weaken this edge: 165.003-T still defines the audit REPORT SHAPE that this task renders, so the producer/consumer ordering stands unchanged. 165.002-T supplies `predecessor_source` for deliverables 1-3; 165.003-T supplies the audit report payload for deliverable 4.

HARDENING H4: output changes must be ADDITIVE so existing agent consumers do not break. Do NOT rename or remove existing fields.
