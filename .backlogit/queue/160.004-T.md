ONE RESOLVED RULE PER PATH PER CHANNEL, UNDER PLAN AC11'S DETERMINISTIC RESOLUTION MODEL (cycle 8, item 6). THE ALGORITHM: (1) REMOVE declared `generated_output_roots` from the input domain BEFORE any matching - those paths are never classified and MUST NOT carry a channel include or exclude rule; (2) build the CANDIDATE SET of every rule whose pattern matches the remaining path; (3) ZERO candidates FAILS CLOSED as unclassified; (4) select the MOST SPECIFIC candidate by the plan's declared ordering - exact literal beats longer literal prefix before the first wildcard, which beats fewer wildcard segments - computed FROM PATTERN TEXT ALONE and therefore INDEPENDENT OF RULE ORDER IN THE FILE; (5) an EQUAL-SPECIFICITY TIE FAILS CLOSED as genuinely ambiguous. THE WITHDRAWN RULE - "fail on a path matching MORE THAN ONE rule ... RULE PRECEDENCE MUST NOT BE USED" - IS DELETED AS FALSE, not softened: the AC11 table intentionally contains six broad-parent/explicit-descendant pairs, so a raw match-count check would have rejected this shipment's own manifest on its first run. THE REPLACEMENT IS NOT FILE-ORDER PRECEDENCE, which was rightly rejected because it hides the losing match: specificity is a PROPERTY OF THE PATTERNS, the FULL CANDIDATE SET IS REPORTED alongside the selected rule, and a tie is a HARD FAILURE rather than a silent win. Reordering the manifest can never change a classification. This resolver is the single implementation of that model; T4/T5/T6/T8 assert against it WITHOUT ADDING ANY TEST ROW.
- TYPED INJECTABLE SEAMS (added in cycle 6, finding 8). The resolver's entry point takes TWO injectable parameters, both DEFAULTING to the real repository:
    repo_root: Path                                        # defaults to the discovered repository root
    tracked_paths: Callable[[], Iterable[str]] | Iterable[str]   # defaults to real `git ls-files` enumeration
  WHY THIS IS REQUIRED: test_unclassified_tracked_path_fails_build (the V4 negative case) must present the resolver with a SYNTHETIC UNCLASSIFIED TRACKED PATH. With no seam, the only way to do that is to CREATE AND STAGE A FILE IN THE REAL GIT INDEX, which mutates the developer's working tree, is order-dependent against every other test, and can leave the index dirty when the test fails midway. With the seam, the case injects the synthetic path through the provider and NEVER TOUCHES THE REAL INDEX. THE DEFAULT PATH IS UNCHANGED: production callers pass nothing and get real git enumeration rooted at the real repository, so the seam adds a test affordance without adding a second behaviour.
- TRACKED-NESS IS EVALUATED AGAINST THE TREE UNDER TEST (cycle 6, finding 10): `git ls-files --error-unmatch -- <path>` against the working tree/index the run executes in, or `git cat-file -e <rev>:<path>` when a specific commit must be interrogated. There is NO `git ls-files at <commit>` operation and that wording must not appear. 160.001-T's baseline is a BYTE/OUTCOME COMPARISON REFERENCE ONLY, never the source of truth for present tracked-ness.
- PATH NORMALIZATION HAPPENS ONCE, HERE, AT THE RESOLVER BOUNDARY (cycle 6, finding 17): every path crossing out of the resolver is a forward-slash POSIX-style string (PurePosixPath), so no downstream render site needs its own normalization and a Windows run and a POSIX run resolve identically.
- Report measured file count and byte size per channel (AC8).

GENERATED-OUTPUT-ROOT SELF-EXCLUSION LIVES IN THE RESOLVER, NOT THE GENERATOR (AC3d, binding). The manifest declares `generated_output_roots` - per channel, the directory the resolved payload is MATERIALIZED INTO (`plugin-payload/` for the plugin channel). BEFORE any classification runs, the resolver REMOVES every path under every declared output root from the tracked-path enumeration. Consequences the implementation must honour:
1. The removal is UNCONDITIONAL and applies to BOTH IN-SCOPE CHANNELS, so the plugin generator can never read its own output and the wheel never picks the tree up as source.
2. Removed paths are NEITHER classified NOR unclassified, so the AC2 unclassified-path failure is not triggered by generated content.
3. `generated_output_roots` is a DISTINCT key from `include`/`exclude`. The resolver must never treat an output root as an include rule and must never rely on rule ORDERING to make the exclusion "win".
4. THE EXCLUSION MUST NOT BE IMPLEMENTED INSIDE THE GENERATION COMMAND. Every other consumer of this resolver - the AC2 classification check, the per-channel size report, `--check` - would otherwise still see the output tree as input, and only the generator would be protected. The resolver is the single choke point.
WHY THIS MATTERS: if `plugin-payload/**` were an `include` rule, run two would resolve it as source and write it INSIDE `plugin-payload/`, producing `plugin-payload/plugin-payload/...`, and every further run would nest again - drift that regenerating can never clear, failing the release gate permanently. Exclusion from classifier INPUT does not affect PUBLICATION: `plugin-payload/` stays tracked, committed, and the `marketplace.json` `source` target (AC3c).

GENERATION COMMAND IS A SEPARATE TASK: hardening decision H1 makes the static `pyproject.toml` include tables and the `marketplace.json` payload declaration DERIVED artifacts. The single deterministic command that generates and drift-checks them - `python -m build_support.payload generate --channel {wheel|plugin|all}` and its `--check` mode, where `all` means both in-scope channels - is delivered by 160.014-T, which CONSUMES this resolver. Keep the resolver's public surface stable and importable so that command can build on it; do NOT implement the generation/serialization path here (it would push this task past the 2-hour rule and mix resolution with codegen). This task delivers the RESOLVER; 160.014-T delivers the GENERATION COMMAND.
