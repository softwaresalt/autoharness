title: Resolve tool-scoped template branches against the branch declared tool with fail-closed binding
updated_at: 2026-09-03T09:13:55.5735521Z

Skill templates use generic {{OP_CREATE_MCP}}/{{STATUS_*}} variables INSIDE branches explicitly scoped to a non-active backlog tool, so a branch introduced by "When backlog-md is the installed backlog tool" renders BACKLOGIT values whenever backlogit is active - wrong in every workspace it appears in. Note the coupling: decision D3 selected keep-but-demote, so option (a) "eliminate the second tool and the trap disappears" is NOT available and the real fix is required here. SELECTED SHAPE (B): make the tool-scoped branch a block the installer resolves per tool, so generic tokens inside it bind to that block's tool. REJECTED (A) per-tool tokens: multiplies the variable table by the number of tools and every new token is a new unresolved-placeholder opportunity; and using the wrong token would be indistinguishable from the right one, whereas an unbound block is a structural error the renderer can reject. BINDING H1: FAIL CLOSED on an unbound tool-scoped block - a block declaring no tool, or a tool the registry set does not contain, must ERROR rather than fall back to the active tool. Silent fallback is the present defect. BINDING H2: no unresolved {{ may survive for EVERY supported tool binding, not only the active one. BINDING H3: templates without tool-scoped blocks must render byte-identically before and after; whole-corpus render diff is the acceptance evidence. BINDING H6 - REGISTRY TOOL NAMES ARE DERIVED DYNAMICALLY, NEVER HARDCODED (PROMOTED IN CYCLE 2 FROM DE-RISKING NOTE TO EXECUTABLE ACCEPTANCE; three sub-requirements, all MANDATORY): (H6a) DYNAMIC DERIVATION AT CHECK TIME - the set of valid tool names the binding validation resolves against MUST be DERIVED AT CHECK TIME from the installed backlog registry set (each registry's declared tool_name). It MUST NOT be a hardcoded literal list, a constant, an enum, a default, or a baked-in fallback anywhere in the renderer, the templates, or the tests - not even "backlogit, backlog-md, manual" as a convenience default. The names cited in this run's analysis are ILLUSTRATIVE OBSERVATIONS OF THE CURRENT SET, never the contract: hardcoding them would silently reject a validly installed fourth registry and would reintroduce exactly the static-assumption class this shipment exists to remove. ASSERT IT: a test that adds a synthetic registry with a NEW tool_name and asserts a block declaring that tool RESOLVES SUCCESSFULLY with no renderer, template, or test edit. (H6a-CLARIFICATION, added in Orchestrator review-fix cycle 1, finding 12 - the no-hardcoding rule and the block-declares-a-tool rule are NOT in conflict, and an implementer must not read H6a as forbidding H1): the no-hardcoding prohibition governs the VALIDATION SET ONLY - the set of names a tool-scoped block is checked AGAINST - and NEVER the block DECLARATION itself. A tool-scoped block is a DECLARATIVE IDENTITY: it exists precisely to say "this content belongs to tool X", so writing a concrete supported tool name INSIDE the block header (for example a block introduced by "When backlog-md is the installed backlog tool") is REQUIRED, is the datum being validated, and is explicitly permitted. What is forbidden is the renderer/test/template carrying a SECOND, DUPLICATED copy of the tool-name universe used to decide whether that declaration is legal; that universe MUST be derived at check time from the installed registry set. Restated as the operative rule: ONE authored occurrence of a tool name per block header (the declaration) is correct; ZERO authored occurrences of the valid-name LIST anywhere in renderer, template, or test fixtures is required. The H6a synthetic-registry test discriminates the two directly - it adds a new tool_name and a block declaring it, and the block must resolve with no edit; a duplicated validation list fails that test, while the block header naming a tool cannot. (H6b) FEATURE-FLAG BINDING IS FORBIDDEN - the validation binds to TOOL IDENTITY ONLY. It MUST NOT read, resolve, validate against, or branch on any registry FEATURE FLAG (features.*, e.g. sizing, shipments, stash). This is what keeps SHIP-6 ORDER-INDEPENDENT of SHIP-7: SHIP-7 changes feature flags and registry contents but does not change tool identity, so a tool-identity-only check cannot be perturbed by SHIP-7 landing after SHIP-6. ASSERT IT: a test that mutates a registry's feature flags and asserts the tool-scoped block resolution is BYTE-IDENTICAL before and after. (H6c) FAIL CLOSED ON NESTED CONDITIONAL BLOCKS - exactly ONE level of tool-scoped block is supported. A tool-scoped block appearing INSIDE another tool-scoped block, or any other nested conditional construct, MUST be a HARD RENDER ERROR naming the file and the offending nesting, never silently flattened, never resolved against the innermost or outermost tool, and never partially rendered. Nesting is ambiguous by construction and an ambiguous resolution is the defect class this task removes. ASSERT IT: a negative test with a deliberately nested block asserting a non-zero, named render error. BINDING H2 (renderer bound, preserved): exactly ONE new construct - no general templating language, no expression evaluation, no nesting beyond the single supported level (see H6c). Pure lookup against the dynamically derived registry-name table; no eval, no shell, no path resolution from template content (finding 7). PLAN REVIEW FINDING 3 (P1): assert parity on NORMALIZED output (trailing-whitespace and line-ending normalized) and ENUMERATE the templates covered, so an intentional change is a visible edit to that enumeration rather than a silent relaxation. SCOPE BOUND: fix the MECHANISM and convert only branches that currently render wrong; a branch that renders correctly today is left alone. Update template-authoring guidance where this pattern is documented (finding 5). SEQUENCING: BLOCKED BY 156.003-T, the de-risking prerequisite, which records the renderer's current construct set, the tool-scoped-branch template inventory, the registry tool-name set, and the baseline corpus render. ACCEPTANCE: H1 fail-closed binding implemented; H6a, H6b and H6c each covered by the named assertion above and all passing; H2/H3 parity evidence produced on normalized output over the enumerated corpus; no hardcoded tool-name literal anywhere in renderer, template, or test fixtures.
