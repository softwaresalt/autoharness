Make AC2's fail-closed promise ENFORCEABLE IN THE ACTUAL RELEASE PATH (T14) by adding an unbypassable payload-composition gate to `.github/workflows/release.yml`.

WHY THIS EXISTS: AC2 promises that an unclassified tracked path FAILS THE BUILD. Hardening decision H1 chose "generated-and-asserted", which means the guarantee lives in a TEST. A test that nothing in the release path is required to run is not a gate - it is a hope. Without this task, a release could be built and published with the composition suite never executed, which is precisely the failure mode that produced the current untrimmed payload.

WHY IT IS A SEPARATE TASK (width isolation): editing a CI workflow is a different surface with a different blast radius and a different diagnosis path than editing packaging config. Folding it into the wheel-wiring task (160.006-T) would mix CI work with packaging work and push that task past the 2-hour rule.

WORKFLOW SHAPE AS IT ACTUALLY EXISTS: `.github/workflows/release.yml` has exactly ONE job (`release`). A separate gating job with a `needs:` edge is therefore NOT available without restructuring the workflow, and restructuring is OUT OF SCOPE for this shipment. The unbypassable form in a single-job workflow is an IN-JOB PREREQUISITE STEP.

DELIVERABLE:
- Add a payload-composition gate step to the `release` job that runs the composition test suite AND `python -m build_support.payload generate --channel all --check` (the command delivered by 160.014-T), where `all` means wheel AND sdist AND plugin.
- The step MUST be ordered BEFORE the build step and BEFORE the publish step.
- The step MUST NOT carry `continue-on-error: true`.
- The step MUST NOT carry any `if:` expression that can skip it - no `if: always()`, no `if: success() || ...`, no workflow_dispatch bypass input.
- A failing gate therefore fails the job before anything is built or published.

THE GATE MUST COVER ALL THREE CHANNELS. `uv build` produces the wheel AND the sdist in one step, and both are published - to PyPI and, via `dist/*`, to the GitHub release. A gate that validates only the wheel and the plugin leaves the sdist - the channel that currently discloses the entire excluded set - completely ungated.

ORDERING IS PART OF THE CONTRACT, NOT A DETAIL: gating after `uv build` would let a bad artifact be built, and gating after publish is not a gate at all.

GREEN RESPONSIBILITY - two RED-FIRST cases authored by 160.005-T:
1. test_release_workflow_runs_payload_gate_before_publish (AC2b). Parse release.yml STRUCTURALLY (not by regex over raw text) and assert: (i) a payload-composition gate step exists in the `release` job; (ii) its step index is strictly LESS than the build step index AND strictly less than the publish step index; (iii) it carries no `continue-on-error: true`; (iv) it carries no `if:` expression at all. A later edit that reorders, conditions, or soft-fails the step is then caught by the test suite rather than discovered at publish time.
2. test_release_gate_covers_all_three_channels (AC2b, AC3b). Assert the gate's channel argument resolves to wheel AND sdist AND plugin. A gate covering two of three channels is not a gate for the third.

NON-REGRESSION TEST: assert that the set of workflow triggers, the `permissions:` block, every secret reference, and every pinned action SHA is BYTE-IDENTICAL before and after this change. The gate step is an addition; nothing else in the release workflow may move.

DEPENDENCIES: blocked by 160.006-T (wheel wiring), 160.019-T (sdist wiring) and 160.007-T (plugin wiring). Gating a channel whose build table has not yet been wired to the manifest would make the gate fail for a reason unrelated to any defect it exists to catch.

FORWARD NOTE (not a deliverable): if a future change splits release.yml into multiple jobs, the gate should migrate to a separate job with a `needs:` edge. That restructuring is explicitly NOT part of this shipment; the in-job prerequisite is the correct enforceable form for the workflow as it exists today.
