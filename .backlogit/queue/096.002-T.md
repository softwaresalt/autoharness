Fix the deploy wrappers so pack selection honors the opt-in reclassification. `default_in_preset: []` alone does NOT stop a default deploy from writing agent-intercom, because the wrappers default OMITTED pack input to "all" and enumerate EVERY registry pack for non-starter presets, ignoring default_in_preset.

Apply the SAME logic change to ALL FOUR mirrored files (dogfood output + product templates), or rendering/parity tests in tests/test_deploy_harness_scripts.py will fail:
- scripts/deploy-harness.ps1  (param default `[string]$Packs = "all"`, scaffold branch ~L258-269, Get-RegistryPacks ~L118)
- scripts/deploy-harness.sh   (`PACKS="all"`, scaffold branch ~L214-225, registry_packs ~L118)
- templates/scripts/deploy-harness.ps1.tmpl  (mirror)
- templates/scripts/deploy-harness.sh.tmpl   (mirror)

## Pack-selection precedence contract (uniform across ALL presets, including starter)

Evaluate in this exact order. This is the single authoritative rule; there is no preset that unconditionally forces an empty pack set:

1. EXPLICIT pack input is ALWAYS honored, regardless of preset.
   - `--packs all` / `-Packs all` = every registry pack (including agent-intercom).
   - An explicit subset = exactly those packs (validated against the registry).
   - `starter` MUST NOT discard an explicit selection. This mirrors the installer contract (`.github/skills/install-harness/SKILL.md:551`: "If capability_packs input is provided explicitly, use it as-is regardless of preset") and FIXES the recorded defect in `docs/memory/082-S-closure.md:72` (FU-1: explicit `--packs`/`-Packs` subset was overridden when `--preset starter` was selected).
2. OMITTED pack input resolves to the SELECTED preset's `default_in_preset` members:
   - `full` / `standard` -> their default_in_preset packs (agent-intercom is NOT among them, because its default_in_preset is []).
   - `starter` -> empty (no pack lists "starter" in default_in_preset).

Note the fix from the pre-existing behavior: `starter` becomes empty ONLY when pack input is omitted (rule 2), never when packs are supplied explicitly (rule 1).

## Implementation requirements
- Distinguish an OMITTED pack input from an EXPLICIT `all` by changing the default sentinel (e.g. empty/`preset`) so omission is detectable rather than pre-set to "all".
- Teach the registry enumerators (Get-RegistryPacks / registry_packs) to parse `default_in_preset` (they currently read only `- id:` lines) with a deterministic line scan (no YAML module dependency), preserving the existing style.
- Apply identical logic to all 4 mirrored files.

## Acceptance criteria
- EXPLICIT input honored on EVERY preset, including starter:
  - starter + explicit `all` -> every registry pack selected (agent-intercom included).
  - starter + explicit subset -> exactly that subset (no dropping of explicit selections — fixes 082-S FU-1).
  - full/standard + explicit `all` -> every registry pack selected (agent-intercom included).
- OMITTED input resolves to preset defaults:
  - omitted + full -> full default_in_preset members only; agent-intercom excluded.
  - omitted + standard -> standard default_in_preset members only; agent-intercom excluded.
  - omitted + starter -> no packs selected.
- Identical logic present in all 4 files; tests/test_deploy_harness_scripts.py parity/rendering tests still pass.
- Enumerators parse default_in_preset via line scan with no new runtime dependency.
- Wrapper behavior matches install-harness precedence semantics (SKILL.md:551).
