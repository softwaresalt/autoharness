DELIVERABLES
1. New subcommand: `autoharness gate closure-evidence --path <file> [--shipment <id>] [--workspace <path>] [--json]`. Added as ONE additional branch in the flat dispatcher at cli.py:369-389, plus its usage/help block alongside the existing pipeline-topology / dag-readiness blocks.
2. Validation, in order, each failure naming the offending field or path:
   (a) the filename matches the CANONICAL WRITE pattern from 167.001-T. A LEGACY-named artifact is a WRITE-TIME FAILURE — recognition is read-side only (D3), and without a write-side failure, read tolerance would silently become permission and the canonical pattern would decay into a suggestion (plan decision P-D4).
   (b) required frontmatter keys `closure_status` and `compaction_status` are present with permitted values.
   (c) the artifact is discoverable for its declared shipment via classify_closure_candidates.
3. Exit codes follow the established gate convention: 0 pass, 1 validation failure, 2 invalid input.

WHY WRITE-TIME (D6, source-report criterion 3)
This moves failure from a SUCCESSOR SHIPMENT'S PRE-CLAIM GATE (weeks later, with no context) back to the author's keyboard, while they still have full context. Every one of the six historical occurrences was discovered at the successor's gate.

SCOPE GUARD
Validation ONLY. This command NEVER writes, renames, or repairs an artifact (D8). It is NOT wired into any pre-existing gate path, so it cannot change the behaviour of `gate check`, `gate pipeline-topology`, or `gate dag-readiness`.

TESTS (4)
1. Canonical filename + valid frontmatter passes with exit 0.
2. Legacy filename fails with exit 1 and the canonical pattern quoted in the message.
3. Missing `closure_status` fails with exit 1 naming that field.
4. An unparseable/absent path exits 2.

ACCEPTANCE
