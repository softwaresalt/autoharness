Monitor the unattended release workflow, capture published-package smoke evidence, and execute the correct rollback branch if it fails.

MONITORING SIGNALS (record the conclusion of each, in order) — .github/workflows/release.yml:
1. Validate tag matches pyproject version (L26-L45)
2. Extract changelog for this version (L47-L67) — must yield NON-EMPTY notes
3. uv build (L77)
4. uvx twine check dist/* (L80)
5. Check PyPI pre-publish state (L82-L107)
6. Publish distribution to PyPI (L109-L112, pypa/gh-action-pypi-publish SHA-pinned @cef221092ed1bacb1cc03d23a2d87d1d172e277b, skip-existing: true)
7. Smoke test published package from PyPI (L114-L138)
8. Create/update GitHub Release

PUBLISHED-PACKAGE SMOKE EVIDENCE (capture, do not just observe):
- uv tool run --isolated --no-config --from "autoharness==1.5.0" autoharness version  -> must equal EXACTLY "1.5.0"
- uv tool run --isolated --no-config --from "autoharness==1.5.0" autoharness home     -> must resolve
- Record the PyPI project page URL and the GitHub Release URL as closure evidence.

VALIDATION WINDOW: the workflow polls PyPI for up to 280 SECONDS (L127). Allow the FULL window before declaring failure. Slow PyPI/CDN propagation is NOT a publish failure and must NOT trigger rollback.

*** WHAT THIS TASK CANNOT ENFORCE (corrected after PR #422 review) ***
The pre-publish probe at L94-L107 FAILS OPEN: when 1.5.0 already exists it merely PRINTS "already on PyPI; publish will skip existing files on reruns" and EXITS 0. The publisher then runs with skip-existing: true, the smoke test passes against the PRE-EXISTING package, and a GitHub Release is created/updated around artifacts this build did not produce — the whole run reports SUCCESS.
Because the workflow is UNATTENDED, there is NO point at which monitoring can interrupt it between the probe and the release. This STOP therefore CANNOT be enforced here. It is enforced as a PRE-TAG assertion in 150.009-T (assertion 5), and permanent workflow hardening is deferred to stash 8E10B13B. Do not treat observation of this step as a gate.

*** ROLLBACK — DETERMINE ACTUAL UPLOAD STATE; DO NOT INFER IT FROM THE FAILED STEP NUMBER ***
Steps 6-8 are NOT uniformly post-upload. The publish action can fail on authentication/OIDC BEFORE any file reaches PyPI. Choosing the irreversible branch from the step number alone can needlessly burn 1.5.0.

ON ANY FAILURE AT OR AFTER STEP 6, FIRST PROBE:
  https://pypi.org/pypi/autoharness/1.5.0/json
- 404 (ABSENT) -> nothing was uploaded. SAFE PATH: delete the tag (git push --delete origin v1.5.0), fix, re-tag. NO version burned. Tag deletion requires operator confirmation.
- 200 (PRESENT) -> version is permanently consumed. DO NOT retry 1.5.0. DO NOT delete the tag — deleting does NOT unpublish and creates misleading history. ESCALATE. Remediation ships as 1.5.1.
- AMBIGUOUS / UNREACHABLE -> FAIL CLOSED: assume consumed, escalate, do NOT re-tag 1.5.0.

FAILED BEFORE step 6 (steps 1-5): SAFE. Delete the tag, fix, re-tag. No version burned.

Published smoke test fails AFTER a confirmed successful publish -> do NOT yank reflexively; capture evidence, escalate, prepare 1.5.1.

ALSO: confirm the PyPI publish credential / OIDC trusted-publishing configuration is in place when reviewing the workflow (plan-review P2-1). A bad credential fails before upload, so no version is burned — and it is exactly the case the probe-first rollback rule above is designed to handle correctly.
