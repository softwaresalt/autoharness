# Windows temp-directory teardown failure in the capability-pack enforcement verifier test — test-only bounded-retry repair

## Problem Frame

<!-- BEGIN:problem-frame -->
After the authorized test-only synchronization repair 183.001-T landed as 622a41a1, the canonical suite (PYTHONPATH=src python -m unittest discover -s tests) failed TWICE at tests/test_capability_pack_enforcement_verifier.py::CapabilityPackEnforcementVerifierTests::test_orphaned_manifest_entry_without_pack_fails. Both failures are located in tempfile.TemporaryDirectory.__exit__ -> shutil.rmtree with PermissionError [WinError 32] (file in use by another process) / [WinError 5] (access denied) — NOT in any assertion. The test body itself passes; only the context manager's teardown raises.

Mechanism: the module-level _run() helper (tests/test_capability_pack_enforcement_verifier.py line ~114) wraps the entire fixture-build + verify_workspace() call in `with tempfile.TemporaryDirectory() as temp_dir:`. On Windows, a directory tree cannot be removed while any handle to a file inside it is still open, and handle release after close is not instantaneous (antivirus/indexer scanning and delayed-close semantics both widen the window). shutil.rmtree therefore raises rather than retrying.

Two candidate root causes were distinguished before deciding: (A) a production file-handle leak in the verifier — src/autoharness/verify_workspace.py leaving a manifest/config/instruction reader open past the targeted capability_pack_enforcement check; or (B) a test-harness teardown race with no production defect. A read-only concurrency review found NO production verifier handle leak on the exercised path, which selects (B) and makes the repair TEST-ONLY.

Question for this deliberation: is this one bounded test-only work unit, and what exactly may the repair touch?
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
OPTION 1 (REJECTED) — Fix it inside the 183.001-T / 189-S fix cycle that discovered it. Rejected under P-021 C1/C4: the authorized change was one test function's readiness synchronization in a DIFFERENT module (tests/test_graphtor_mcp_shim.py). "Same suite", "same verification gate", "same PR" are explicitly NOT scope tests (C1 worked discrimination (b)). C4 states no authorization — including explicit operator authorization — retroactively widens the discovering cycle. Doing this would be a C7 violation.

OPTION 2 (REJECTED) — Modify the production verifier to close handles more eagerly. Rejected on evidence: the read-only concurrency review found no production handle leak on the exercised path. Changing production code to chase a test-harness teardown race would be an unevidenced production mutation with real blast radius on a shipped verification gate.

OPTION 3 (REJECTED) — shutil.rmtree(ignore_errors=True) or TemporaryDirectory(ignore_cleanup_errors=True). Rejected on principle and on precedent: it converts a real, reproducible defect into invisible residue, permanently suppresses the WinError 5 access-denied signal (which is NOT the benign sharing-violation case and may indicate a genuine permissions or leaked-handle defect), and leaks temp trees into the OS temp area every run. The sibling stash entry 8CB606F8 records this exact anti-pattern already present in tests/test_graphtor_mcp_shim.py tearDown as a defect in its own right — adopting it here would spread it.

OPTION 4 (REJECTED) — Relocate the fixture under .autoharness/staging/tmp/ per the 2026-09-15 flat-manifest-closure decision D7b containment rule. Rejected as OUT OF SCOPE for this unit and recorded as an open question instead: it is a containment/policy change, not a teardown-race repair, and it would not by itself stop a rmtree from raising on a still-open handle. Noted for a future containment-scoped unit.

OPTION 5 (SELECTED) — Test-only bounded retry at the teardown site in tests/test_capability_pack_enforcement_verifier.py: catch PermissionError whose winerror is 32 or 5, retry removal a small fixed number of times with a short bounded backoff, and RE-RAISE the final exception once the bound is exhausted. No ignore-cleanup-errors, no ignore_errors, no production change, no other file touched.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
OPTION 5 — a test-only, bounded, re-raising retry around the temp-workspace teardown in tests/test_capability_pack_enforcement_verifier.py, promoted as its own minimum work unit (one covering feature, one task, one shipment), SEPARATE from both the discovering 183.001-T/189-S unit and from the Graphtor tearDown leak captured as stash 8CB606F8.

Rationale:
1. P-021 C1 classifies this OUT of scope for the discovering fix cycle (different module, different contract surface), so it MUST become a separate unit; C6 requires this deliberation before any planning, which this artifact discharges.
2. The concurrency review's negative finding (no production verifier handle leak) is what authorizes a test-only repair and simultaneously PROHIBITS production mutation under this unit.
3. Bounded + re-raising is the only variant that fixes the flake without destroying the signal: a transient Windows sharing violation is absorbed, while a persistent handle leak still fails the suite loudly. ignore-cleanup-errors would be indistinguishable from a passing run.
4. Both WinError 32 and WinError 5 are retried because the observed evidence includes both codes, but the retry is narrowed to PermissionError with those two winerror values so unrelated OSErrors still propagate immediately.

BLAST RADIUS: one test module, teardown path only, no assertion changes, no production code, no schema, no CLI, no template. Plan hardening (P-006): NOT REQUIRED — single test file, test-only, no elevated-blast-radius signal (no schema, no CLI distribution, no multi-template-family surface). Lightweight depth is proportionate; a full impl-plan/plan-harden cycle would exceed the work.

VERIFICATION ORDER (mandatory, exactly as directed, in order, after the code change):
(1) the exact test — tests/test_capability_pack_enforcement_verifier.py::CapabilityPackEnforcementVerifierTests::test_orphaned_manifest_entry_without_pack_fails;
(2) the cross-test sequence pairing that module with the Graphtor shim module in one process, to exercise the suspected cross-module handle interaction;
(3) an explicit check that no relevant child process and no relevant temp directory linger after the run;

Step (2) exists precisely because 8CB606F8 is the leading hypothesis for the external handle pressure; if step (2) or (3) shows lingering processes/dirs, that is evidence the true cause is 8CB606F8's teardown leak and the task STOPS and returns the finding to Stage rather than widening the retry bound to mask it.

PROHIBITED under this unit: any change to src/ (notably src/autoharness/verify_workspace.py); ignore_cleanup_errors=True or shutil.rmtree(ignore_errors=True); an unbounded or swallowing retry; weakening/deleting/skipping any assertion; folding in the 8CB606F8 tearDown repair; touching any other test module; adding a `dir=Path.cwd()` anchor to TemporaryDirectory (tests/test_test_suite_isolation_contract.py guards against reintroducing that pattern under tests/, per the 149-S/141-F closure record).

## Open Questions

<!-- BEGIN:open-questions -->
1. UNPROVEN CAUSAL LINK: whether the Graphtor shim tearDown leak (stash 8CB606F8) is an actual contributing cause of the sharing violations here is a hypothesis, not a finding. Verification steps (2) and (3) are designed to produce evidence either way. A negative result does not block this repair.
2. WHY THIS TEST: test_orphaned_manifest_entry_without_pack_fails is the manifest-listed-but-file-absent path. Whether that specific path holds a handle marginally longer than its siblings, or whether it is simply the unlucky test in ordering, was not determined and is not required for the bounded-retry repair.
3. CONTAINMENT TENSION (deferred, not resolved here): docs/decisions/2026-09-15-flat-manifest-shipment-closure-deliberation.md D7b requires fixture workspaces to resolve under the repo-internal .autoharness/staging/tmp/ root rather than the OS temp area. This test uses a bare tempfile.TemporaryDirectory() in the OS temp area. Reconciling that is a separate containment-scoped unit; it is explicitly NOT authorized here, and the bounded-retry repair neither advances nor obstructs it.
4. SCOPE OF THE RETRY HELPER: whether the retry should later be generalized into a shared test helper for other TemporaryDirectory sites is deferred. This unit fixes the one observed site only; premature generalization would widen a bounded repair and touch modules with no observed defect.
5. RETRY BOUND VALUES: the exact attempt count and backoff are left to implementation within the "small and fixed" constraint; they are not a contract surface, but the bound MUST be finite and MUST end in a re-raise.
