Derive the tier and orchestrator route variables, handling the POLYMORPHIC `config.model_routing` shape.

**Plan:** `docs/plans/2026-08-21-verify-workspace-variable-derivation-plan.md` Task 1 (first half) + amendment B6

## Variables in scope (~13)
`MODEL_ROUTING_TIER1`, `MODEL_ROUTING_TIER2`, `MODEL_ROUTING_TIER3`, `TIER_1_FAMILY`, `TIER_1_PROVIDER`, `TIER_1_REASONING_EFFORT`, `TIER_2_FAMILY`, `TIER_2_PROVIDER`, `TIER_2_REASONING_EFFORT`, `TIER_3_FAMILY`, `TIER_3_PROVIDER`, `TIER_3_REASONING_EFFORT`, `ORCHESTRATOR_FAMILY`, `ORCHESTRATOR_PROVIDER`, `ORCHESTRATOR_REASONING_EFFORT`.

## THE CENTRAL DEFECT (amendment B6 — this is very likely the actual root cause)
`config.model_routing` is NOT a uniform mapping. In the live workspace:
```yaml
model_routing:
  tier1:                       # MAPPING
    model: "gpt-5.6-luna"
    model_family: "gpt-5.6-luna"
  tier2: "claude-sonnet-5"     # SCALAR STRING
  tier3: "claude-opus-5"       # SCALAR STRING
  orchestrator: "gpt-5.6-sol"  # SCALAR STRING
  stage: {...}                 # MAPPING
  ship: {...}                  # MAPPING
  escalation: {...}            # MAPPING
```
A derivation written against the mapping shape returns NOTHING for exactly the variables in the stash entry's evidence. **Normalisation rules** (SKILL.md rows 414–428 plus the prose rule at line 452 are authoritative; the scalar rule is **NOT uniform across route keys**):
- SCALAR form, TIER routes (`tier1`/`tier2`/`tier3`) → the value is the model identifier; it populates `MODEL_ROUTING_*` and `*_FAMILY`. `*_PROVIDER` and `*_REASONING_EFFORT` derive to the EMPTY STRING (SKILL.md rows 414–416: "all other tier sub-fields default to empty").
- SCALAR form, ORCHESTRATOR route → the value populates `ORCHESTRATOR_FAMILY` ONLY. `ORCHESTRATOR_PROVIDER` and `ORCHESTRATOR_REASONING_EFFORT` **fall back to `{{TIER_2_PROVIDER}}` / `{{TIER_2_REASONING_EFFORT}}`** — they do NOT derive to empty. SKILL.md rows 426–427 declare the Tier 2 fallback, and line 452 states it verbatim for the string form: "When `config.model_routing.orchestrator` is a plain string ... it is treated as the `model_family` value. The `reasoning_effort` and `model_provider` fields fall back to their tier2 equivalents." **Asymmetry to preserve:** `ORCHESTRATOR_FAMILY` itself does NOT fall back to tier2 — its own default is `gpt-5.4` (SKILL.md row 428). (Corrected in review-fix cycle 1: the original rule applied the tier-scalar empty-metadata behaviour to the orchestrator, which would empty exactly the variables this feature exists to fix, for the live `orchestrator: "gpt-5.6-sol"` config.)
- MAPPING form → each sub-field derives independently (`model`/`model_family`/`model_provider`/`reasoning_effort`), with the SAME per-field fallbacks above applied to any absent or empty sub-field.
