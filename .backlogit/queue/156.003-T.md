=== DELIVERABLE (3), CORRECTED IN REVIEW-FIX CYCLE 5 (FINDING 5) ===

WITHDRAWN WORDING: "the set of REGISTRY TOOL NAMES the fail-closed binding check will resolve against (measured: backlogit, backlog-md, manual)" is WITHDRAWN and MUST NOT be reintroduced. IT IS FACTUALLY WRONG AND WOULD FABRICATE A REGISTRY. MEASURED at HEAD: templates/backlog/registries/ contains EXACTLY TWO files - backlogit.registry.yaml (tool_name: "backlogit") and backlog-md.registry.yaml (tool_name: "backlog-md"). THERE IS NO manual.registry.yaml AND THERE IS NOT MEANT TO BE ONE. An implementer told that three names are "registry tool names" would either go looking for a third registry file and be blocked, or - the likelier and worse outcome - CREATE one, inventing a registry for a mode whose entire definition is that no registry exists. Either way the fail-closed check would be built on a false premise.

CORRECTED MODEL - TWO SOURCES, EACH WITH ITS OWN AUTHORITY. `manual` IS REAL, but it is a BUILT-IN NO-REGISTRY FALLBACK, not a registry-derived name:

  SOURCE A - REGISTRY-DERIVED SET = {backlogit, backlog-md}. SOURCE OF TRUTH: the tool_name field of each templates/backlog/registries/*.registry.yaml file. This set is OPEN and GROWS: adding a registry file adds a name. The binding check MUST derive it BY ENUMERATING THE REGISTRY DIRECTORY AND READING tool_name, never by a literal list, so a third registry added later is picked up without editing the check.

  SOURCE B - BUILT-IN NO-REGISTRY FALLBACK = {manual}. SOURCE OF TRUTH: the backlog tool enum declared in schemas/workspace-profile.schema.json (backlog.tool_name enum: backlogit, backlog-md, manual, null) and schemas/harness-config.schema.json (backlog.tool enum: backlogit, backlog-md, manual). The workspace-profile schema states the semantics VERBATIM: "When 'manual', no registry is expected. The harness installs a minimal backlog directory structure (queue/, archive/) without tool integration." `manual` is therefore a SENTINEL MEANING "NO REGISTRY", and expecting a registry for it contradicts its own definition.

  ACCEPTED SET = SOURCE A UNION SOURCE B. This union is what the fail-closed binding check resolves against.

NO HARDCODED DUPLICATE VALIDATION SET (BINDING). The check MUST NOT carry its own literal copy of the accepted names. It derives Source A from the registry directory and Source B from the schema enum, and any name in the schema enum that is NEITHER a registry tool_name NOR the declared no-registry sentinel is a FAIL-CLOSED ERROR naming the unknown value and both sources consulted. Recording a third literal set would create a third place to update and a silent drift surface between the schema, the registry directory, and the check - precisely the class of defect SHIP-6 exists to remove.

RECORD THE DIVERGENCE CHECK EXPLICITLY. Deliverable (3) must state, as a measured finding: the registry directory listing with each tool_name; the exact schema enum values from BOTH schema files and whether they agree with each other; and the resulting union. If the two schemas ever disagree, RECORD THE DISAGREEMENT as a finding rather than silently picking one - that is a real defect for a P-021 capture, not something this de-risking task resolves.

STAYS ORDER-INDEPENDENT OF SHIP-7 (binding H6, unchanged): the check resolves tool IDENTITY ONLY and MUST NOT read or validate feature flags. `manual` participates as an identity with no registry and therefore no features; that is exactly why it must be modelled as a distinct source rather than smuggled into the registry-derived set, where "has a registry" is an implicit property of every member.

ACCEPTANCE: all four deliverables recorded/committed; deliverable (3) records BOTH sources with their distinct sources of truth, the measured registry listing, the measured schema enums from both schema files, the resulting union, and an explicit statement that no manual registry exists or is to be created; 156.002-T explicitly consumes all four; no production file modified by this task.
