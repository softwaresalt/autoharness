BLOCKING SPIKE (plan-review finding P0-1; branch set corrected in review-fix cycle 2, findings 5 and 14). Establish how the Copilot plugin channel payload can actually be constrained before any plugin wiring begins.

The plan assumes the plugin payload can be trimmed, but the only observed mechanism is `.github/plugin/marketplace.json`'s `source: "."`, and no evidence establishes that Copilot CLI supports an exclusion or allowlist for plugin sources.

Determine which branch holds:
(a) marketplace source supports an exclusion/allowlist mechanism -> wire directly in the plugin-channel task (160.007-T); or
(b) it does not -> 160.007-T must instead materialize a TRACKED payload directory `plugin-payload/` from the manifest and repoint `source` at it; or
(c) neither (a) nor (b) is demonstrably supported -> HALT TO THE OPERATOR with the evidence. Do NOT invent or assume marketplace behaviour that the evidence does not show.

CONSUMER-FETCHABILITY CONSTRAINT (AC3c, NEW IN CYCLE 2, FINDING 5 - BINDING ON EVERY BRANCH): whatever `source` the spike selects MUST resolve to a path that a CONSUMER can actually fetch from a repository checkout. Cycle 1 selected `dist/plugin/`, but `dist/.gitignore` contains `*`, so that directory is untracked and absent from every consumer checkout - a consumer installing the plugin would resolve `source` to nothing and the install would simply fail. A build-output path is therefore NOT a valid `source` target, and this spike MUST NOT select one. The spike must not propose an unpublishable strategy on the assumption that some later step will publish it.

BRANCH (b) CONSEQUENCES THE SPIKE MUST RECORD IF IT SELECTS (b) - CORRECTED IN CYCLE 2:
- The materialized payload directory is `plugin-payload/` and is TRACKED, not gitignored. Tracked-ness is the whole point: it is what makes `source` fetchable from a plain `git clone`.
- `plugin-payload/**` must be classified in the manifest (160.003-T) as a GENERATED, INCLUDED-IN-PLUGIN-CHANNEL surface, and must be EXCLUDED from the wheel and sdist channels so the payload is not shipped twice.
- The materialization step must invoke the single generation command from 160.014-T (NOT 160.004-T - corrected in cycle 2, finding 14; 160.004-T is the resolver, 160.014-T is the generation command) rather than reimplementing resolution.
- Because the directory is tracked and derived, it inherits H1's generate-and-assert contract exactly as pyproject.toml and marketplace.json do: `generate --channel plugin --check` must detect drift between the committed `plugin-payload/` tree and the manifest, and CI must run it.
- The AC2b release-path gate (160.015-T - NOT 160.006-T; corrected in cycle 2, finding 14; 160.006-T is the wheel wiring task, 160.015-T is the release-path gate) must cover the plugin channel via `generate --channel all --check`.
- Overwriting a tracked `plugin-payload/` tree is a DESTRUCTIVE operation on tracked content. It is governed by the plan's rollback contract R-3/R-4: regeneration through the single generation command is the normal, non-destructive path; any restore or overwrite outside that command requires FRESH LIVE OPERATOR APPROVAL obtained in the session performing it. A backlog comment, this task's text, or any prior recorded approval is AUDIT EVIDENCE ONLY and can NEVER serve as that authorization.

BRANCH (a) CONSEQUENCE: if a genuine exclusion/allowlist mechanism exists, the spike must record the EXACT mechanism and its documented semantics (option name, file format, precedence), not merely that "exclusions appear supported". 160.007-T wires it directly and `plugin-payload/` is never created.

BRANCH (c) CONSEQUENCE: record the evidence gathered and the specific gap, then HALT. Opening a separate approved mechanism (for example a release artifact with supported installer semantics) is a NEW decision requiring operator approval - it is out of scope for this task to self-authorize.

WHICHEVER BRANCH IS SELECTED, the spike's finding is the input to the plugin-channel RED-FIRST case test_plugin_source_path_is_tracked_and_fetchable (authored by 160.005-T, green owned by 160.007-T), which asserts the resolved `source` path is tracked and present in a consumer-fetchable checkout.

ACCEPTANCE: documented finding naming the mechanism, with evidence (Copilot CLI plugin docs/behavior), and a decision recorded for branch (a), (b) or (c), including an explicit statement that the selected `source` path is consumer-fetchable and the evidence for it. NO SOURCE CHANGES.

BLOCKS: 160.007-T must not begin until this resolves. Proceeding on assumption (a) without evidence risks discovering mid-implementation that the plugin half of the feature is infeasible as written.

This task IS the de-risking step for its own high complexity.
