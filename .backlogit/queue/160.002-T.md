BLOCKING SPIKE (T1). Establish how the Copilot plugin channel payload can actually be constrained before any plugin wiring begins.

The plan assumes the plugin payload can be trimmed, but the only observed mechanism is `.github/plugin/marketplace.json`'s `source: "."`, and no evidence establishes that Copilot CLI supports an exclusion or allowlist for plugin sources.

Determine which branch holds:
(a) marketplace source supports an exclusion/allowlist mechanism -> wire directly in the plugin-channel task 160.007-T; or
(b) it does not -> 160.007-T must instead materialize a TRACKED payload directory `plugin-payload/` from the manifest and repoint `source` at it; or
(c) neither (a) nor (b) is demonstrably supported -> HALT TO THE OPERATOR with the evidence. Do NOT invent or assume marketplace behaviour that the evidence does not show.

DURABLE FINDING DESTINATION (authorized, binding). The finding is written to docs/spikes/2026-09-03-ship10-plugin-channel-mechanism.md - the path named for this task in the SHIP-10 plan H2 writable-surface table. A blocking spike whose determination gates 160.007-T cannot leave that determination in a transcript: 160.007-T, 160.005-T's test_plugin_source_path_is_tracked_and_fetchable, and the plan's AC3c all cite it, and a citation needs something to cite.

CONSUMER-FETCHABILITY CONSTRAINT (AC3c, BINDING ON EVERY BRANCH): whatever `source` the spike selects MUST resolve to a path that a CONSUMER can actually fetch from a repository checkout. A `dist/plugin/`-style build-output path is NOT valid: `dist/.gitignore` contains `*`, so such a directory is untracked and absent from every consumer checkout - a consumer installing the plugin would resolve `source` to nothing and the install would simply fail. The spike MUST NOT select a build-output path, and MUST NOT propose an unpublishable strategy on the assumption that some later step will publish it.

BRANCH (b) CONSEQUENCES THE SPIKE MUST RECORD IF IT SELECTS (b):
- The materialized payload directory is `plugin-payload/` and is TRACKED, not gitignored. Tracked-ness is the whole point: it is what makes `source` fetchable from a plain `git clone`.
- `plugin-payload/` IS THE PLUGIN CHANNEL'S GENERATED OUTPUT ROOT, NOT A CLASSIFIER INPUT (plan AC3d). It is declared in the manifest's `generated_output_roots` key and is NOT an `include` rule in ANY channel. THE DISTINCTION IS LOAD-BEARING, NOT COSMETIC: the plugin generator materializes INTO that tree, so an `include` rule naming it would make the generator's own output part of its next run's input - the second run would resolve `plugin-payload/**` as source and write it INSIDE `plugin-payload/`, yielding `plugin-payload/plugin-payload/...`, and every further run would nest again. `generate --check` would then report drift that regenerating can never clear, because each regeneration deepens the tree. That is PERMANENT DRIFT and it fails the release gate on every subsequent run.
- Paths under a declared output root are REMOVED FROM THE TRACKED-PATH ENUMERATION BEFORE classification, so generated content is neither classified nor unclassified and never trips AC2's unclassified-path build failure. The removal applies to all three channels, which is also what keeps the tree out of the wheel and the sdist (it is a derived duplicate of payload content, not source).
- EXCLUSION FROM CLASSIFIER INPUT DOES NOT MEAN EXCLUSION FROM PUBLICATION. The tree stays tracked and committed and remains the directory `marketplace.json`'s `source` points at. Input role and output role are different properties of the same path.
- The materialization step must invoke the single generation command owned by 160.014-T rather than reimplementing resolution. (160.004-T owns the resolver; 160.014-T owns the generation command that drives it.)
- Because the directory is tracked and derived, it inherits H1's generate-and-assert contract exactly as pyproject.toml and marketplace.json do: `generate --channel plugin --check` must detect drift between the committed `plugin-payload/` tree and the manifest, and CI must run it.
- The AC2b release-path gate owned by 160.015-T must cover the plugin channel via `generate --channel all --check`, where `all` means wheel, sdist and plugin.
- OVERWRITING OR REMOVING TRACKED CONTENT IN `plugin-payload/` IS DESTRUCTIVE AND REQUIRES FRESH LIVE OPERATOR APPROVAL (Constitution Principle VII; plan H2 "Principle VII generation rule"; CORRECTED IN EXTENDED REVIEW-FIX CYCLE 4, FINDING 3). THE WITHDRAWN CYCLE-3 WORDING - "regeneration through the single generation command is the normal, NON-DESTRUCTIVE path; any restore or overwrite OUTSIDE that command requires fresh live operator approval" - IS WITHDRAWN AND MUST NOT BE REINTRODUCED. It exempted the single most dangerous run in the shipment: the first materialization of the tree is pure creation and is harmless, but EVERY SUBSEQUENT regeneration after a manifest change OVERWRITES and possibly REMOVES tracked, committed payload content - and that is exactly the run in which a manifest mistake silently deletes files a consumer depends on. A trusted generator writing over a tracked file destroys committed content just as surely as an untrusted one; "it is a declared output root" describes the path's ROLE, not the REVERSIBILITY of the write, and neither the generator's trustworthiness nor the directory's designation can convert destruction into non-destruction. If the spike selects (b) it MUST record this rule in the finding, in this form:
  * A generation run partitions its planned writes into CREATE (target absent and untracked), NO-OP (tracked, bytes byte-identical - destroys nothing, so treated as CREATE-equivalent, which is what keeps idempotent regeneration from tripping the gate), OVERWRITE (tracked, bytes differ) and REMOVE (tracked, no longer resolved).
  * A NON-EMPTY OVERWRITE-or-REMOVE set requires FRESH, LIVE operator approval obtained IN THE SESSION PERFORMING THE RUN over a channel THE AGENT CANNOT SYNTHESIZE (R-3). Standing, blanket, prior-session and inferred approvals, this task's text, the spike finding itself, and any backlog comment are AUDIT EVIDENCE ONLY and can NEVER serve as that authorization. With no such channel available the agent HALTS and does not run the generation (R-4) - it does not downgrade, partially apply, or defer-and-proceed.
  * A run whose OVERWRITE-and-REMOVE sets are BOTH EMPTY requires NO approval and MUST NOT demand one. Creating files that are absent and untracked destroys nothing and is explicitly permitted unattended.
  * `generate --check` is READ-ONLY by construction and NEVER requires approval.

BRANCH (a) CONSEQUENCE: if a genuine exclusion/allowlist mechanism exists, the spike must record the EXACT mechanism and its documented semantics (option name, file format, precedence), not merely that "exclusions appear supported". 160.007-T wires it directly and `plugin-payload/` is never created.

BRANCH (a) CARRIES NO DESTRUCTIVE-APPROVAL REQUIREMENT AT ALL (cycle 4, finding 3). Under branch (a) NO output tree is materialized, no generation run writes into a tracked output root, and the OVERWRITE-and-REMOVE partition is EMPTY BY CONSTRUCTION. The spike MUST record explicitly that branch (a) requires NO operator approval for generation, and 160.007-T and 160.014-T MUST NOT request one on this path. Demanding approval where nothing can be destroyed is a FALSE GATE: it trains the operator to approve reflexively, which is precisely what destroys the value of the gate on the branch-(b) run that genuinely needs it.

BRANCH (c) CONSEQUENCE: record the evidence gathered and the specific gap, then HALT. Opening a separate approved mechanism (for example a release artifact with supported installer semantics) is a NEW decision requiring operator approval - it is out of scope for this task to self-authorize.

WHICHEVER BRANCH IS SELECTED, the spike's finding is the input to TWO plugin-channel cases, whose classes DIFFER and must not be conflated (corrected in cycle 4, findings 5 and 6):
- test_plugin_source_path_is_tracked_and_fetchable - CLASS CHARACTERIZATION, authored by 160.016-T, PRESERVATION owner 160.007-T. It asserts the resolved `source` path is tracked and present in a consumer-fetchable checkout. It is NOT red-first: the baseline `source: "."` resolves to the repository root, which IS tracked and IS in every consumer checkout, so the property is BASELINE-TRUE and branch (a) preserves it unchanged. Its job is PRESERVATION - whatever branch the spike selects must not break it, which is exactly the `dist/plugin/` failure mode the CONSUMER-FETCHABILITY CONSTRAINT above exists to prevent.
- test_plugin_payload_conforms_to_the_selected_strategy - CLASS RED-FIRST, authored by 160.005-T, green owner 160.007-T. Branch-parametric: under (a) it asserts NO tree is materialized AND the natively-filtered payload EQUALS the manifest-derived plugin set; under (b) it asserts the tracked tree exists, is flat, is self-excluded from classifier input, and `generate --channel plugin --check` reports no drift after regeneration. THE SELECTED STRATEGY IS REQUIRED DATA - a run in which no strategy is declared FAILS, so the case can never be satisfied by silence. The spike MUST therefore record the selected strategy in a form 160.003-T can encode as a declared manifest key, not merely as prose.
