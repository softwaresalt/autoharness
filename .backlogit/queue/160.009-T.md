Verify cross-environment registration against the trimmed payload, under an EXPLICIT channel x environment support matrix.

WHY THIS WAS REWRITTEN (Orchestrator review-fix cycle 1, finding 5): the original task listed vscode / copilot-cli / claude / codex as a flat set of "supported environments" and then, in prose, noted that plugin-only consumers cannot use three of them. That mixes two different channels' registration surfaces into one undifferentiated list. Registration support is a function of (channel, environment), not of environment alone, and it must be asserted as such.

SUPPORT MATRIX (AC7). Rows are registration targets; columns are install channels. This matrix is the acceptance contract - every cell is asserted, positively or negatively.

| Registration target | pip / clone (Python CLI present) | plugin-only (no Python CLI) |
| deploy-harness register --vscode / setup-vscode | SUPPORTED | NOT SUPPORTED (pre-existing) |
| deploy-harness register --copilot-cli | SUPPORTED | SUPPORTED - this is the plugin channel's own target |
| deploy-harness register --claude / setup-claude | SUPPORTED | NOT SUPPORTED (pre-existing) |
| deploy-harness register --codex / setup-codex | SUPPORTED | NOT SUPPORTED (pre-existing) |
| autoharness verify-workspace | SUPPORTED | NOT SUPPORTED (pre-existing) |

EVIDENCE FOR THE "pre-existing" CLAIM: docs/installation.md states that the plugin path "gives Copilot CLI users built-in versioning and update management with no Python dependency" and that "the Python CLI is still needed for setup-vscode, verify-workspace, and registering with Claude Code or Codex." Excluding src/ from the plugin channel PRESERVES that documented state; it does not create it.

POSITIVE TESTS (pip/clone column):
- test_register_phase_all_environments_python_channel (AC7) - the deploy-harness.ps1 / deploy-harness.sh `register` phase succeeds for vscode, copilot-cli, claude, and codex against the trimmed payload with the Python CLI present. BOTH script variants are covered; a PowerShell-only or POSIX-only pass is not evidence for the other.

NEGATIVE ASSERTIONS (plugin-only column) - MANDATORY, not optional prose:
- test_plugin_only_register_copilot_cli_succeeds - the one supported plugin-channel cell, asserted positively.
- test_plugin_only_unsupported_targets_fail_the_same_way_as_baseline - for vscode, claude, codex, and verify-workspace, assert the plugin-only environment fails, AND assert the failure is IDENTICAL IN KIND to the v1.5.0 untrimmed baseline's failure in the same environment. The assertion is "UNCHANGED", not merely "fails". A test that only asserts failure cannot distinguish a preserved limitation from a regression that this shipment introduced.
- test_plugin_channel_excludes_python_cli_by_design - assert src/ and pyproject.toml are absent from the resolved plugin payload, so the unsupported cells are unsupported for the DECLARED reason (no Python distribution) rather than by accident.

RATIONALE: the manifest ships only a SUBSET of scripts/ (deploy-harness.*, acquire_lock.*, release_lock.*, ci-topology-check.sh). If registration for any supported cell depends on a script or artifact the manifest excluded, it fails at consumer install time rather than in CI (risk R1). This matrix is the guard.

SCOPE BOUNDARY: this task asserts REGISTRATION support per channel. It does NOT define or test the `_DATA_DIR` / plugin-root RESOLUTION contracts - those are 160.013-T (AC6a / AC6b). Consume that task's contracts; do not restate them.
