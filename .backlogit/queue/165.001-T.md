RED MECHANISM — A NARROW CUSTOM HELPER, NOT `xfail` AND NOT `unittest.expectedFailure` (PR review-fix cycle 2, staging PR #448, thread PRRT_kwDORzpWpM6h3frC — the finding is VALID and ACCEPTED; this REPLACES the cycle-3 "xfail-strict / expectedFailure with `raises=`/reason" instruction, which was NOT IMPLEMENTABLE in this repository).
WHY THE CYCLE-3 INSTRUCTION WAS WRONG, VERIFIED AT THIS HEAD:
- CANONICAL CI RUNS `python -m unittest discover -s tests` (`.github/workflows/ci.yml`; the file's own header states "autoharness has no ruff/pyright/pytest configured; the only real gates are the stdlib unittest suite ... and markdownlint"). Under `unittest`, a `@pytest.mark.xfail(...)` decorator is INERT — it attaches an attribute and nothing reads it — so the test BODY RUNS, the expected failure is raised, and CI GOES RED. Specifying `xfail-strict` here would have made the harness task leave canonical CI failing, which directly contradicts "THIS TASK ENDS GREEN". `pytest` being importable in a local environment does not change what CI executes.
- `unittest.expectedFailure` DOES run under the canonical runner and DOES fail the suite on an unexpected success, but it CANNOT CONSTRAIN THE REASON: it accepts ANY exception as satisfying the expectation and takes NO `raises=` argument and NO reason argument. A fixture error, an import error, an unregistered `--phase`, or a typo would all be recorded as the expected failure. That is precisely the "unconstrained xfail is indistinguishable from a broken fixture" hazard cycle 3 set out to close, so `expectedFailure` cannot close it.
REQUIRED INSTEAD — build ONE small stdlib-only helper (e.g. `tests/support/red.py`), used by every RED expectation in this shipment:
`@expect_red(raises=<ExceptionType | tuple[ExceptionType, ...]>, message_contains="<substring>", reason="<why this is not yet implemented>")`
Semantics, all three mandatory:
  a. The decorated test body runs. If it raises an exception that IS an instance of `raises` AND whose NORMALIZED message contains `message_contains`, the expectation is satisfied and the test PASSES (green suite, recorded RED). Normalization: `str(exc)`, whitespace collapsed to single spaces, stripped, casefolded — so the match is not brittle against formatting while still being a real content assertion.
  b. If the body raises ANYTHING ELSE — a different exception type, or the right type with a non-matching message — the test FAILS, with a diagnostic that names BOTH the expected and the observed type/message and states explicitly that this is a WRONG FAILURE, not the expected one. A broken fixture, a collection/import error, an unregistered phase, or a typo therefore turns the suite RED instead of masquerading as "still red".
  c. If the body raises NOTHING, the test FAILS as XPASS, with a message instructing the reader to flip the expectation to an ordinary assertion. This preserves the strictness property that made `xfail(strict=True)` desirable.
The helper MUST be pure stdlib (`functools.wraps` + `try/except`), MUST NOT import `pytest`, and MUST behave IDENTICALLY under `python -m unittest discover -s tests` and under a local `pytest` run. `assertRaises` is NOT a substitute: it asserts the exception but does not distinguish an XPASS from a missing behaviour, and it does not carry the "this is a known RED, flip me later" intent that 165.002-T acts on.
SIMPLER ALTERNATIVE, EXPLICITLY PERMITTED: if for any specific expectation the helper proves awkward, that expectation may instead be authored IN THE SAME TASK AS ITS IMPLEMENTATION (so it is written red and turned green within one task and one commit), PROVIDED the RED observation is still RECORDED — the observed failing exception type and message captured in that task's disposition notes before the implementation lands. Either route is acceptable; leaving a genuinely unconstrained expectation is not. EVERY TASK ENDS GREEN under both routes.
