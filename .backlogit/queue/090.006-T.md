## Description

<!-- BEGIN:description -->
Stop defaulting quality-report metrics to "observed" when no quality label was ever recorded (source: stash 59E6CD50).

Files (2): src/autoharness/telemetry/report.py, tests/test_telemetry_reports.py

Current state: _quality (report.py:98-115) defaults worst to "observed" whenever worst is None, unless the metric field name is in _unavailable_metrics (report.py:51-60), which only flags fields whose VALUE is None/"unavailable" -- it does not distinguish "no quality label was ever attached" from "quality label was attached and is genuinely observed". This makes reports overstate confidence for metrics that were never quality-annotated.

TDD (red->green): add two tests to test_telemetry_reports.py (both fail first). (1) test_quality_reports_unavailable_when_no_label_recorded: a metric history with zero quality-label entries asserts _quality returns "unavailable" (NOT "observed"). (2) test_quality_reports_unavailable_for_mixed_missing_label_history: a MIXED history containing one genuinely "observed" record and one populated record with NO same-named quality label must degrade the aggregate to "unavailable" (not "observed") -- this is the real 59E6CD50 failure mode, since _quality skips missing labels per record. Then change _quality so each populated record with a missing same-named quality label is treated as "unavailable": do NOT introduce a new "unknown" value -- the documented quality vocabulary is observed/derived/estimated/unavailable/not-applicable (docs/telemetry-reference.md:27,47), so reuse the existing "unavailable". Preserve current behavior for fields already in _unavailable_metrics.
<!-- END:description -->

## Acceptance Criteria

<!-- BEGIN:acceptance-criteria -->
- Metrics with zero recorded quality labels report "unavailable", not "observed".
- A mixed history where any populated record lacks a same-named quality label degrades the aggregate to "unavailable", not "observed".
- No new "unknown" quality value is introduced; only the documented vocabulary (observed/derived/estimated/unavailable/not-applicable) is used.
- Metrics whose populated records all carry a real "observed" quality label continue to report "observed".
- Existing _unavailable_metrics-driven behavior for None/"unavailable" values is unchanged.
