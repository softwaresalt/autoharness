# AutoHarness Framework multi-tier spec: gap analysis vs shipped capabilities

## Problem Frame

<!-- BEGIN:problem-frame -->
docs/product-specs/autoHarness-framework-specifications.md restates a 5-part framework vision: (1) role components Orchestrator/Stage/Ship/Verification-Compaction; (2) dynamic model routing (Sol/Opus 4.8/Terra/Haiku-Luna); (3) unified CLI+MCP tool-execution abstraction (action/observation loop, sequential pipelining, stderr routing); (4) dynamic escalation routing with telemetry thresholds (MAX_ITERATIONS), adversarial verification pass, escalation-payload handoff to Sonnet 5, terminal engram handoff; (5) durable granular checkpointing/state recovery with crash resumption and context pruning. Much of this is ALREADY SHIPPED. Staging must reconcile net-new scope against shipped work before any harvest, and must NOT blind-harvest an aspirational spec into speculative, unverifiable tasks (P-003 risk).
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
A) Blind-harvest the 5 phases into features/tasks now — REJECTED: most phases duplicate shipped work; the genuinely net-new items are large/architectural and unbounded without design, producing non-granular, unverifiable tasks (violates the 2h rule and P-003). B) Treat the whole spec as one epic and decompose top-down — REJECTED for this pass: no operator prioritization of which net-new capability leads; risks scope expansion beyond the dark-mode scope contract. C) (CHOSEN) Gap-analyze spec vs shipped ledger, mark duplicative phases as satisfied, isolate the genuinely net-new capabilities, and SURFACE them for operator prioritization + per-capability spike/plan before any harvest.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Option C — Gap analysis + surface for operator prioritization; do NOT harvest into a shipment this pass. Ledger reconciliation: §1 role components + §2 model routing are SUBSTANTIALLY SHIPPED via 013-S (P-013 tier taxonomy + persona isolation), 020-S (routing + cross-provider verification), 027-S (elective agent routing), and 104-F/108-S (invocation-time role routing enforcement, verifiable, P-013.5). §4 adversarial verification/escalation is PARTIALLY addressed by 096-S (multi-model adversarial review routing). §2/§4 telemetry inputs are SHIPPED via 079-F/092-S (telemetry contract + ToolTelemetryEvent v1.0) and 084-F/107-S (token-efficiency emission + deterministic epoch composition). §5 checkpointing has a shipped substrate (backlogit checkpoints + agent-engram). Genuinely NET-NEW, each LARGE and needing its own spike/plan: (a) §3 unified CLI/MCP action-observation execution abstraction with sequential pipelining + stderr-to-model routing; (b) §4 telemetry-driven AUTO-escalation (MAX_ITERATIONS thresholds -> halt -> escalation-payload compilation -> Sonnet 5 re-route -> terminal engram handoff), beyond today's review-routing; (c) §4/background Verification & Compaction layer (log parsing, history summarization, state pruning); (d) §5 crash-resumption orchestration + context-pruning-on-restore over the existing checkpoint/engram substrate. None are bounded enough to become a safe (<2h/task, single-family) shipment without operator selection of the lead capability and a per-capability spike. Also SURFACE a model-pick DIVERGENCE: the spec assigns Ship=GPT-5.6 Terra and escalation=Sonnet 5, whereas shipped config/P-013.5 sets Ship=claude-sonnet-5 — operator must reconcile the spec's model picks against the shipped routing config.
<!-- END:chosen-direction -->
