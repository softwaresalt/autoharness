# Role-based model routing enforcement: design deliberation

## Problem Frame

<!-- BEGIN:problem-frame -->
Autoharness's core purpose includes deliberate model routing, but the Orchestrator invokes Stage/Ship subagents (Steps 1/2) with NO explicit model-override directive. Sub-sessions therefore inherit the default/session model. The installed agent defs already declare model_family (Stage=claude-opus-4.8, Ship=claude-sonnet-5) and config.model_routing already binds tier3=claude-opus-4.8/tier2=claude-sonnet-5, but frontmatter model_family is advisory ('may be ignored') and there is no invocation-time enforcement and no verification that fails when routing is omitted or silently defaults. P-013 (013-S) established the tier taxonomy + persona isolation and must NOT be regressed; model_tier frontmatter was retired (053.004-T) and must not return. Goal: make role-based routing (Stage->Opus 4.8, Ship->Sonnet 5) executable and verifiable, configurable for installed harnesses, and environment-agnostic (no provider IDs hardcoded across templates; capability-aware fallback), not an informal per-session prose promise.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
Option A — First-class per-role config routes only: add stage/ship/orchestrator object routes under config.model_routing (reusing the existing anchor_review/alt_review named-route pattern), decoupled from tiers; installer resolves them into agent frontmatter. Pros: explicit role-based routing operator asked for; reuses precedent. Cons: role fully decoupled from P-013 tier taxonomy could drift from tier semantics; needs a default when unset.
Option B — Reuse existing tier binding only: keep Stage=tier3/Ship=tier2 implicit binding; add ONLY the invocation-time enforcement directive + verification, no new config keys. Pros: minimal new surface; leans on shipped P-013. Cons: role->model stays implicit prose (Stage forever==tier3), does not deliver the explicit, operator-legible 'role-based' mapping; overloads tier as the only routing axis.
Option C (HYBRID, recommended) — Role->route resolution layer: add OPTIONAL first-class stage/ship role routes to config.model_routing (object form {model_family, model_provider, reasoning_effort}, reusing anchor_review pattern); when a role route is unset, resolve via the agent's config-bound tier (Stage->tier3, Ship->tier2) as the environment-agnostic default so nothing regresses. Add an explicit invocation-time model-routing directive to Orchestrator Steps 1/2 (and the skill-delegation contract) that resolves role->model and passes/declares the override at invocation. Add a fail-closed verify_workspace assertion: each pipeline agent must declare a RESOLVED model_family/model_provider (no unresolved {{...}} placeholder, non-empty) AND the Orchestrator invocation protocol must contain the explicit routing directive; the role route must resolve. Add capability-aware fallback (P-012 style): when the runtime cannot honor a per-invocation model override, DECLARE ROUTING_DEGRADED and surface to operator — never silently default. Reconcile the versioned 1.0.0 schema skew.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Option C (Hybrid role->route resolution with fail-closed verification). Rationale: (1) Preserves the shipped P-013 tier taxonomy — role routes DEFAULT to the config-bound tier, so no regression and no reintroduction of model_tier; (2) Delivers the explicit, operator-legible role-based mapping (Stage->claude-opus-4.8, Ship->claude-sonnet-5) as configurable config routes, not prose; (3) Keeps provider-specific model IDs in config.yaml ONLY (templates stay variable-parameterized {{...}}), honoring environment agnosticism and letting installed harnesses remap or supply capability-aware equivalents; (4) Reuses the established anchor_review/alt_review named-route schema pattern (low novelty); (5) Makes routing VERIFIABLE and FAIL-CLOSED via a verify_workspace assertion + tests that fail when the invocation directive is missing, the role route is unresolved, or an agent's model_family is an unresolved placeholder/empty — satisfying 'must not remain an informal per-session promise'; (6) Environment-agnostic fallback: explicit ROUTING_DEGRADED declaration instead of silent default, consistent with P-012.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
1. Invocation directive form: per Core Rule 3 (environment agnosticism) the override MUST be expressed as an explicit intent directive in the Orchestrator/skill prose plus the resolved model_family/model_provider the runtime can honor — NOT a literal baked --model CLI flag. Confirm no environment-specific CLI contract is hardcoded. 2. Skill-workflow routing: skills are leaf executors (P-013) inheriting the invoking agent's session model; enforcement point is that the AGENT session is correctly routed before it invokes skills — confirm we do not need per-skill model fields. 3. Versioned schema skew: schemas/harness-config/1.0.0.schema.json still defines tiers as plain strings while the unversioned schema uses oneOf[string,object]; adding stage/ship role routes must reconcile BOTH schemas. 4. Whether a new policy sub-clause (e.g., P-013.5 'invocation-time routing enforcement') should be appended to workflow-policies vs amending P-013.4 — OPERATOR-VISIBLE naming decision. 5. Default reasoning_effort/provider values for the role routes in the dogfood config (operator dogfood: anthropic/high already present in installed defs).
<!-- END:open-questions -->
