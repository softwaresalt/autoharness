SIZE: S. COMPLEXITY: medium. (Two independent axes; also emitted as structured backlog fields.) Shipment 1 (P0). Split out of 118.005-T by the F27 ruling so that the atomic-acquisition task and the lock-lifecycle task each stay inside the 2-hour box. Extend src/autoharness/supervise/locking.py with STALE-RECORD LIFECYCLE handling, built strictly on top of the guard primitive established in 118.005-T and never as a substitute for it.

F34 RULING (2026-08-11, operator-accepted; SUPERSEDES the earlier 'acquire the same primitive' wording that F34 proved unimplementable, and REPLACES the compare-and-DELETE framing with compare-and-REPAIR under the guard). This task operates on the GUARD/RECORD SPLIT defined in 118.005-T and MUST NOT reintroduce a single-file lock:

THE GUARD IS NEVER THE THING REMOVED. Force-unlock and stale cleanup MUST NEVER delete, unlink, rename, replace or recreate the GUARD FILE. The guard is stable and permanent; only the RECORD FILE (PID + process start-time + session id) is ever read, validated, replaced or removed. Any specification, test, or implementation that deletes the guard is a DEFECT, not an alternative - deleting the guard reintroduces the path/inode race in which one process holds a lock on the old inode while another locks a freshly created one and both believe they hold exclusion.

BOTH PATHS TAKE THE SAME GUARD LOCK. NORMAL ACQUISITION (118.005-T) and FORCE-UNLOCK/STALE CLEANUP (this task) MUST BOTH acquire the SAME guard lock, and cleanup MUST hold it BEFORE it reads, validates, replaces or removes ANY record metadata. Inspection and mutation of the record are ONE critical section under the guard, never two operations with a gap. This is now actually achievable - which the previous formulation was not - precisely because the guard always exists and is never deleted, so cleanup can always attempt the identical lock that acquisition takes.

A LIVE HOLDER PREVENTS CLEANUP. If the guard lock CANNOT be acquired, a live holder exists BY DEFINITION and force-unlock MUST REFUSE. It MUST NOT fall back to inspecting, rewriting or removing the record, MUST NOT bypass the guard by operating on the record file directly, and MUST NOT delete the guard to 'break' the lock. Liveness observed OUTSIDE the critical section is ADVISORY DIAGNOSIS ONLY and is NEVER sufficient authority to mutate anything. Stale metadata may be repaired ONLY while holding the guard.

COMPARE-AND-REPAIR UNDER THE GUARD. Once the guard lock is held, the record is RE-READ INSIDE the critical section and MUST still match the record that was diagnosed stale (PID + process start-time + session id). ANY mismatch means the situation changed after diagnosis and force-unlock MUST REFUSE rather than mutate. Only on a match is the stale record removed or replaced, and that removal is confined to the RECORD file.

F31 SAFETY PROPERTY PRESERVED (this is why the ruling exists, not a relaxation of it). The F27 ruling made ACQUISITION atomic; it did NOT make stale CLEANUP safe, and those are two different operations. Force-unlock as originally specified was a check-then-act sequence with its own TOCTOU window: it diagnoses a holder as stale, a DIFFERENT supervisor legitimately acquires the lock in the interval, and the unchecked delete then removes a LIVE holder's state - defeating the single-session invariant through the very remedy meant to restore it, and doing so SILENTLY because the deleter believes it removed a corpse. The guard/record split closes that window while keeping --force-unlock REACHABLE, which the previous single-primitive formulation did not: under exclusive-create, a stale lock means the path already exists, so cleanup could never acquire and --force-unlock would always refuse, stranding the workspace with no remedy at all.

STALE-RECORD LIFECYCLE (F27 requirements preserved). Liveness uses PID PLUS PROCESS START-TIME so a recycled PID cannot be mistaken for the original holder. A stale record (dead PID, or start-time mismatch) is NEVER silently reclaimed: it requires an explicit operator --force-unlock, which is exposed by the 120.006-T CLI option contract and is the only reachable remedy for a stranded lock. Crash-without-release is DIAGNOSED and reported with an actionable message naming the holding PID and session id, and cleared only on explicit operator action. Note that a crashed holder's GUARD LOCK is released by the OS automatically (118.005-T criterion (c)), so the residue requiring the operator remedy is the STALE RECORD, not a stranded kernel lock. FAIL CLOSED (H2): when liveness cannot be determined, treat the holder as LIVE and REFUSE. Errors use the taxonomy from 118.003-T.

TESTS: dead-PID stale detection, start-time mismatch (recycled PID) rejection, force-unlock happy path, force-unlock REFUSED against a LIVE lock, crash-without-release cleanup, and indeterminate-liveness -> REFUSED.

MANDATORY REAL CONTENDER/RACE TESTS (F31 + F34, non-negotiable; a sequential ordering assertion CANNOT observe these defects and does not satisfy this criterion). Spawn GENUINE CONCURRENT PROCESSES, run repeatedly over a bounded iteration count so a single lucky interleaving cannot be mistaken for correctness, and assert on BOTH Windows and POSIX:
(1) CLEANUP CANNOT REMOVE OR REPLACE A LIVE HOLDER'S METADATA: one process performs force-unlock against a record it has diagnosed as stale while a contender performs a NORMAL acquisition, interleaved so the contender acquires AFTER the stale diagnosis but BEFORE the mutation - the window the previous specification left open. The run MUST end with exactly one live holder, that holder MUST be the contender, the contender's record MUST be intact and unmodified, and the force-unlock MUST have REFUSED.
(2) STALE METADATA IS REPAIRABLE ONLY UNDER THE GUARD: a cleanup that has NOT taken the guard lock is never able to mutate the record; assert that every observed record mutation is attributable to a guard-holding actor, and that a contended cleanup performs ZERO writes.
(3) GUARD SURVIVES CLEANUP: after every force-unlock outcome (success, refusal, and error), the guard file still exists with an UNCHANGED identity (inode/file-id compared before and after), proving cleanup never deleted or recreated it.
POSITIVE CONTROLS REQUIRED (each must FAIL the suite, because a race test that never fails is indistinguishable from a race test that cannot detect the race): (a) a deliberately UNSAFE compare-free record delete; (b) a deliberately UNSAFE cleanup that mutates the record WITHOUT holding the guard; (c) a deliberately UNSAFE cleanup that DELETES AND RECREATES the guard file.
