SIZE: S. COMPLEXITY: medium. (Two independent axes; also emitted as structured backlog fields.) Shipment 1 (P0). Split out of 118.005-T by the F27 ruling so that the atomic-acquisition task and the lock-lifecycle task each stay inside the 2-hour box. Extend src/autoharness/supervise/locking.py with STALE-LOCK LIFECYCLE handling, built strictly on top of the atomic primitive established in 118.005-T and never as a substitute for it. Liveness uses PID PLUS PROCESS START-TIME so a recycled PID cannot be mistaken for the original holder. A stale lock (dead PID, or start-time mismatch) is NEVER silently reclaimed: it requires an explicit operator --force-unlock, which is exposed by the 120.006-T CLI option contract and is the only reachable remedy for a stranded lock. Crash-without-release leaves a stale lock that is DIAGNOSED, reported with an actionable message naming the holding PID and session id, and cleared only on explicit operator action. FAIL CLOSED (H2): when liveness cannot be determined, treat the lock as LIVE and refuse. Errors use the taxonomy from 118.003-T. F31 RULING - FORCE-UNLOCK MUST BE MUTUALLY EXCLUSIVE WITH ACQUISITION, NOT MERELY 'CHECKED FIRST'. The F27 ruling made ACQUISITION atomic; it did NOT make stale CLEANUP safe, and those are two different operations. As previously specified, force-unlock was still a check-then-act sequence with its own TOCTOU window: it diagnoses a holder as stale, a DIFFERENT supervisor legitimately acquires the lock in the interval, and the unchecked delete then removes a LIVE holder's lock - defeating the single-session invariant through the very remedy meant to restore it, and doing so SILENTLY because the deleter believes it removed a corpse. REQUIRED: force-unlock MUST FIRST ACQUIRE THE SAME OS-BACKED EXCLUSION PRIMITIVE used by 118.005-T acquisition, and MUST hold it across BOTH the inspection AND the removal - inspection and deletion are ONE critical section, never two operations with a gap. If that primitive cannot be acquired, a live holder exists BY DEFINITION and force-unlock MUST REFUSE - it MUST NOT fall back to inspecting or deleting metadata, and MUST NOT bypass the primitive by operating on the file directly. Removal is therefore a COMPARE-AND-DELETE under exclusion: the metadata identifying the holder (PID + process start-time + session id) is re-read INSIDE the critical section and MUST still match the record that was diagnosed stale; ANY mismatch means the lock was re-acquired and force-unlock MUST REFUSE rather than delete. Liveness observed OUTSIDE the critical section is advisory diagnosis only and is NEVER sufficient authority to delete. Tests: dead-PID stale detection, start-time mismatch (recycled PID) rejection, force-unlock happy path, force-unlock refused against a LIVE lock, crash-without-release cleanup, and indeterminate-liveness -> REFUSED. MANDATORY RACE TEST (F31, and it must be a REAL concurrency test - a sequential ordering assertion CANNOT observe this defect and does not satisfy this criterion): spawn genuine concurrent processes in which one performs force-unlock against a lock it has diagnosed as stale while a contender performs a NORMAL acquisition, interleaved so the contender acquires AFTER the stale diagnosis but BEFORE the removal - the window the previous specification left open. ASSERT THAT THE NEWLY ACQUIRED LIVE LOCK IS NEVER DELETED: the run must end with exactly one live holder, that holder must be the contender, and the force-unlock must have REFUSED. Run it repeatedly (bounded iteration count) so a single lucky interleaving cannot be mistaken for correctness. POSITIVE CONTROL REQUIRED: the same harness, pointed at a deliberately UNSAFE compare-free delete, MUST FAIL - a race test that never fails is indistinguishable from a race test that cannot detect the race.
