<!-- BEGIN:description -->
WIDTH: CLI/presentation ONLY. Files: src/autoharness/cli.py + tests/test_gate_dag_readiness_cli.py. Does NOT touch gates/topology.py (115.001-T owns it) and does NOT touch docs (115.003-T owns them).

Wire the analyzer from 115.001-T into the existing `autoharness gate dag-readiness` command. NO new flag and NO new subcommand: the three cursor fields are emitted UNCONDITIONALLY as ADDITIVE fields (014-DL open question 1 resolved — an opt-in flag would create two payload shapes to test and document for no benefit, and additive fields are already backward compatible).

JSON FIELDS ADDED (all always present):
- `next_eligible`: shipment id or null.
- `next_eligible_reason`: exactly one of `resume_active`, `ready_set_head`, `no_candidates`, `multi_active_anomaly`, `ambiguous_provenance`, `cycle_detected`, `degraded`. Always populated, even when `next_eligible` is null.
- `next_eligible_detail`: object with BOTH `candidate_ids` and `offending_ids` keys always present (empty lists when not applicable).

HUMAN REPORT: `_format_dag_readiness_report` gains AT MOST ONE line, e.g. `next eligible: 117-S (resume_active)` or `next eligible: (none) — multi_active_anomaly: 118-S, 119-S`. The line must render on the cycle and DEGRADED early-return paths too, so the operator never sees a report that silently omits the cursor.

DEGRADED PATH: the existing `BacklogUnavailableError` handler builds its payload literally in `_gate_dag_readiness_command`; it must also carry `next_eligible: null` / `next_eligible_reason: "degraded"` / an empty detail object, so the DEGRADED payload has the SAME key set as the ok/empty payloads.

EXIT CODES ARE UNCHANGED: 0 for any report (ok/empty/degraded) and 2 for invalid args. dag-readiness still has NO BLOCK verdict — the multi-active anomaly is REPORTED, never escalated to a non-zero exit here; the pipeline-topology gate owns that BLOCK. Changing exit codes would break the Phase 1 contract.
