Epoch-keyed report emitter under .autoharness/gates/pre-review/ (Q1 exception) plus the D6 freshness rule. Epoch key is `<head_sha>-<fingerprint>` so a tool-version change at unchanged HEAD can write fresh evidence without overwrite. Flat list only — the signature makes a persisted graph unrepresentable. No read-back, no blocking authority. Domain: code. Files: 1.

<!-- BEGIN:acceptance-criteria -->
* **INV-1 / Decision D-5**: the writer accepts a flat `Sequence[NodeResult]` and has **no access to edges** — a persisted graph is **unrepresentable by type**, not merely forbidden by prose. Derive-never-persist still holds for the graph itself.
* **INV-2 (Q1 boundary)**: the report is **derived evidence, not the source of truth**. The module exposes **NO read-back API** in S1. Regeneration from the tree at that SHA must be possible.
* The emitter has **no blocking authority** and cannot influence the exit code.
* **INV-8 — epoch key is `<head_sha>-<fingerprint>`**, where `<fingerprint>` is the first 16 hex chars of SHA-256 over a canonical (JSON, `sort_keys=True`, no whitespace, UTF-8) serialization of ALL freshness dimensions: detector-registry version, validation-gates schema version, and the resolved values of every declared `producer.tool_version_dims`, sorted.
* **Deterministic**: identical dimensions produce an identical key across processes, platforms, and input orderings.
* **Refresh at unchanged HEAD works**: after a tool-version change at the SAME HEAD, a rerun writes a **new fresh report under a new key**; the prior file is **not** overwritten and consumers are **not** stranded at `insufficient_evidence`.
* **Unique current report**: a consumer COMPUTES the expected key and reads exactly that path — never scans-and-guesses. At most one report can match the current dimensions.
* **Stale siblings**: other `<head_sha>-*.json` files remain on disk as history and can **never** be consumed as fresh, because their key cannot equal the computed current key. Rejection is structural (key mismatch), not a check a consumer could forget.
* **Concurrent / idempotent same-key writes**: atomic `os.replace` from a temp file in the target dir, or `O_EXCL` treating an existing same-key file as success. Two concurrent writers yield exactly one well-formed, non-corrupt, non-duplicated report.
* Append-only: no report is ever mutated, replaced, or deleted.
* Stale `head_sha` or changed `tool_version_dims` -> `insufficient_evidence`, never a reused `passed`.
<!-- END:acceptance-criteria -->

<!-- BEGIN:description -->
Plan unit **U7**. Create `src/autoharness/detectors/report.py`.

Write `.autoharness/gates/pre-review/<epoch_key>.json` — a **flat list of node results**, keyed by immutable epoch, **append-only, never overwritten**. This sits alongside the existing `.autoharness/gates/*-force-audit.log` and `pipeline-topology-telemetry.jsonl` precedents.

**EPOCH KEY (D-11)**: `<head_sha>-<fingerprint>`. HEAD alone is NOT sufficient — see implementation notes for the deadlock it causes. The fingerprint is the first 16 hex chars of `SHA-256` over a canonical serialization (JSON, `sort_keys=True`, separators without whitespace, UTF-8) of:

* the detector-registry version,
* the validation-gates schema version, and
* the resolved values of all declared `producer.tool_version_dims`, sorted.

**Provenance block (D6)**: `base_sha`, `head_sha`, `epoch_key`, `fingerprint`, `reviewed_sha` (nullable), `platform`, `tool_versions`, `produced_at` (RFC3339), and `touches_reviewable_paths: bool` (per `028-DL` R2, so documentation-only pushes do not inflate the epoch count).

**Freshness rule (D6, unchanged in meaning)**: a node result is fresh iff its `head_sha` equals current HEAD **and** every dimension declared in `producer.tool_version_dims` is unchanged. Both conditions are now **encoded in the key itself**, so freshness and identity are the same predicate. **A stale result is `insufficient_evidence`, never a reused `passed`.**

**Consumer selection rule** (specified here, IMPLEMENTED BY S8 — not a read path in S1): compute the expected key from current HEAD plus the current fingerprint, then read exactly that path.

**Write strategy**: atomic temp-file + `os.replace`, or `O_EXCL` with existing-same-key treated as success. Content is deterministic per key, so concurrent writers cannot diverge.

**Execution posture**: test-first.

<!-- BEGIN:implementation-notes -->
**Depends on U1.** Tested by U10b (149.014-T, shape + freshness semantics) and U10c (149.015-T, epoch determinism + concurrency).

**Decision D-11 (PR #414 cycle-1 correction, thread PRRT_kwDORzpWpM6dGx-1)**: the earlier draft keyed the report on `<head_sha>.json` alone. Combined with append-only-never-overwrite, that **conflicts with the D6 freshness rule**:

* D6 declares a report stale if ANY declared `tool_version_dims` value changed, even at the same HEAD.
* But the only path is `<head_sha>.json`, and same-epoch writes never overwrite.
* So after a tool-version change the sole persisted report is **stale**, and a rerun **cannot write fresh evidence for that same HEAD**.
* Consumers are stranded at `insufficient_evidence` until an unrelated commit happens to move HEAD. The gate becomes unable to refresh its own evidence.

Folding a canonical fingerprint of the freshness dimensions into the key dissolves the deadlock **without weakening immutability**: nothing is ever mutated or replaced: a *new* file is written under a *new* key, and the old one survives as history. Freshness and identity become the same predicate, so stale-sibling rejection is structural rather than a comparison a consumer might skip.

**Q1 IS PRESERVED EXACTLY AS APPROVED.** Q1 grants a single persistence exception to Law 1 for the derived *report*. D-11 changes only the report's **key**, not its shape, its authority, or its read-back status. Law 1 (derive-never-persist) still applies in full to the **graph itself** — INV-1 and D-5's type-level constraint are untouched. The Q1 justification remains conditional: **if S8 wires no named consumer, the writer must be WITHDRAWN** (D9 / Law 2). Record that condition in the shipment closure record, along with the `<head_sha>-<fingerprint>` convention and the canonical fingerprint input list.

**No migration, no backfill.** S1 has not shipped, so **no report has ever been written** under the old convention. This is new-at-birth, not changed-in-flight — nothing to migrate and nothing to delete.

RK4: the risk is that Q1's exception widens into a persisted graph or a source of truth. D-5 (type-level) and INV-2 (no read-back API in S1) remain the two structural containments. The consumer-selection rule above is a written specification plus a pure, tested key-computation function — **not** a production read path.
