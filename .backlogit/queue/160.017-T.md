TRANSITION LEDGER (T16). This is the task that makes the two-class test contract MACHINE-ENFORCED rather than a labelling convention.

WHY THIS TASK EXISTS: the plan classifies every composition/verification case as either RED-FIRST or CHARACTERIZATION, and each class implies a REQUIRED PAIR OF OBSERVATIONS. Without a terminal task that checks the pairs actually occurred, the classification is unverified metadata - an agent could declare a case CHARACTERIZATION to excuse it from ever being red, or declare it RED-FIRST and never record the green. This task closes that loop and is the only task in the shipment that observes POST-CHANGE transitions.

SCOPE OF THE LEDGER - ALL 46 CANONICAL CASES (RECALCULATED IN REVIEW-FIX CYCLE 5; the cycle-4 figure of 52 / 35 / 17 and the cycle-3 figure of 51 / 35 / 16 are BOTH SUPERSEDED and MUST NOT be reintroduced). The plan's Case table is the single authoritative ledger: 46 cases, 32 RED-FIRST and 14 CHARACTERIZATION, authored T3a/160.005-T 22 (22 red, 0 char), T3b/160.016-T 4 (0 red, 4 char), T9/160.008-T 3 (1 red, 2 char), T10/160.012-T 3 (1 red, 2 char), T11/160.013-T 8 (5 red, 3 char), T12/160.009-T 4 (1 red, 3 char), T13/160.010-T 2 (2 red, 0 char). Column checks that MUST reconcile: 22+0+1+1+5+1+2 = 32 RED-FIRST; 0+4+2+2+3+3+0 = 14 CHARACTERIZATION; 22+4+3+3+8+4+2 = 46 TOTAL.

This task verifies all 46 pairs. A case present in the suite but ABSENT from the canonical table, or present in the table but ABSENT from the suite, is itself a FAILURE - the bijection between the table and the shipped suite is part of what this task asserts. Every RENAMED case above must match the shipped name EXACTLY; any OLD NAME appearing in the suite is a bijection break.

THIS LEDGER VERIFIES EVIDENCE; IT DOES NOT ACCEPT ATTESTATIONS (REWRITTEN IN REVIEW-FIX CYCLE 5, FINDING 10, REPLACING AN ATTESTATION MODEL WITH A VERIFICATION MODEL). The cycle-4 contract took each producer's recorded outcome AT FACE VALUE: it joined on `test_name` and compared self-declared fields. A ledger that trusts the record it is auditing verifies NOTHING - a task that never ran, ran a differently-named test, ran against a different commit, or edited its log afterwards would all be INDISTINGUISHABLE FROM A CLEAN PASS.

FIRST-OBSERVATION INPUT. The seven authoring tasks each write their FIRST observation to docs/audits/2026-09-03-ship10-payload-evidence/observations/{T3a,T3b,T9,T10,T11,T12,T13}.json, plus a BOUNDED RAW LOG under that producer's own logs subdirectory (see AUTHORIZED RAW-LOG PATHS below) - all inside the SAME single bounded evidence surface this task writes its ledger to, NOT a second store. This task READS those records and logs and MUST NOT modify them.

PER-FIELD VERIFICATION - EVERY ONE OF THESE IS AN INDEPENDENT CHECK PERFORMED BY THIS TASK, NOT A FIELD COPIED FROM THE RECORD:
- `exit_status`: the NATIVE PROCESS EXIT STATUS, a STRICT INTEGER. A boolean is REJECTED - `True` is not `1` here, and accepting it would let a truthy attestation stand in for a measured status. It MUST be NON-ZERO for a RED-FIRST first observation and ZERO for every other declared observation. Rejects a pass claimed with a zero-exit "red", and a red claimed with a non-zero-exit "green".
- `expected_outcome`: must EQUAL what the case's declared class requires for that observation slot. Rejects a record whose stated expectation contradicts its class.
- `case_name`: the CANONICAL LOGICAL CASE IDENTITY - the BARE case name, exactly as it appears as one of the 46 rows of the plan's canonical case ledger. It MUST match a ledger row VERBATIM, and it MUST NOT contain `::` or `/`. THIS IS THE JOIN KEY, and it is the ONLY field joined to the ledger. Rejects a renamed, misspelled or non-existent case.
- `test_node_id`: the EXECUTABLE IDENTITY - a FULL PYTEST NODE ID of the form `tests/<module>.py::<Class>::<test_method>`. It MUST contain `::`, and this task asserts THE NODE ID IS PRESENT IN THE OUTPUT OF `uv run python -m pytest --collect-only` FOR THE SHIPPED SUITE. A node id that does not collect is a REJECTION - a name that matches the table but does not collect is a fabricated result. The TRAILING COMPONENT of `test_node_id` MUST EQUAL `case_name`, which is what binds the executable identity to the logical one.
- TWO IDENTITY FIELDS, TWO DISJOINT SHAPES, AND NO FIELD MAY SATISFY BOTH (CYCLE 8, ITEM 3). `case_name` is REJECTED IF IT CONTAINS `::`; `test_node_id` is REJECTED IF IT DOES NOT. The shapes are mutually exclusive BY CONSTRUCTION, so a single value can never be silently used for both purposes and the two checks can never collapse into one. THE SPLIT IS A FIELD SPLIT, NOT A CASE ADDITION: the ledger remains 46 rows (32 RED-FIRST + 14 CHARACTERIZATION) and every per-author count is unchanged. The withdrawn single `test_name` field tried to be a ledger key AND a runnable id at once, which is why it drifted across records.
- THE RUNNER IS PYTEST AND THE COMMAND IS `uv run python -m pytest` (CYCLE 8, ITEM 2). AUTHORITY, MEASURED: `.github/instructions/constitution.instructions.md` declares `| Test | pytest (suite under tests/) |`; `.github/instructions/github-pr-automation.instructions.md` gives the canonical command `uv run python -m pytest`; and `pyproject.toml` carries a live `[tool.pytest.ini_options]` section with `pythonpath = ["src"]`. THE CYCLE-6 FINDING-2 WITHDRAWAL IS ITSELF WITHDRAWN: it removed node-id vocabulary on the ground that "this repository runs `PYTHONPATH=src python -m unittest discover -s tests`; there is no collection phase and no node id". CI DOES currently run `unittest discover`, but CI IS NOT THE AUTHORITY - the constitution and the PR-automation instruction are, and they both mandate pytest. The correct reading is that CI HAS DRIFTED FROM THE MANDATE, which 160.020-T (T0) corrects (REASSIGNED IN CYCLE 9 - the ci.yml changes moved off 160.015-T, which now owns release.yml ONLY); the fix is NOT to redefine the test contract around the drifted CI. Pytest node IDs are therefore the executable identity, and `unittest.defaultTestLoader.loadTestsFromName(...)` resolution is WITHDRAWN.
- `evidence_ref`: must RESOLVE TO AN EXISTING FILE under the authorized raw-log path for that producer. Rejects a dangling or absent log reference.
- `evidence_sha256` and `evidence_bytes`: this task RECOMPUTES the digest and size of the referenced log and COMPARES. Rejects a log edited or replaced after the run.
- `source_commit`: a FULL 40-CHARACTER SHA, **CAPTURED, NOT ASSERTED** (CYCLE 8, ITEM 4). The producing task runs `git rev-parse HEAD` IMMEDIATELY BEFORE the test command and writes the result into the raw log's head; `source_commit` is that captured value. THIS TASK RE-DERIVES IT FROM THE LOG AND REQUIRES AN EXACT MATCH - it does not merely check that the recorded SHA is well-formed and resolvable. Rejects a record whose `source_commit` disagrees with the HEAD its own log captured, which is the falsification a format-only check cannot catch.
- `worktree_status`: the VERBATIM output of `git status --porcelain=v1`, captured IMMEDIATELY BEFORE the test command and after the `git rev-parse HEAD` capture. **IT MUST BE EMPTY.** A NON-EMPTY VALUE IS REJECTED OUTRIGHT - a red or green observed on a dirty tree is not attributable to any commit, so it is not evidence. THE COMMIT COMES FIRST: the RED HARNESS COMMIT must exist before a RED observation is taken, and the GREEN IMPLEMENTATION COMMIT must exist before a GREEN observation is taken. Rejects an observation taken mid-edit.
- `observation_phase` (ADDED IN CYCLE 10, OPERATOR ITEM 7): the DECLARED PHASE OF THE OBSERVATION, exactly one of `baseline` or `post-change`. A missing, empty, or out-of-enum value is REJECTED. THIS FIELD SELECTS WHICH ARTIFACT IDENTITY SOURCE `artifact_ref` IS VALIDATED AGAINST; without it there is no way to tell an observation taken against the UNTRIMMED baseline build from one taken against the TRIMMED build under test, and the two have DIFFERENT DIGESTS BY CONSTRUCTION.
- `artifact_ref`: the built artifact's AGGREGATE DIGEST for the channel under test, RECOMPUTED BY THIS TASK USING THE PLAN'S SINGLE CANONICAL DEFINITION - SHA-256 over the newline-joined, PATH-LEXICOGRAPHICALLY-SORTED `(path, size, sha256)` triples, ASCII unit separator (U+001F) between fields, forward-slash-normalized UTF-8 paths (cycle 8, item 10; there is exactly ONE digest contract in this shipment and no variant form is accepted anywhere). TWO IDENTITY SOURCES, SELECTED BY `observation_phase` (CORRECTED IN CYCLE 10, OPERATOR ITEM 7): when `observation_phase` is `baseline`, `artifact_ref` is checked against 160.001-T's durable E1 BASELINE INVENTORY; when it is `post-change`, `artifact_ref` is checked against the CURRENT TRIMMED ARTIFACT INVENTORY produced by the run under test. THE WITHDRAWN CYCLE-8 RULE - checking EVERY `artifact_ref` against 160.001-T's baseline inventory unconditionally - IS FALSE AND MUST NOT RETURN: this shipment's entire purpose is to CHANGE the payload, so a post-change artifact's digest CANNOT equal the baseline digest, and a rule requiring that equality would fail every post-change observation while the shipment was working correctly. A POST-CHANGE ARTIFACT DIGEST IS NEVER REQUIRED TO EQUAL THE BASELINE DIGEST. WHAT SURVIVES UNCHANGED: `artifact_ref` - NOT `source_commit` - REMAINS THE ARTIFACT-IDENTITY FIELD, so a CHARACTERIZATION observation is tied to its artifact by DIGEST rather than by commit, which is what makes `same artifact, same behaviour` checkable ACROSS DIFFERING COMMITS. THE CYCLE-6 FINDING-11 WITHDRAWAL ALSO STANDS: requiring CHARACTERIZATION first observations to record 160.001-T's baseline COMMIT was wrong, because 160.001-T runs once and early while every later observation necessarily runs on a LATER commit. `source_commit` is a CAPTURED-AND-RE-DERIVED PROVENANCE field and is NOT an artifact-identity field. Rejects a result attributed to the wrong build.
- REVIEWED PARTITION RECORDS FROM 160.006-T AND 160.007-T (added cycle 6, finding 12): those two tasks are the only ones authorized to mutate tracked payload files, and each appends a REVIEWED PARTITION RECORD - the AC3e class table for its mutating run, the approval decision, and the R-3 approval reference - as a section of the pre-change byte record it writes into docs/audits/2026-09-03-ship10-payload-evidence/. THIS TASK VERIFIES BOTH: it RECOMPUTES OVERWRITE union REMOVE from the recorded class table and asserts it EQUALS the recorded approval set, and asserts the applied bytes match the recorded reviewed proposal. It DOES NOT look for such a record from 160.014-T, WHICH PRODUCES NONE - the generator returns and prints its partition and writes nothing under docs/audits/**.
- `declared_class`, `author_task` and `owner_task`: must MATCH the plan's canonical case ledger row for this `case_name` - the declared class, the authoring task ID, and the owning task ID respectively. `owner_task` is verified EXPLICITLY (added in cycle 10, operator item 8) because it is what binds an observation to the task whose green transition it evidences; a record that names the right case, the right class and the right author but the WRONG owner attributes a transition to a task that never made it. Where the ledger row carries TWO owners, the record's `owner_task` must be one of them, and BOTH owners must be covered across the ledger row's records. Every ledger row must have EXACTLY ONE observation record per declared observation slot.

REJECTION IS THE DEFAULT. A record that is MISSING any field, carries a MALFORMED value, or FAILS any comparison FAILS THE SHIPMENT. This task does not warn, does not skip, and does not treat an unverifiable record as a pass. A ledger row with no corresponding record likewise fails - SILENCE IS NOT A GREEN.

FAIL THE SHIPMENT on any of the following - each is a distinct failure mode and each must be reported by name, never collapsed into a generic failure:
- a case with NO DECLARED CLASS (classification is mandatory and exhaustive);
- a case declaring BOTH classes (the classes are mutually exclusive);
- a declared class with NO RECORDED FIRST OBSERVATION (the authoring task did not do its job);
- a RED-FIRST case with no recorded red (it was green on arrival - it never exercised the not-yet-built behaviour);
- a CHARACTERIZATION case with no recorded green-on-baseline (the baseline claim was never verified);
- a case in the suite with no row in the canonical table, or a row in the canonical table with no case in the suite (bijection break);
- ANY case that is red now;
- ANY per-field verification above that fails: non-integer or boolean `exit_status`, an exit status inconsistent with the declared class, an `expected_outcome` contradicting the class, a `case_name` that does not match a ledger row verbatim OR that contains `::` or `/`, a `test_node_id` that lacks `::` OR THAT DOES NOT APPEAR IN `uv run python -m pytest --collect-only` OR whose trailing component is not equal to `case_name`, a dangling `evidence_ref`, a recomputed digest or byte count that disagrees with `evidence_sha256`/`evidence_bytes`, a `source_commit` that is not a full 40-char SHA OR THAT DOES NOT MATCH THE `git rev-parse HEAD` VALUE CAPTURED IN THAT OBSERVATION'S OWN RAW LOG (it is NEVER required to equal 160.001-T's baseline SHA - baseline identity is carried by `artifact_ref`, not by `source_commit`; requiring a post-baseline observation to report the baseline SHA would be requiring it to misreport where it ran), a NON-EMPTY `worktree_status` (a dirty tree is rejected outright - an observation taken mid-edit is not attributable to any commit and is therefore not evidence), an `artifact_ref` that does not match 160.001-T's E1 inventory under the canonical `(path, size, sha256)` digest definition, or any missing/malformed field;
- ANY raw log exceeding the bounds below without a correctly-recorded truncation marker and pre-truncation counts;
- the run's recorded APPROVAL SET not equalling OVERWRITE union REMOVE recomputed from the generator's reported AC3e partition table (plan AC3e rule 4).
A DECLARED CLASS WITH NO RECORDED TRANSITION IS A FAILURE, NOT A PASS. Absence of evidence must never be read as evidence of success - that is the fail-open shape this shipment exists to remove.

BOUNDED LOGS (BINDING; cycle 5, findings 10 and 15). Unbounded raw logs turn an audit directory into a liability, so the limits are stated rather than implied, and this task ENFORCES them:
- PER LOG: <= 256 KiB AND <= 2,000 lines. A run exceeding either limit is truncated head-and-tail with an explicit truncation marker, and the record sets `truncated: true` with the pre-truncation byte and line counts. The digest is taken over the STORED (possibly truncated) file, so the recomputation check stays exact.
- PER CASE: at most 3 logs (first observation, second observation, one retry).
- PER SHIPMENT: at most 200 files under the logs root, and no single file may be a binary artifact.
- RETENTION: logs are retained until this task completes and the shipment closes; they are not pruned earlier and are not carried past closure.
