TRANSITION LEDGER (T16). This is the task that makes the two-class test contract MACHINE-ENFORCED rather than a labelling convention.

WHY THIS TASK EXISTS: the plan classifies every composition/verification case as either RED-FIRST or CHARACTERIZATION, and each class implies a REQUIRED PAIR OF OBSERVATIONS. Without a terminal task that checks the pairs actually occurred, the classification is unverified metadata - an agent could declare a case CHARACTERIZATION to excuse it from ever being red, or declare it RED-FIRST and never record the green. This task closes that loop and is the only task in the shipment that observes POST-CHANGE transitions.

SCOPE OF THE LEDGER - ALL 52 CANONICAL CASES (RECALCULATED IN EXTENDED REVIEW-FIX CYCLE 4; the cycle-3 figure of 51 / 35 / 16 is SUPERSEDED and MUST NOT be reintroduced). The plan's Case table is the single authoritative ledger: 52 cases, 35 RED-FIRST and 17 CHARACTERIZATION, authored T3a/160.005-T 25 (25 red, 0 char), T3b/160.016-T 7 (0 red, 7 char), T9/160.008-T 3 (1 red, 2 char), T10/160.012-T 3 (1 red, 2 char), T11/160.013-T 8 (5 red, 3 char), T12/160.009-T 4 (1 red, 3 char), T13/160.010-T 2 (2 red, 0 char). Column checks that MUST reconcile: 25+0+1+1+5+1+2 = 35 RED-FIRST; 0+7+2+2+3+3+0 = 17 CHARACTERIZATION; 25+7+3+3+8+4+2 = 52 TOTAL. WHAT CHANGED AND WHY: finding 5 RECLASSIFIED test_plugin_source_path_is_tracked_and_fetchable from RED-FIRST/T3a to CHARACTERIZATION/T3b (it is baseline-true - `source: "."` resolves to the tracked, fetchable repository root - and branch (a) preserves it, so it could never have been red), moving one case between authors and classes without changing the total; finding 9 ADDED test_target_workspace_prefixes_have_exactly_one_authored_occurrence as RED-FIRST/T3a with green owner 160.003-T (AC2d described it in prose but no ledger row named it, so it was invisible to this task and effectively unowned). T3a's red count is therefore UNCHANGED AT 25 by two offsetting moves, not by oversight. This task verifies all 52 pairs. A case present in the suite but ABSENT from the canonical table, or present in the table but ABSENT from the suite, is itself a FAILURE - the bijection between the table and the shipped suite is part of what this task asserts. NOTE ALSO the case RENAME under finding 6: test_plugin_payload_tree_is_self_excluded_and_flat is now test_plugin_payload_conforms_to_the_selected_strategy (branch-aware, still RED-FIRST/T3a, still green-owned by 160.007-T); the ledger must match the shipped name exactly, so the OLD NAME appearing in the suite is a bijection break.

FIRST-OBSERVATION INPUT - THE MACHINE-READABLE HANDOFF THIS TASK CONSUMES (added in extended review-fix cycle 4, finding 7). The seven authoring tasks each write their FIRST observation to docs/audits/2026-09-03-ship10-payload-evidence/observations/{T3a,T3b,T9,T10,T11,T12,T13}.json - a subdirectory of the SAME single bounded evidence surface this task writes its ledger to, NOT a second store. Each record carries: `test_name` (verbatim ledger row name), `declared_class`, `author_task`, `first_observation` ("red" or "green-on-baseline"), `observed_at`, `command`, `exit_status`, `failing_assertion` (non-null for red, null otherwise), `evidence_ref`. THIS TASK JOINS those records to the canonical case table ON `test_name` and asserts, for all 52 cases: every ledger row has EXACTLY ONE observation record; `declared_class` and `author_task` MATCH the ledger; `first_observation` is "red" IFF the class is RED-FIRST and "green-on-baseline" IFF CHARACTERIZATION. This is what turns "a recorded RED observation from the authoring task" from a prose expectation into a checkable join - before cycle 4 the authoring tasks had NO AUTHORIZED DESTINATION for these records at all, so this task was required to verify a first observation that had nowhere to durably exist. This task READS those records and MUST NOT modify them.

DELIVERABLE: re-run the COMPLETE suite against the BUILT TRIMMED ARTIFACTS - the built wheel, the built sdist, AND the resolved plugin payload - and produce a durable ledger asserting, per case:
- RED-FIRST cases: a recorded RED observation from the authoring task AND a GREEN observation now. Assert the transition red -> green.
- CHARACTERIZATION cases: a recorded GREEN-ON-BASELINE observation from the authoring task AND a GREEN observation now. Assert the preservation green -> green.

LEDGER DESTINATION (SHIP-10 plan H2, mandatory durable output): the ledger is written to docs/audits/2026-09-03-ship10-payload-evidence/ - the single bounded evidence surface authorized for this shipment in the H2 writable-surface table. It is a tracked, reviewable artifact, not a transient console dump: a transition ledger that exists only in a CI log cannot be cited by the shipment's closure record.

FAIL THE SHIPMENT on any of the following - each is a distinct failure mode and each must be reported by name, never collapsed into a generic failure:
- a case with NO DECLARED CLASS (classification is mandatory and exhaustive);
- a case declaring BOTH classes (the classes are mutually exclusive);
- a declared class with NO RECORDED FIRST OBSERVATION (the authoring task did not do its job);
- a RED-FIRST case with no recorded red (it was green on arrival - it never exercised the not-yet-built behaviour);
- a CHARACTERIZATION case with no recorded green-on-baseline (the baseline claim was never verified);
- a case in the suite with no row in the canonical table, or a row in the canonical table with no case in the suite (bijection break);
- ANY case that is red now.
A DECLARED CLASS WITH NO RECORDED TRANSITION IS A FAILURE, NOT A PASS. Absence of evidence must never be read as evidence of success - that is the fail-open shape this shipment exists to remove.
