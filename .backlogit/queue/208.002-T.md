BOTH classes derive the tier through ONE parse: a TARGETED REGEX over the template's frontmatter block (not a full YAML parse; template frontmatter can carry unquoted {{...}} values) for the {{TIER_<N>_FAMILY}} variable; exactly one distinct N gives default_tier="tier<N>" (the mapping _derive_tier_route_variables uses). UNRESOLVED DEFAULT: when the template cannot yield exactly one tier the site STILL registers managed=True, default_tier=None, and SiteRegistry.unresolved maps its id to a reason: template-path-unusable (community template_path fails containment, is missing, or is not a file), template-unreadable (read or decode error), no-tier-placeholder, or ambiguous-tier (more than one distinct N). The builder never raises, never guesses a tier, never demotes the site to workspace-authored (the class comes from the manifest, as in frontmatter_conformity where an unusable community template is 'unproducible', not unmanaged). A managed-rendered file whose template source is missing never reaches this branch (the classifier already treats it as unknown-provenance, so it registers workspace-authored). An unresolved site is still a KNOWN site (it exists, so an unbound one gets the B7 verdict) but is NOT BINDABLE: a binding on it is rejected up front by B6 (208.008-T) as ROUTING_BINDING_UNRESOLVED_SITE: <id>: <reason> and again by B7 (208.009-T), because a binding is applied only by overlaying the four TIER_<N>_* variables of one resolved tier (B6a, 208.007-T); B2 only records the reason and enforces nothing.
