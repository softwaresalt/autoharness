# CI-blocking checklist Recommended-Action truncation: authorize as separate auxiliary work unit on PR #373

## Problem Frame

<!-- BEGIN:problem-frame -->
Stash D71F6283 is a P-021 C2 DEFERRED SCOPE EXPANSION captured by Ship during shipment 143-S's PR-CI fix cycle. The required `test` and downstream `ci gate` checks on PR #373 fail on DeployHarnessPs1ChecklistExecutionTests.test_checklist_report_prints_non_interactively.

CONFIRMED ROOT CAUSE (static, single call site): scripts/deploy-harness.ps1 line 291 renders the pre-merge-install checklist as `$rows | Format-Table -AutoSize | Out-String | Write-Host`. PowerShell's `Out-String` falls back to an 80-column default width when stdout is redirected/non-TTY (as under the test harness and CI capture), so `-AutoSize` column widths are clamped and the RecommendedAction column is ellipsis-truncated ("retain-pre...", "needs-inst...") before the literals the test asserts on complete. The sh counterpart (scripts/deploy-harness.sh invoke_checklist) uses fixed-width `printf '%-24s'` and is NOT defective, which is exactly why only the Ps1 execution class fails. Exactly ONE Out-String/Format-Table call site exists in the ps1, so the defect surface is precisely bounded.

PRE-EXISTING AND UNRELATED TO 143-S: neither tests/test_deploy_harness_scripts.py nor scripts/ appear in the diff between merge-base 94898dc7 and branch HEAD fab2ed60; it reproduces on main and on a local Windows run. It surfaced now only because 143-S's PR is the first since 2026-08-16 (run 31942166603) to touch real .py test files and therefore the first to clear the workflow's "detect code changes" gate.

THE DEADLOCK: P-021 C4 forbids fixing it inside the discovering cycle. P-001 forbids a second in-flight release-unit PR. 143-S cannot merge while CI is red. Therefore neither "fix it in 143-S" nor "ship it as a second shipment now" is available, and the question is whether a C4 forward-authorized SEPARATE work unit may execute on the already-open branch/PR without becoming a silent 143-S manifest expansion.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
OPTION 1 — Expand 143-S scope and fix inside the active fix cycle.
REJECTED. P-021 C4 is unconditional and explicitly admits no override, "INCLUDING EXPLICIT OPERATOR AUTHORIZATION". Authorization is a FORWARD act that opens new work, never a RETROACTIVE one. Adding the task to the 143-S manifest would be the silent manifest expansion C4 exists to prevent, and would also invalidate the C1 classification already published in PR #373's residual-risk record.

OPTION 2 — Create a second shipment now and ship the fix on its own branch/PR.
REJECTED (blocked, not merely undesirable). P-001 permits at most one release-unit PR in flight; 143-S is active with PR #373 open and unmerged. P-016 additionally prohibits a second implementation branch/worktree while one is in use. And it does not even resolve the deadlock, because 143-S's own required checks stay red until the fix lands on 143-S's branch.

OPTION 3 — Wait: merge 143-S first, then fix separately.
NOT AVAILABLE. 143-S's required `test`/`ci gate` checks are red precisely because of this defect. Merging requires green CI (P-014/P-018 merge gates), so "merge first" is unreachable. This is a hard deadlock, not a preference.

OPTION 4 — Weaken or retarget the assertion in the failing test instead of fixing production output.
REJECTED. The assertion encodes a real user-visible contract: the operator reading a non-interactive/CI checklist report must see the complete Recommended Action literal, not an ellipsis. Retargeting the test to a machine-readable field (the stash's alternate suggestion) would make CI green while leaving the actual reporting defect shipped, and it is the drift risk recorded in docs/compound/2026-08-17-ci-skip-coverage-gap-prefer-pinned-binary-over-reimplementation.md (do not reshape the assertion to fit broken behaviour).

OPTION 5 (CHOSEN) — C4 forward-authorized SEPARATE auxiliary work unit, executed by Ship on the existing branch/PR #373, under its OWN covering feature, explicitly NOT added to the 143-S manifest.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
CHOSEN: Option 5 — a separate, explicitly approved auxiliary CI-unblocker work unit (own covering feature + one task), executed by Ship on the existing branch feat/143-s-... and PR #373, with NO mutation of the 143-S shipment manifest and NO second shipment.

WHY THIS IS POLICY-COMPLIANT, CLAUSE BY CLAUSE:

- P-021 C4 SATISFIED. C4 permits exactly this: "What explicit operator authorization CAN do is create or approve a SEPARATE work unit for the expansion, and only through the normal intake path: the C2 capture, then the mandatory C6 Stage deliberation/research/planning, then a new or expanded approved scope carried by that separate unit." The full path has been walked: C2 capture (D71F6283, by Ship) -> C6 Stage deliberation (this artifact) -> new approved scope (the new covering feature + task). C4's boundary is on SCOPE AUTHORITY, not on branch or PR identity. C1 is explicit that "same PR" is not a sufficient test of scope; symmetrically, a DIFFERENT PR is not a necessary condition of scope separation. The fix is executed under a different approved scope, not as an expansion of 143-S's approved scope.

- P-021 C1 PRESERVED. The published C1 classification stands unamended: a checklist table-rendering width defect remains a different contract surface from authoring P-021 policy carriers. Nothing here re-classifies it as in-scope for 143-S.

- P-001 SATISFIED. No second shipment and no second release-unit PR is created. Exactly one release unit (143-S) remains in flight. The auxiliary unit is deliberately shipment-less; it rides the in-flight PR as a distinct commit and is closed on its own path.

- P-016 SATISFIED, AND THIS IS THE DECIDING CONSTRAINT. Same-branch execution is the ONLY compliant option: creating a branch or worktree for the auxiliary unit while 143-S's implementation branch is in use is precisely the prohibited parallel-implementation state. The same-branch route is not a concession; it is what P-016 requires.

- P-015 SATISFIED BY CONSTRUCTION (non-obvious, and it drives the parenting decision). P-015's protected set for 143-S closure is its covering feature 134-F plus every unshipped 134.*-T sibling NOT in the manifest, and every protected-set member must remain in queue/ throughout closure. Parenting the auxiliary task under 134-F would make it a protected-set member, so completing and archiving it before or during 143-S closure would trip P-015's verify-after-each cascade gate as a FALSE POSITIVE and halt closure. Giving the auxiliary unit its OWN covering feature places it outside both the manifest and the protected set, leaving its lifecycle independent of 143-S closure. This is why a separate feature is created rather than reusing 134-F.

- P-010 / role separation PRESERVED. Stage authored the intake, deliberation, plan and backlog; Ship executes. Stage modified no source, template, test or config file and created no branch, worktree or shipment.

- NOT A SILENT EXPANSION. The relationship is recorded explicitly and in the open: a distinct feature/task pair with its own acceptance criteria, a relates_to link to 134-F, a blocks dependency making 143-S's merge-readiness depend on it, this deliberation, a decision record, and the existing residual-risk comment on PR #373 (issue comment 5354283673) that already names D71F6283. An auditor reading PR #373 can see two clearly labelled, separately approved scopes, not one quietly widened one.

TECHNICAL DIRECTION FOR THE FIX (bounded, test-first):
Preserve full Recommended Action literals in non-interactive output by giving the checklist render an explicit, generous output width instead of inheriting the 80-column redirected-stdout default — i.e. pass an explicit -Width to Out-String at scripts/deploy-harness.ps1:291 (or equivalently emit fixed-width rows mirroring the sh variant's '%-24s' contract). PARITY IS MANDATORY: templates/scripts/deploy-harness.ps1.tmpl:291 and the committed instance scripts/deploy-harness.ps1:291 must change identically, or DeployHarnessRenderingTests.test_template_renders_to_committed_instance fails. scripts/deploy-harness.sh must NOT be touched — it is already correct, and touching it is scope creep.

SHIP MAY PROCEED. No safe-sequencing blocker remains; the exact authority and scope are recorded on the created task.
