**LAYER 5 — assertion integrity. NO assertion is weakened; only failure-path DIAGNOSIS changes.**

This is the ONLY task in `144-F` that touches `src/autoharness/`, and only the `_run_git` diagnostic seam. Gate verdict semantics, tokens, and exit codes are OUT OF SCOPE and MUST NOT change.

## Part 1 — `src/autoharness/gates/topology.py:200` `_run_git`

Currently `check=False` and `return ""` on nonzero exit: a git INFRASTRUCTURE failure is laundered into "no branch" -> `detached_head` -> `BRANCH_MISMATCH` -> `exit_code == 1`. Victims #1 and #2 assert `exit_code == 0` and therefore fail with a FALSE DOMAIN DIAGNOSIS. Same anti-pattern as `docs/compound/2026-08-08-shell-pipeline-exit-status-masking-in-version-probes.md` (a failing probe's exit status discarded while partial stdout is still consumed).

**A3 (BINDING) — strictly additive and schema-safe:**

- Add ONE new key, `details['git_invocation_error']`, carrying the captured stderr.
- It is **ABSENT** (key not present at all) whenever every git invocation succeeded, so the success-path `details` payload is BYTE-IDENTICAL to today.
- It never replaces, renames, or reorders an existing key.
- `_run_git`'s return contract is UNCHANGED: still `""` on nonzero exit, so the gate's token and exit code are IDENTICAL on every path.
- Add a **verdict-equality test**: for a simulated nonzero git exit, `result.exit_code`, `check.token`, and EVERY pre-existing `details` key equal the pre-change behavior, AND the new key carries the captured stderr.
- **Re-run the consumer grep at THIS task's head** and record the result: `scripts/ci-topology-check.sh` and `tests/test_ci_topology_check_entrypoint.py` for whole-`details` equality or strict-key consumption. If ANY consumer compares exactly, route the diagnostic to stderr logging only and DROP the `details` key.

Pre-verified at plan-review time (review finding N1, informational only, NOT a substitute for the grep above): `scripts/ci-topology-check.sh` has zero `details` references; `tests/test_ci_topology_check_entrypoint.py` has zero; every `details` assertion in `tests/test_gates_topology.py` is an individual key lookup (`['current_branch']`, `['default_branch']`, `['detached_head']`, `['resolved_via_ci_env_fallback']`, `['default_branch_resolved_via_ci_env_fallback']`), never whole-dict equality; there is no JSON schema for topology output under `schemas/`.

## Part 2 — `tests/test_telemetry_gitignore_template.py:33`

`self.assertEqual(result.returncode, 0, f"{rel} is not gitignored")` reports a gitignore defect when git actually died at config-parse time. `git check-ignore` returns `0` = ignored, `1` = not ignored, `>=128` = error.

- Keep the `returncode == 0` assertion **EXACTLY AS STRONG** — do not relax, branch, or make it conditional.
- Branch only the MESSAGE on `returncode >= 2`, reporting the captured stderr as a git INVOCATION failure rather than a gitignore defect. Requires adding `capture_output`-derived stderr to the message (already captured at that seam).
- Add a test proving the new message appears for a simulated `returncode=128` and the ORIGINAL message for `returncode=1`.

**A6/AIG-2 (BINDING):** this message argument is the SINGLE authorized assertion-argument divergence in the whole feature. It must be cited line-by-line in the task record, and the assertion's non-message arguments (`result.returncode`, `0`) must still compare EQUAL under AIG-1.
