# Model routing v2: deterministic route resolver, tier-delta catalog, subagent site bindings (schema 1.2.0), staged escalation-chain and review-diversity follow-ups

## Problem Frame

<!-- BEGIN:problem-frame -->
Operator asked for an improved model routing mechanism using docs/design-docs/model-routing-v2.md as the baseline proposal. The baseline adds YAML-anchor route aliases, per-phase and per-subagent routes, a Ship escalation fallback with max_cycles, a cross-family anchor_review, and GPT-architect Stage routing. Verified against the repo: the baseline does not load as written (undefined aliases); with anchors defined it fails the current schema in 7 places; and most of its named phases/subagents (dispatcher, checkpoint_manager, conflict_evaluator, backlogit_ops, engram_curator, graphtor_indexer, architect/materialize/context_slice...) are not agents or invocation boundaries in this harness. Observed real gaps: (1) 13 installed subagent frontmatters carry stale install-time routes matching neither tier1 nor tier2 and verify-workspace checks only the 3 pipeline agents; (2) route-resolution logic is duplicated across verify_workspace helpers, agent-executed prose, and instruction docs, which already drifted (1F13DF5E, 3C19FA0F, stale escalation-protocol prose); (3) unknown model_routing keys pass the schema and are silently inert; (4) no per-subagent binding other than install-time tier. Full analysis: docs/decisions/2026-10-11-model-routing-v2-deliberation.md
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
A) Adopt the baseline as written (anchors, phases, subagents, max_cycles, tier3=GPT): rejected, does not load, fails schema, binds to non-existent sites, breaks the skill-inherits-route and same-route contracts. B) Adopt baseline semantics with a schema+loader rewrite (phases as sites): rejected, a phase inside one session cannot change model; would need isolated phase invocations (9B582824 keystone). C) Data-only: re-point existing role routes and anchor_review at a GPT architect/Claude reviewer: valid today, no mechanism needed, but leaves gaps 1-4. D) CHOSEN: deterministic resolver as single source of truth + tier-delta route catalog + installed-agent subagent site bindings + drift/unknown-key verification (additive schema 1.2.0, new mirror), then staged escalation chain and review-diversity invariant; phases deferred behind a promotion rule.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Option D, released in stages. R1 (planned and harvested now): src/autoharness/model_routing.py pure resolver with language-neutral conformance vectors; verify_workspace delegates to it; schema 1.2.0 adds model_routing.routes (named tier deltas, NO YAML anchors) and model_routing.bindings (agent:<id> sites enumerated from installed agent files, then classified managed or workspace-authored by joining to the manifest); verify checks for ref integrity, unknown sites, unknown model_routing keys (the 1.2.0 schema closes model_routing with an allowlist; advisory below 1.2.0), alias-free routing (ONE shared raw-YAML guard, R1-A unit A2a, called on the raw text before loading by both verify-workspace and the CLI), and subagent frontmatter drift; autoharness routing resolve CLI; install/tune/policy/doc updates; dogfood config values untouched. R2 (stash follow-up): ordered escalation.chain as a dispatchability fallback (analysis-only handoff preserved; max_cycles rejected). R3 (stash follow-up): invocation-time subagent/review directives plus review-diversity invariant (routing concern, evidence only, never a P-014/P-018 merge gate). R4 (gated): phase-site promotion with 9B582824 component A/C. Resolution precedence per field: site binding delta -> catalog tier -> tier fallback -> terminal default (context_tier only); frontmatter is a rendered default, not part of the chain.
<!-- END:chosen-direction -->
