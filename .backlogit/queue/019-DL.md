# P-021 Bounded Fix-Cycle Scope Containment &amp; Deferred Expansion Capture

## Problem Frame

<!-- BEGIN:problem-frame -->
Operator direction B48A482A: when fixing a bug or resolving a Copilot review comment would expand work beyond the currently approved feature/task scope, the expansion MUST NOT be implemented in that fix cycle. It must be captured as a separate stash entry for later Stage triage plus MANDATORY deliberation/research before planning or implementation. The active feature/task stays bounded. Review pressure, severity, dark mode, and convenience do not authorize silent scope expansion. The original in-scope defect/comment is still resolved as far as possible without the expansion, and the deferred expansion ID is referenced in the review reply / residual-risk record.

Current harness state (verified 2026-08-18):

- No named policy encodes this. The closest artifact is a compound learning (docs/compound/2026-08-16-bounded-review-fix-cycle-scope-and-mechanical-consequence-judgment.md) captured from PR #348, which is advisory prose, not a policy with a violation action.
- The circuit-breaker instruction's "Review-Fix Cycle Definition" bounds the NUMBER of cycles (3) but says nothing about the SCOPE of a fix within a cycle. An agent can stay under 3 cycles while silently expanding scope.
- github-pr-automation's autonomous comment-handling loop tells the agent to "fix valid comments" with no scope test.
- CRITICAL LATENT CONTRADICTION: templates/agents/_ship.agent.md.tmpl line 38 Role Boundary lists "stash operations" in Ship's FORBIDDEN column, while Ship Step 9 (pre-merge, line 527-530) and post-merge Step 6 (line 763-766) already REQUIRE Ship to create stash entries for follow-ups. role-enforcement.instructions.md mandates fail-closed halt + P-010 violation on any forbidden-column operation. Mandating a mid-cycle stash capture without resolving this makes the required behavior a policy violation by construction.
<!-- END:problem-frame -->

  Rejected: the direction covers bug fixes and CI/build fixes, not just Copilot review comments; and P-018 is a pre-merge gate verdict, whereas this is an in-cycle authoring constraint. Overloading P-018 would blur a deterministic gate with a judgment rule.

Option C - New workflow policy P-021 carried coherently across policy registry, agent templates, shared instructions, skills, prompts, dogfood surfaces, manifest checksums, and a contract test. CHOSEN.

Option D - Option C plus a deterministic CLI gate (autoharness gate scope-containment).
  Rejected for this shipment: "did this fix expand scope" has no machine-detectable signal; a diff-size or touched-file heuristic would produce false BLOCKs and would be trivially defeated. Recorded as residual risk / future work rather than implemented.

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Option C. Author a new named workflow policy **P-021: Bounded Fix-Cycle Scope Containment & Deferred Expansion Capture** (Amendment Log 1.20.0) and carry it across every coherent autoharness surface, keeping source templates and dogfood-generated surfaces byte-consistent with refreshed manifest checksums.

Normative content of P-021:

1. **Scope test (narrow and literal).** Promote the PR #348 compound learning from advisory prose to the normative in-scope test: a finding is in scope only if fixing it requires ONLY completing the exact change already authorized (the same contract surface). "Same file", "same function", "same PR", "same subsystem", or "related" is NOT sufficient. Anything requiring original design/decision work or an unrelated code path is OUT of scope. When genuinely ambiguous, the fail-safe default is OUT of scope + defer.
2. **Mandatory capture, not silent drop.** An out-of-scope expansion MUST be captured as a stash entry carrying a DEFERRED SCOPE EXPANSION marker, the source refs (PR number when applicable, review-thread ID when applicable — separate refs whose availability is judged independently, not a single fused PR/thread ID — plus task/feature ID and shipment ID), and a `requires deliberation` flag. Capture is a precondition for closing the finding, not an optional courtesy, and is never conditional on a PR or review thread existing.
3. **Bounded resolution of the original.** The in-scope defect/comment is still resolved as far as possible WITHOUT the expansion. The reference obligation is conditional on actual thread availability: where a review thread exists, the deferred entry ID is referenced in the review-thread reply and in the PR/closure residual-risk record, which satisfies P-018 zero-unresolved-threads honestly without fabricating scope; where no thread exists (pre-PR local review, build/CI), the obligation is discharged in full by the task/run/closure residual-risk citation, and P-018 raises no obligation because there is no thread to leave unresolved.
4. **Non-bypass.** Review pressure, finding severity, dark factory mode (P-017), circuit-breaker exhaustion, and apparent convenience never authorize expansion — and neither does any authorization, explicit operator authorization included. Nothing expands the fix cycle that discovered the expansion. Explicit operator authorization can create or approve a **separate** work unit for the expansion, and only through the normal intake path (capture, then mandatory Stage deliberation, then a new/expanded approved scope); it is a forward act that opens new work, never a retroactive one that makes an already-discovered expansion in-scope for the cycle in flight.
5. **Ship capture-only carve-out (resolves the P-010 contradiction).** Ship MAY create stash entries for capture only. Ship MUST NOT triage, prioritize, re-classify, edit, harvest, deliberate on, discretionarily remove, or discretionarily archive them. The one disposition that remains Allowed is the manifest-derived retirement of the source stash entry that fed the shipped scope, performed after a successful merge by Ship's existing post-merge Step 7: the distinction is PROVENANCE, not verb. The Ship Role Boundary table and role-enforcement's fail-closed pre-mutation protocol are amended together so the required capture is Allowed rather than a P-010 violation.
6. **Stage intake obligation.** A stash entry marked DEFERRED SCOPE EXPANSION is a distinct triage classification that MUST route to the deliberate skill (Stage Step 2) before any planning, regardless of shape or apparent triviality.
7. **Violation action.** Implementing an out-of-scope expansion inside a fix cycle, or closing an out-of-scope finding without a captured deferred entry, records a P-021 violation via P-005 telemetry and halts.
