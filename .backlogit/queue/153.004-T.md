DE-RISKING PREREQUISITE (SHIP-3 plan H9, two-axis gate). BLOCKS 153.001-T and 153.002-T; neither may begin until this matrix is recorded. NO PRODUCTION EDITS - recorded findings only, written to docs/. Produce a two-platform (Windows PowerShell + POSIX sh) behaviour matrix for the file-lock path-resolution and lock-path computation over SEVEN escape cases: (1) absolute path outside the workspace root; (2) ../ traversal; (3) directory symlink/junction pointing outside the root; (4) sibling directory whose name shares the root's prefix (/repo vs /repo-evil - the prefix-string containment trap forbidden by H4); (5) root-level target file that EXISTS; (6) root-level target file that is MISSING (the Split-Path -Parent empty-string defect, finding 6); (7) nested git checkout where `git rev-parse --show-toplevel` resolves to the PARENT repository (plan-review finding 2). For EACH cell record: the observed behaviour of the current resolution primitive, and the intended post-fix behaviour. SECOND DELIVERABLE - CANONICAL TOKEN/DIGEST INTEROPERABILITY VECTORS (ADDED IN ORCHESTRATOR REVIEW-FIX CYCLE 1, FINDING 16). This task is the declared prerequisite of 153.002-T, but the path-resolution matrix alone does not supply what 153.002-T's TOKEN CONTRACT actually needs. 153.002-T binding TC4 requires that a token acquired under one platform variant VERIFIES under the other; that is an INTEROPERABILITY contract between two independent implementations (PowerShell and POSIX sh), and two implementations cannot be shown to agree without SHARED CANONICAL VECTORS agreed BEFORE either is written. Producing them after the fact would mean deriving the "expected" value from whichever implementation was written first, which proves nothing. Therefore this task MUST additionally record, as committed docs/ content:
(V-a) TOKEN ENCODING CANONICALIZATION - the exact byte sequence a token is, stated unambiguously: character set and alphabet, length in characters AND in bits of entropy (>= 128 per the token contract), text encoding (UTF-8, no BOM), case sensitivity, and the explicit absence of any trailing newline or CR. State it as bytes, not as "a string", because the CRLF/LF split between the two platforms is exactly where a silent mismatch would live.
(V-b) DIGEST CANONICALIZATION - the exact input fed to the digest function (token bytes only, or token bytes plus a declared separator/salt - name which), the algorithm (SHA-256 or stronger; MD5/SHA-1 forbidden), and the output representation (hex vs base64, upper vs lower case, no trailing newline). PowerShell Get-FileHash and POSIX sha256sum differ in default output case and in trailing-whitespace/filename suffix handling; the canonical form must pin all three.
(V-c) AT LEAST FIVE FROZEN (token -> owner_digest) VECTORS, written literally in the doc so both implementations are tested against the SAME constants rather than against each other. Include deliberately adversarial cases: an all-lowercase-hex token, a token containing the maximum-value character in the declared alphabet, ONE CANONICAL VALID-LENGTH TOKEN, and one vector whose plaintext token differs from another vector only in its LAST character (so a truncating implementation is caught). CORRECTED IN REVIEW-FIX CYCLE 2, FINDING 12 - the cycle-1 wording asked for "a minimum-length token" AND "a maximum-length token", which is UNSATISFIABLE against TC2: TC2 declares the token encoding FIXED LENGTH, so there is exactly ONE valid length and therefore no distinct minimum-valid and maximum-valid token. An author trying to honour both clauses would have to either invent a variable-length encoding - contradicting TC2 and reopening the shell-word-safety and truncation risks TC2 exists to close - or record the same token twice under two different labels, which is a fake vector. Record ONE canonical valid token at the single length declared in V-a.

(V-c2) LENGTH-BOUNDARY REJECTION VECTORS - INVALID BY CONSTRUCTION (ADDED IN REVIEW-FIX CYCLE 2, FINDING 12). Because the valid length is fixed, the boundary worth testing is the REJECTION boundary, not a range of accepted lengths. Record TWO literal tokens that are well-formed in every respect EXCEPT length: ONE CHARACTER SHORT and ONE CHARACTER LONG relative to the canonical length. Both are INVALID. They have NO owner_digest at all - they are rejected before any digest is computed - so what this task records for them is the FAIL-CLOSED OBSERVABLE, not a (token -> owner_digest) pair: non-zero exit, named error, NO LOCK ACQUIRED, and no digest emitted. These two vectors catch the two real defects a fixed-length contract is exposed to: an implementation that PADS OR TRUNCATES a wrong-length token into the valid length, silently accepting an attacker-supplied short token; and one that validates a PREFIX and ignores trailing characters. A one-character-short token that is ACCEPTED is a security defect, not a formatting nit.

(V-c3) CROSS-PLATFORM INTEROPERABILITY EXPECTATION FOR THE LENGTH BOUNDARY (ADDED IN REVIEW-FIX CYCLE 2, FINDING 12). For the canonical valid token AND for both invalid boundary tokens, PowerShell and POSIX must produce the SAME VERDICT and the SAME OBSERVABLE: identical accept/reject decision, identical digest for the accepted vector, and for the two rejected vectors a non-zero exit with no lock acquired on BOTH platforms. Record this as a per-vector two-cell expectation mirroring V-d's directionality. This is not redundant with V-d: a length check implemented with a platform-specific string primitive - .Length over UTF-16 code units in PowerShell versus a byte- or character-oriented check in POSIX - is exactly where the two implementations silently disagree, and a single-platform boundary test cannot see it.
(V-d) A ROUND-TRIP DIRECTION MATRIX - acquire-on-PowerShell/verify-on-POSIX and acquire-on-POSIX/verify-on-PowerShell recorded as two SEPARATE cells with observed and intended behaviour, because a one-directional check passes trivially when both sides share the same bug.
(V-e) THE NO-SHA-256-UTILITY FAIL-CLOSED VECTOR - the expected observable behaviour (non-zero exit, named error, NO lock acquired) when no SHA-256-or-stronger utility is available, recorded per platform, so 153.002-T's fail-closed assertion has a declared expected value rather than an invented one.
EXPLICIT PREREQUISITE RELATIONSHIP: 153.002-T MUST cite V-a through V-e by name as the source of its TC1-TC6 expected values and MUST NOT compute an expected digest from its own implementation. This task remains RECORD-ONLY - no production edits; the vectors are computed with standard platform utilities and written down, not baked into a script. ACCEPTANCE: matrix covers all 7 cases x 2 platforms with observed AND intended behaviour in every cell; committed to docs/; explicitly referenced by 153.001-T and 153.002-T as their test vectors. Acceptance also requires V-a through V-e present, each vector reproducible by an independent reader using standard platform utilities, and explicitly referenced by 153.002-T. SAFETY MODE: careful.
