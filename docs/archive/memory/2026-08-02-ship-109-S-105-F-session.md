## Review Cycles

* **Local adversarial review (cycle 1/3)**: a code-review subagent found a
  genuine P1 — the Required Protocol step only matched record status
  queued/blocked, leaving the mainline `active` record status (normal at
  the skill's own mandatory Ship Step 6 invocation site) with no defined
  branch. Fixed by adding an explicit ACTIVE/DONE-always-consistent branch
  and tightening the mutual-exclusivity claim. Also fixed a P3 (dead
  `if False else` ternary in a test assertion).
* **Copilot review pass 1**: found that the new classification aggregated
  status over the untyped `items` manifest list without filtering to task
  artifacts, so a covering feature entry (e.g. in a fallback-assembled
  manifest) could be misread as a "conflicting task" and cause a false
  halt. Fixed by filtering to `artifact_type: task` before aggregating
  (reusing the type already read in step 3, no new read) — mirrors the
  Ship agent's existing task-artifact filter for its own intake
  early-warning scan (`106-S`).
* **Copilot review pass 2**: raised a broader, valid-but-out-of-scope
  concern — safe-close step 4 (pre-existing, unrelated to this PR)
  archives every manifest item generically regardless of `artifact_type`,
  so a malformed manifest containing a non-task id could still be
  archived. Classified **Partial**: declined the broader remedy (reject
  malformed manifests / remove a fallback seed feature) as out-of-scope for
  this task's approved plan (would touch pre-existing step 3/4 behavior
  outside 105.002-T's Scope-Boundary). Recorded as an explicit residual-risk
  note in the PR body rather than implemented; Ship does not create backlog
  items or expand scope mid-session.

## Reusable Lesson

**Aggregate/rollup checks over an untyped manifest items list must filter by
artifact_type before computing the aggregate — not just when scanning for a
specific known-bad case.** This is the second time this exact pitfall has
been caught in this repo's shipment-reconcile / Ship claim-integrity family
(first in the Ship agent's Unit B `SHIPMENT_STATE_INCONSISTENT` scan,
`106-S`; now in `shipment-reconcile` pre-mode's new record-status
classification, `109-S`). Any future check that aggregates status across
`custom_fields.items` (or an equivalent manifest list) should apply the
task-artifact filter as a first-class step in its own design, not as an
afterthought caught by review.

**Declining a valid-but-broader review finding requires an explicit,
specific rationale tied to the approved plan's Scope-Boundary** — a vague
"out of scope" is not enough; cite the exact boundary text and explain why
implementing the full remedy would touch pre-existing behavior the current
task never modified.
